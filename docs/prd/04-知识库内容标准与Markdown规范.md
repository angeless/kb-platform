# 知识库内容标准与 Markdown 规范

## 1. 总体原则
平台生成的知识文档必须满足以下原则：
- 不裁剪核心信息；
- 不以总结替代证据；
- 保留来源定位；
- 支持版本化；
- 对 AI 友好，对人类也可读。

## 2. 为什么不能只输出一份总结
单份总结看似简洁，但会带来三类问题：
- 细节丢失，后续无法核对；
- 冲突被抹平，错误难发现；
- 新资料无法稳定增量补入。

因此必须拆成多种类型的 Markdown 文档。

## 3. 文档类型
### 3.1 来源索引文档
记录这一批知识来自哪些原始材料。

### 3.2 主题文档
围绕某个主题形成完整说明。

### 3.3 流程文档
用于描述步骤、顺序、角色和条件。

### 3.4 FAQ 文档
用于沉淀高频问答。

### 3.5 实体文档
围绕某个实体，例如产品、部门、角色、客户对象、工具等沉淀知识。

### 3.6 术语表
用于统一词汇定义，避免后续 AI 理解不一致。

### 3.7 冲突文档
用于明确记录相互矛盾的信息，不允许强行合并。

### 3.8 维护说明文档
告诉后续 AI 或维护者如何继续补充和修正知识库。

## 4. Markdown 基础结构
每份正式知识文档建议包含：
1. 标题；
2. 文档元信息；
3. 适用范围；
4. 正文内容；
5. 来源列表；
6. 版本记录；
7. 更新说明；
8. 关联节点。

## 5. 文档头信息示例
```md
---
doc_id: kb_doc_001
doc_type: topic
title: 客服退款规则
industry: 电商
knowledge_node_id: node_003
version: 1.0.0
status: published
source_refs:
  - src_001
  - src_008
updated_at: 2026-03-09
---
```

## 6. 来源引用规范
每一个关键结论都应该能追溯到来源，至少能定位到：
- 文件；
- 页码或时间戳；
- 段落或片段。

## 7. 冲突处理规范
当两个来源对同一问题给出不同结论时：
- 不允许直接合并成一个看似一致的结论；
- 必须保留冲突双方；
- 写明适用时间、适用范围和信心等级。

## 8. 版本规范
每次补充、修正和废弃都要写版本记录。
