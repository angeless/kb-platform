# 开发任务拆分与 Sprint 计划

## 1. 开发总原则
- 先打通最小闭环，再扩展能力；
- 先保证追溯和治理，再优化自动化；
- 先做架构管理，再做大规模增量更新；
- 所有阶段都必须可测试、可回归。

## 2. 推荐团队分工
### 产品
负责需求澄清、验收口径、业务流程校对。

### 前端
负责 Web 端页面、可视化架构编辑、审核工作台。

### 后端
负责 API、任务编排、数据存储、权限与审计。

### AI 工程
负责解析链路、Prompt 模板、模型路由、质量校验。

### QA
负责测试用例、回归验证、发布前验收。

## 3. Sprint 规划
### Sprint 1：最小可用闭环
目标：实现资料上传、解析、架构初稿生成、知识文档草稿输出。

任务：
- 建立项目与资料表；
- 完成文件上传和 URL 导入；
- 完成基础解析器接入；
- 完成初版架构生成；
- 完成知识文档基础模板输出；
- 完成任务状态页。

### Sprint 2：审核与发布
目标：实现人工审核、正式发布、版本记录。

任务：
- 审核中心；
- 文档状态流转；
- 架构版本发布；
- 来源绑定与版本记录；
- 基础全文检索。

### Sprint 3：增量更新与冲突治理
目标：新材料进入后可判断是新增、补充、修正还是冲突。

任务：
- 增量接入 API；
- 旧知识匹配；
- 冲突记录与处理页；
- 文档版本比对；
- 架构节点待确认池。

### Sprint 4：模型配置与治理能力
目标：支持多模型配置、路由规则、租户隔离、安全和审计。

任务：
- 模型配置页；
- 密钥加密存储；
- 模型路由规则；
- 审计日志；
- 权限控制完善。

## 4. 关键里程碑
- M1：完成从上传到草稿输出；
- M2：完成架构审核与发布；
- M3：完成增量更新；
- M4：完成生产可用治理能力。

## 5. 完成定义
每个任务完成必须满足：
- 有代码；
- 有接口文档；
- 有单元测试或集成测试；
- 有失败场景处理；
- 有日志埋点；
- 可被 QA 验证。
