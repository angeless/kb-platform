# 数据模型与存储设计

## 1. 存储分层原则
平台必须把“保存”拆成四层：
1. 原始文件层；
2. 元数据层；
3. 结构化知识层；
4. 索引层。

## 2. 为什么不能只存 Markdown
如果只存 Markdown，会丢失：
- 原始证据；
- 解析状态；
- 任务记录；
- 冲突与版本信息；
- 检索索引。

因此必须多层存储。

## 3. 核心实体
### 3.1 租户 tenant
表示一个独立组织或客户。

### 3.2 项目 project
表示一个具体知识工程项目。

### 3.3 资料 asset
表示用户上传或导入的原始材料。

### 3.4 解析片段 asset_chunk
表示从原始资料中提取出的结构化片段。

### 3.5 架构 architecture
表示某个项目下的知识系统架构版本。

### 3.6 架构节点 architecture_node
表示架构中的具体节点。

### 3.7 知识文档 knowledge_doc
表示正式知识内容。

### 3.8 文档版本 knowledge_doc_version
表示知识文档的每次更新记录。

### 3.9 来源引用 source_ref
表示文档某个结论关联的来源。

### 3.10 冲突 conflict_record
表示未被合并的矛盾知识。

### 3.11 任务 job
表示异步处理流程中的任务。

### 3.12 模型配置 model_provider / model_route
表示模型供应商与调用路由配置。

## 4. 存储建议
- 对象存储：保存原文件、网页快照、架构图片；
- PostgreSQL：保存元数据、文档、版本、架构、任务；
- 向量库：保存语义检索索引；
- 搜索引擎：保存全文检索索引；
- 缓存：保存热数据和任务状态。

## 5. 关键关系
- 一个租户有多个项目；
- 一个项目有多个资料；
- 一个项目有多个架构版本；
- 一个架构版本有多个节点；
- 一个文档绑定一个主节点，但可引用多个相关节点；
- 一个文档版本可关联多个来源；
- 一个冲突记录可关联多个文档版本和来源。

## 6. 最低可用字段建议
### asset
- id
- project_id
- asset_type
- filename
- source_url
- object_path
- file_hash
- parse_status
- uploaded_by
- uploaded_at

### architecture_node
- id
- architecture_id
- parent_id
- node_name
- node_type
- level
- description
- accept_types
- reject_types
- review_policy
- status

### knowledge_doc
- id
- project_id
- node_id
- doc_type
- title
- current_version
- status
- created_at
- updated_at

## 7. 版本与回滚
任何知识文档和架构版本都必须支持：
- 查看历史版本；
- 对比差异；
- 回滚到已发布版本；
- 保留回滚原因。
