# 代码脚手架与初始化规范

## 1. 这份文件解决什么问题
这份文件用于约束项目的初始代码结构，避免开发人员在开工时因为目录随意、职责不清、配置散落而导致后续持续返工。

所谓“脚手架”，不是业务功能本身，而是项目的基础骨架。它决定代码放在哪里、模块如何拆分、配置如何读取、日志如何记录、接口文档如何生成。

## 3. 各层职责解释
### 3.1 apps/web
用户通过浏览器操作的平台前端。它负责上传材料、查看任务、审核知识、编辑架构图、管理模型配置。

### 3.2 services/api
处理登录、权限、项目管理、文档读取、任务下发、审核发布等请求。它是系统的业务入口。

### 3.3 services/ingestion-worker
负责把原始材料转换成统一中间格式。例如 OCR、ASR、URL 抽取、压缩包解包、视频抽帧。

### 3.4 services/ai-orchestrator
负责调用大模型，并根据不同任务使用不同提示词与输出模板。

### 3.5 services/pipeline-worker
负责驱动完整流水线，把“采集结果”推进到“分类、生成、质检、待审核、发布”。

## 4. 初始化要求
- 所有服务必须支持本地启动、Docker 启动、CI 运行三种模式。
- 所有配置必须从环境变量读取，不允许把 API Key 写死在代码里。
- 所有服务必须提供 `/healthz` 与 `/readyz`。
- 所有对外接口必须优先维护到 `openapi/openapi.yaml`。
- 所有新模块必须说明输入、输出、依赖、失败处理。

## 5. 分支与发布规范
- `main`：稳定主分支。
- `develop`：集成分支。
- `feature/*`：功能开发。
- `fix/*`：问题修复。
- `release/*`：上线准备。

## 6. 禁止事项
- 禁止直接在业务代码里拼接 SQL 与模型提示词。
- 禁止把“知识系统架构”逻辑写死在前端。
- 禁止仅保存 AI 结论而不保存来源。
- 禁止跳过审核直接把生成文档发布到正式知识库。
