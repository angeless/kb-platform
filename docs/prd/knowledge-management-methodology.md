## 〇、方法论总纲

KB Platform 的核心价值不是"文件管理"，而是**知识结构化**。我们处理的不是文件，而是文件中承载的**知识单元**。

核心理念：**理解 → 结构 → 归位 → 连接**

```
                    ┌─────────────────────────┐
                    │    知识管理四阶段模型      │
                    └────────────┬────────────┘
                                 │
          ┌──────────┬───────────┼───────────┬──────────┐
          ▼          ▼           ▼           ▼          ▼
     ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐
     │ 理 解  │ │ 结 构  │ │ 归 位  │ │ 连 接  │ │ 演 化  │
     │        │ │        │ │        │ │        │ │        │
     │解析原文│ │建立骨架│ │放到对的│ │建立关联│ │持续进化│
     │提取知识│ │组织体系│ │位置    │ │形成网络│ │自我修复│
     └────────┘ └────────┘ └────────┘ └────────┘ └────────┘
```

## 一、首次创建知识库：如何理解并结构化传入的信息

### 1.1 问题本质

用户首次上传一批资料时，系统面对的是**无结构的混沌信息**。核心挑战是：在对领域一无所知的情况下，如何产生一个合理的知识结构？

### 1.2 方法论：三阶段渐进式建构

#### 第一阶段：理解（Understanding）

**目标**：理解传入资料"在谈什么"，而不是急于分类。

**具体操作**：

1. **内容解析**（已有 — ingestion-worker）
   - 多模态解析：PDF → 文本、音频 → ASR、图片 → OCR
   - 分块（chunking）：按段落/章节切分，保留上下文

2. **知识元素提取**（新增增强）
   对每个 chunk 提取：
   - **主题标签**：这段内容在讨论什么主题？（2-5 个关键词）
   - **知识类型**：事实（Fact）/ 流程（Process）/ 规范（Rule）/ 定义（Definition）/ 案例（Case）
   - **受众层级**：入门 / 进阶 / 专家
   - **时效性**：永久有效 / 有时效 / 已过期
   - **来源质量**：官方文档 / 教程 / 个人笔记 / 讨论

3. **领域识别**
   综合所有 chunk 的主题标签，识别：
   - 这批资料属于什么行业/领域？
   - 涉及哪些核心概念？
   - 是否有明显的上下游关系？

#### 第二阶段：结构（Structuring）

**目标**：建立知识骨架（架构树），而不是随便堆文件夹。

**核心方法：MECE + 分类维度声明**

MECE（Mutually Exclusive, Collectively Exhaustive）= 互斥且穷举。每个知识单元应有且仅有一个"主位置"。

**分类维度选择**（按资料特征自动推荐）：

| 维度 | 适用场景 | 示例 |
|------|---------|------|
| **按主题**（Topic-based） | 知识百科、技术文档 | `数据库 > 索引 > B+树` |
| **按流程**（Process-based） | SOP、操作手册、项目管理 | `需求 > 设计 > 开发 > 测试` |
| **按受众**（Audience-based） | 培训资料、分级教程 | `新手入门 > 进阶实践 > 专家深潜` |
| **按时间**（Chronological） | 日志、记录、历史 | `2024Q1 > 2024Q2 > 2024Q3` |
| **混合**（Hybrid） | 复杂知识体系 | 一级按主题，二级按流程 |

**架构提议流程**：

```
输入：所有 chunk 的主题标签 + 知识类型 + 领域识别结果
  ↓
步骤 1：LLM 分析主题标签的聚类模式
  ↓
步骤 2：LLM 推荐最佳分类维度（附理由）
  ↓
步骤 3：LLM 生成架构树（3-5 层，每层 3-7 个节点）
  ↓
步骤 4：自动质量检查
  - MECE 检查：是否有遗漏？是否有重叠？
  - 深度检查：不超过 5 层
  - 平衡检查：没有节点包含 >60% 的内容
  - 孤儿检查：没有空节点
  ↓
步骤 5：输出架构提议 + 覆盖度评分 + 未归类内容列表
  ↓
步骤 6：用户审核 → 确认 / 调整 → 定稿
```

#### 第三阶段：归位（Placement）

**目标**：将每个知识 chunk 放到架构树中正确的位置，并生成结构化文档。

**归位策略**：

```
对每个 chunk：
  1. 计算与每个叶子节点的语义相似度
  2. 选择相似度最高的节点作为"主归位"
  3. 如果相似度 < 0.3，标记为"未归类"，提交人工审核
  4. 如果与多个节点相似度都 > 0.7，标记为"交叉引用候选"
```

**文档生成规则**：
- 同一架构节点下的多个 chunk 合并为一篇结构化文档
- 文档必须包含：标题、正文、关键词、知识类型、来源追溯
- 严禁编造不在原文中的信息（反幻觉约束）
- 矛盾内容保留并标注，不强行合并

|-----------|------------|------|-----------|

## 二、为知识库增加知识：增量合入策略

### 2.1 问题本质

知识库已有结构，新资料进来后，需要判断：它是新东西，还是对已有内容的补充、修正或挑战？如果现有结构装不下它，该怎么办？

### 2.2 方法论：五分类决策树

```
                     新资料进入
                         │
                    ┌────┴────┐
                    │ 理解内容 │
                    └────┬────┘
                         │
              ┌──────────┼──────────┬──────────┬──────────┐
              ▼          ▼          ▼          ▼          ▼
         ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐
         │  新增  │ │  补充  │ │  修正  │ │  冲突  │ │ 重构   │
         │  NEW   │ │SUPPLE- │ │CORREC- │ │CONFLICT│ │RESTRUC-│
         │        │ │MENT    │ │TION    │ │        │ │TURE    │
         └────┬───┘ └────┬───┘ └────┬───┘ └────┬───┘ └────┬───┘
              │          │          │          │          │
         创建新文档  合并到已有  更新已有    标记冲突   提议结构
         归入节点    文档中     并记录版本  等待人工   变更
```

#### 分类一：新增（NEW）

**判定条件**：新内容的主题在现有架构中没有对应节点（语义相似度 < 0.3）

**处理**：
1. 在最相近的父节点下创建新的子节点
2. 生成新文档
3. 如果找不到合适的父节点（与任何节点相似度 < 0.2），触发"结构扩展建议"

#### 分类二：补充（SUPPLEMENT）

**判定条件**：新内容与已有文档主题一致（相似度 > 0.7），但包含已有文档中不存在的信息

**处理**：
1. 找到最匹配的已有文档
2. 将新内容补充到文档的对应章节
3. 新增内容标注来源，保留可追溯性
4. 更新文档版本号

#### 分类三：修正（CORRECTION）

**判定条件**：新内容与已有文档主题一致，且**明确否定**或**更新**了已有结论

**处理**：
1. 更新文档内容
2. 保留旧版本（版本 diff 可查）
3. 在文档中标注"更新原因"
4. 如果修正影响其他文档（通过交叉引用），发出影响提醒

#### 分类四：冲突（CONFLICT）

**判定条件**：新内容与已有文档存在矛盾，但无法自动判定哪个正确

**处理**：
1. 创建冲突记录
2. 保留双方内容和来源
3. 推入审核队列
4. 在相关文档上标注"存在争议"

#### 分类五：重构（RESTRUCTURE）— v0.42 新增

**判定条件**：
- 某个架构节点下文档数 > 15（过载）
- 新内容横跨 3 个以上现有节点（跨域）
- 新内容揭示了一个之前未识别的分类维度

**处理**：
1. LLM 分析当前节点的内容分布
2. 提出节点拆分/合并建议
3. 生成"重构提案"交给用户审核
4. 用户确认后执行重组（移动文档、更新引用）

### 2.3 不适配时的结构演化策略

当新内容与当前架构不适配时，系统有三个层级的自适应：

**Level 1 — 局部生长**：在现有节点下新增子节点

```
当前架构:
  数据库/
    └── 关系型/

新内容: "Redis 集群配置指南"

结果:
  数据库/
    ├── 关系型/
    └── 缓存型/          ← 自动新增
        └── Redis集群配置指南
```

**Level 2 — 节点拆分**：当某个节点过载时

```
当前架构:
  前端开发/  (25篇文档，过载)

结果建议:
  前端开发/
    ├── 框架与工具/      ← 拆分
    ├── 样式与布局/      ← 拆分
    └── 性能优化/        ← 拆分
```

**Level 3 — 维度切换**：当大量新内容揭示了更好的组织方式

```
当前架构（按技术栈分类）:
  React/
  Vue/
  Node.js/

大量新内容: 都是关于"认证"的，分散在 React/Vue/Node 下

建议:
  ① 保持现有架构不变
  ② 新增"认证"跨域标签，通过交叉引用连接分散内容
  ③ 不建议全面重构（代价太大），而是通过索引层解决
```

## 三、多知识库路由：信息该进哪个知识库

### 3.1 问题本质

当用户有多个知识库项目（如"产品文档"、"技术文档"、"市场研究"），新资料进来时，如何判断它该放哪里？

### 3.2 方法论：三层路由策略

```
┌─────────────────────────────────────────────┐
│              多库路由决策树                    │
├─────────────────────────────────────────────┤
│                                             │
│  Layer 1: 显式路由                           │
│  用户在上传时指定了目标项目                    │
│  → 直接路由，不做判断                         │
│                                             │
│  Layer 2: 语义匹配路由                       │
│  用户未指定项目                              │
│  → 对新内容生成 embedding                    │
│  → 与每个项目的"项目画像"做相似度计算          │
│  → 相似度 > 0.7 → 自动路由到该项目           │
│  → 0.4-0.7 → 推荐 top-3，用户确认           │
│  → < 0.4 → 建议创建新项目                    │
│                                             │
│  Layer 3: 规则路由                           │
│  用户预设了路由规则                           │
│  → 关键词匹配（如"API"→技术文档）            │
│  → 文件类型匹配（如 .pdf → 产品文档）         │
│  → 来源匹配（如 Slack #dev → 技术文档）       │
│                                             │
└─────────────────────────────────────────────┘
```

### 3.3 项目画像

每个项目维护一个"画像"（Profile），用于路由匹配：

```json
{
  "project_id": "uuid",
  "name": "产品文档",
  "description": "产品需求、设计稿、用户研究报告",
  "keywords": ["产品", "需求", "设计", "用户研究", "PRD"],
  "embedding": [0.12, 0.34, ...],  // 项目描述 + 架构树节点名称的综合 embedding
  "routing_rules": [
    {"type": "keyword", "pattern": "PRD|需求文档|用户故事", "weight": 1.0},
    {"type": "file_ext", "pattern": ".fig|.sketch", "weight": 0.8}
  ]
}
```

**画像更新策略**：每次项目架构更新时，重新计算项目 embedding。

### 3.4 路由置信度与人工介入

| 置信度 | 行为 | 用户体验 |
|--------|------|---------|
| > 0.7 | 自动路由 | 通知用户"已自动归入[项目名]" |
| 0.4 - 0.7 | 推荐 top-3 | 弹窗让用户选择 |
| < 0.4 | 无法路由 | 建议创建新项目或手动指定 |

### 3.5 实现映射

| 步骤 | 代码位置 | 现状 | v0.42 改动 |
|------|---------|------|-----------|
| 显式路由 | routers/assets.py | 已有 project_id 参数 | 不变 |
| 语义匹配 | 新增 project_router_service.py | 不存在 | 新增 |
| 项目画像 | 新增 project 表字段 | 仅有 name/description | 新增 embedding + keywords |
| 规则路由 | 新增 routing_rules 表 | 不存在 | v0.43 考虑 |

## 四、跨知识库索引：当信息关联多个知识库

### 4.1 问题本质

一条信息可能同时与多个知识库有关。例如"API 认证方案"既属于"技术文档"也与"产品文档"中的"安全需求"相关。硬性选择一个放置位置会丢失关联性。

### 4.2 方法论：主归位 + 交叉引用

**核心原则**：每个文档有且仅有一个"主位置"（物理归属），但可以有多个"引用链接"（逻辑关联）。

```
┌──────────────────────────────────────────────┐
│              跨库索引模型                       │
│                                              │
│  文档 A（主位置：技术文档/认证模块）            │
│    │                                         │
│    ├── related_to ──→ 文档 B（产品文档/安全需求）│
│    ├── depends_on ──→ 文档 C（技术文档/密码学）  │
│    └── contradicts ─→ 文档 D（旧版文档/认证方案）│
│                                              │
└──────────────────────────────────────────────┘
```

### 4.3 关联类型

| 关联类型 | 含义 | 示例 |
|---------|------|------|
| `related` | 主题相关 | "React 性能优化" ↔ "Chrome DevTools 使用" |
| `depends_on` | 前置依赖 | "部署指南" → "Docker 安装教程" |
| `extends` | 扩展延伸 | "Python 基础" → "Python 高级技巧" |
| `contradicts` | 存在矛盾 | "方案 A" ↔ "方案 B" |
| `supersedes` | 替代 | "新版接口文档" → "旧版接口文档" |

### 4.4 自动发现策略

**策略一：Embedding 相似度**

```python
# 对每个新生成/更新的文档
# 计算与所有其他项目文档的 embedding 相似度
# 相似度 > 0.75 → 建议 related 关联
# 相似度 > 0.85 → 建议 extends 或 depends_on（根据内容分析）
```

**策略二：关键词重叠**

```python
# 两个文档的关键词交集 >= 3 → 建议 related
# 一个文档的关键词是另一个的超集 → 建议 extends
```

**策略三：引用链分析**

```python
# 文档 A 的来源素材也是文档 B 的来源 → 建议 related
# 文档 A 引用了文档 B 中定义的术语 → 建议 depends_on
```

### 4.5 用户体验设计

**在 Wiki 页面中的呈现**：

```
┌─────────────────────────────────────┐
│  # API 认证方案                      │
│                                     │
│  （正文内容...）                      │
│                                     │
│  ─────────────────────────────────  │
│  📎 关联知识                         │
│                                     │
│  同库:                               │
│  → 密码存储最佳实践  [扩展阅读]       │
│  → JWT Token 管理    [前置依赖]      │
│                                     │
│  跨库:                               │
│  → [产品文档] 安全需求规格  [相关]    │
│  → [旧版文档] OAuth 2.0 方案 [已替代]│
│                                     │
└─────────────────────────────────────┘
```

### 4.6 数据模型

```sql
CREATE TABLE cross_references (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id UUID NOT NULL REFERENCES tenants(id),
    source_doc_id UUID NOT NULL REFERENCES knowledge_docs(id),
    target_doc_id UUID NOT NULL REFERENCES knowledge_docs(id),
    relation_type VARCHAR(50) NOT NULL,
    -- 'related' | 'depends_on' | 'extends' | 'contradicts' | 'supersedes'
    confidence FLOAT DEFAULT 1.0,
    -- 1.0 = 用户确认, 0.x = 系统建议
    created_by VARCHAR(20) NOT NULL DEFAULT 'system',
    -- 'system' = 自动发现, 'user' = 人工创建
    note TEXT,
    -- 可选的关联说明
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE(source_doc_id, target_doc_id, relation_type)
);

CREATE INDEX idx_cross_refs_source ON cross_references(source_doc_id);
CREATE INDEX idx_cross_refs_target ON cross_references(target_doc_id);
CREATE INDEX idx_cross_refs_tenant ON cross_references(tenant_id);
```

## 六、附录：LLM Prompt 设计要点

### A. 反幻觉约束（所有 prompt 必须包含）

```
严禁编造不在原始资料中的信息。
每一个事实性陈述必须附带来源标注 [来源N]。
如果原始资料中信息不足以回答某个问题，明确标注"信息不足"。
如果原始资料中存在矛盾，保留双方并标注"存在争议"。
```

### B. MECE 架构 prompt 增强

```
请为以下知识内容设计架构树。要求：
1. 声明你选择的分类维度（按主题/按流程/按受众/混合）并解释原因
2. 确保节点满足 MECE 原则：
   - 互斥：任何一个知识 chunk 的主归位唯一
   - 穷举：所有 chunk 都能归入某个节点
3. 如果有无法归类的内容，列出并解释原因
4. 架构深度不超过 5 层，每层 3-7 个节点
5. 输出覆盖度评分（0-100%）
```
