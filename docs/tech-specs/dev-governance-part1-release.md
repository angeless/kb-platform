## 1.10 大版本（vX.Y.0）封板检查清单

> 当一个功能项版本（vX.Y）下的所有任务全部完成（`Completed`）后，在标记为 `Sealed` 之前，必须通过以下封板检查。任何一项 ❌ 均禁止封板。

### 1.10.1 注释代码审核与清理

**目的**：在开发过程中，铁律 #11 要求"不删除已有代码，仅注释掉"。大版本封板是统一清理这些注释代码的时机。

**执行步骤**：
1. 在整个代码库中搜索所有 `DEPRECATED vX.Y` 标记的注释代码：
   ```bash
   grep -rn "DEPRECATED v{{X}}.{{Y}}" --include="*.ts" --include="*.py" --include="*.go" --include="*.js" --include="*.tsx" --include="*.jsx"
   ```
2. 对每段注释代码逐一审核：
   - 确认该代码确实已被新实现替代且不再被任何地方调用
   - 确认删除不会影响现有功能
   - 确认没有其他模块通过反射、动态引用等方式依赖该代码
3. 审核通过的注释代码 → 删除
4. 审核存疑的注释代码 → 保留，标记为 `// REVIEW: 保留原因`，记入审计报告
5. 输出注释代码清理汇总：清理 N 处、保留 M 处（含原因）

### 1.10.2 安全加固审查

**目的**：确保版本发布前不存在已知安全隐患。

**检查清单**：

| 检查项 | 检查方式 | 通过标准 |
|--------|---------|---------|
| 依赖漏洞扫描 | `pip audit`（后端）/ `npm audit`（前端） | 无 high/critical 漏洞，或已记录豁免原因 |
| 硬编码机密检测 | `grep -rn "password\|secret\|api_key\|token" --include="*.ts" --include="*.py"` 等 | 无硬编码机密（环境变量 / 配置文件除外） |
| SQL 注入防护 | 检查所有数据库查询是否使用参数化（SQLAlchemy ORM） | 100% 参数化 |
| 权限检查覆盖 | 检查所有 API 端点是否有鉴权中间件 | 无裸露端点（公开端点需显式标注） |
| HTTPS / TLS | 检查外部通信是否加密 | 无明文 HTTP 调用（localhost 除外） |
| 输入校验 | 检查用户输入是否有校验（Pydantic schemas） | 关键端点均有输入校验 |
| 错误信息泄露 | 检查错误响应是否暴露内部信息 | 生产模式不返回 stack trace |

### 1.10.3 全功能端到端用例测试

**目的**：模拟真实用户操作，验证本版本所有功能在完整场景下正常工作。

**执行要求**：
1. 从开发计划中提取本版本所有任务的验收标准，汇总为端到端测试用例列表
2. 每个测试用例必须模拟完整的用户操作路径（不是单元测试级别，是业务场景级别）
3. 测试场景必须覆盖：
   - **正常路径**：每个功能的主要使用场景
   - **异常路径**：错误输入、网络异常、权限不足等
   - **边界条件**：空数据、极大数据、并发操作等
   - **新用户路径**：首次使用的完整流程
   - **升级用户路径**：从上一版本升级后的兼容性
4. 每个测试用例记录：测试步骤、预期结果、实际结果、通过/失败
5. 所有测试用例必须全部通过。存在失败 → 禁止封板

### 1.10.4 封板技术审计报告

**目的**：生成一份完整的版本级技术审计报告，作为封板的最终依据。

**报告路径**：`docs/versions/seal-audit-vX.Y.md`

**报告必须包含以下章节**：

```markdown
# 大版本封板审计报告 — vX.Y

## 1. 版本概览
- 版本号：vX.Y.0
- 包含任务：vX.Y.1 ~ vX.Y.N
- 审计日期：{{日期}}

## 2. 注释代码清理结果
- 清理数量：{{N}} 处
- 保留数量：{{M}} 处（含原因）
- 状态：✅ / ❌

## 3. 安全加固审查结果
（逐项列出 1.10.2 检查清单的结果）
- 状态：✅ / ❌

## 4. 全功能端到端测试结果
- 测试用例总数：{{N}}
- 通过：{{N}} / 失败：{{N}} / 跳过：{{N}}
- 失败用例详情：（如有）
- 状态：✅ / ❌

## 5. 版本号一致性检查
（按 §1.1 逐项检查所有位置的版本号）
- 状态：✅ / ❌

## 6. 回归测试结果
- 全量测试通过率：{{N}}%
- 新增失败：{{N}} 个
- 状态：✅ / ❌

## 7. 封板结论
- [ ] 注释代码清理：✅
- [ ] 安全加固审查：✅
- [ ] 全功能端到端测试：✅
- [ ] 版本号一致性：✅
- [ ] 回归测试：✅

**结论：** ✅ 允许封板 / ❌ 禁止封板（原因：...）
```

**封板规则**：
- 第 7 节所有检查项必须为 ✅ 才能封板
- 任何一项 ❌ → 禁止封板，必须修复后重新执行封板检查
- 审计报告生成后即封板（加入 §1.7 Tier 2 保护），不允许事后修改
- 封板成功后执行：`git tag vX.Y.0` + 更新 RELEASE_NOTES + 标记开发计划中所有任务为 `Sealed`

## 1.11 UI 规范增量更新流程

> 当新功能涉及的 UI 组件/模式不在现有 UI 规范覆盖范围内时，按以下流程进行增量更新。

**前提**：项目已有 UI 设计规范文件（如 `docs/ui-design-spec.html`）。如果项目尚未有 UI 规范，在初始化时通过 `web-artifacts-builder-pro-*` skill 创建首版（名称中尾部版本号可能变化，按实际可用版本匹配，如 `web-artifacts-builder-pro-v1-1-0`）。

**增量更新触发条件**：
- 当前任务需要新增 UI 组件（现有规范中未定义的组件类型）
- 当前任务需要新增交互模式（现有规范中未覆盖的交互方式）
- 当前任务需要扩展 Design Token（新的颜色语义、间距等级等）

**增量更新步骤**：

| 阶段 | 操作 | 说明 |
|------|------|------|
| Phase 1 | 在实施计划中标注"需新增 UI 组件/模式"，列出需要新增的具体组件或 Token | 明确增量范围 |
| Phase 2 编码前 | 调用 `web-artifacts-builder-pro-*` skill 产出增量 UI 组件，追加到现有 UI 规范文件 | **追加新章节，不重写已有内容** |
| Phase 2 编码中 | 新增代码严格遵循增量 UI 规范中定义的 Token 和组件样式 | 禁止自行发明颜色值、间距值 |
| Phase 4 审计 | Part B 技术规范合规审计中检查新增代码是否遵循了增量 UI 规范 | 新组件必须使用规范定义的 Token |

**增量内容要求**：
- 新增组件必须遵循现有 Token 体系（不创建新的颜色/字体/间距系统）
- 如确需扩展 Token，必须在 Token 定义区追加，不修改已有 Token 值
- 新增组件必须同时提供浅色+深色主题的样式
- 新增组件必须有可渲染的交互式示例
