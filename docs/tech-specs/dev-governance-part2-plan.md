# 第二部分：开发计划管理

> 本部分定义开发计划的结构规范和追踪规则。
> **重要：开发计划由产品负责人（Product Owner）编写并放置在 `docs/dev-plans/` 路径下。AI 开发 Agent 不负责创建开发计划，只负责从中领取任务并产出实施计划。**

## 2.1 开发计划文档命名和位置

**位置：** `docs/dev-plans/`

**命名规则：** `dev-plan-vX.Y.md`（精确到前两位，即功能/优化项级别）

**示例：**
- `docs/dev-plans/dev-plan-v0.39.md`（KB Platform v0.39 版本的开发计划）
- `docs/dev-plans/dev-plan-v0.40.md`（KB Platform v0.40 版本的开发计划）

**相关文档命名：**
- 版本 PRD：`docs/prd/prd-vX.md`（精确到第一位）
- 任务实施计划：`docs/dev-plans/impl-plan-vX.Y.Z.md`（精确到三位）
- 任务完成汇报：`docs/versions/task-report-vX.Y.Z.md`
- 代码审计报告：`docs/versions/audit-report-vX.Y.Z.md`
- 用户测试报告：`docs/versions/test-report-vX.Y.Z.md`
- 空闲循环测试报告：`docs/versions/idle-test-report-vX.Y.Z-{a}.md`（版本号 + 循环序号）
- Bug 修复清单：`docs/dev-plans/bugfix-list-vX.Y.Z-{a}.md`（版本号 + 清单序号）
- 阶段报告：`docs/versions/phase-report-vX.Y.md`
- 版本发布说明：`docs/versions/RELEASE_NOTES_vX.md`
- 大版本封板审计报告：`docs/versions/seal-audit-vX.Y.md`（精确到前两位）

## 2.2 开发计划文档结构（参考规范）

> 以下为开发计划的推荐结构。AI 开发 Agent 在 Phase 1 读取开发计划时，应期望文档包含以下章节。如果产品负责人提供的计划缺少必要章节，应在 Phase 1 ③ 门禁中标记并向用户反馈，而非自行补全。

每个开发计划应包含以下章节：

### 1. 版本目标

```markdown
## 1. 版本目标

目标版本：v{{x.y.z}}
预计时间：{{时间段}}
主要目标：
- {{目标1}}
- {{目标2}}
- {{目标3}}
```

### 2. 版本范围

```markdown
## 2. 版本范围

### 包含的需求
- {{需求1}}：{{简要描述}}
- {{需求2}}：{{简要描述}}

### 不包含的需求（Future）
- {{未来需求1}}
- {{未来需求2}}
```

### 3. 任务列表

```markdown
## 3. 任务列表

| 任务版本号 | 任务名称 | 优先级 | 规划周期 | 状态 |
|----------|--------|------|--------|------|
| v0.39.1 | {{任务1}} | P0 | {{时间}} | Planned |
| v0.39.2 | {{任务2}} | P0 | {{时间}} | Planned |
| v0.39.3 | {{任务3}} | P1 | {{时间}} | Planned |
```

### 4. 各任务详细定义

```markdown
## 4. 各任务详细定义

### v0.39.1: {{任务名称}}

**目标：** {{明确的目标}}

**输入：**
- {{输入1}}
- {{输入2}}

**输出：**
- {{输出1}}
- {{输出2}}

**验收标准（Checklist）：**
- [ ] {{标准1}}
- [ ] {{标准2}}
- [ ] {{标准3}}

**依赖项：**
- {{前置任务或条件}}

**预计工作量：** {{时间}}
**规划开始日期：** {{日期}}
**规划完成日期：** {{日期}}
```

重复此结构用于 v0.39.2、v0.39.3 等任务。

### 5. 完成状态追踪

**任务状态定义（单向流转，禁止逆向）**：

| 状态 | 标记 | 含义 | 触发条件 |
|---|---|---|---|
| 待开发 | `Planned` | 已定义但未开始 | 计划创建时 |
| 开发中 | `In Progress` | 已领取，正在执行 | Phase 1（理解与计划）开始时 |
| 已完成 | `Completed` | 全部门禁通过，已 commit | Phase 6 收尾完成 + TODO_NEXT 更新 |
| 已封板 | `Sealed` | 所属 Phase 全部任务完成 + 回归测试通过 + VERSION 更新 + git tag | Phase 结束时整体标记 |
| 已发布 | `Released` | 版本发布完成 | RELEASE_NOTES 产出 + 最终 git tag |

**状态流转规则**：`Planned → In Progress → Completed → Sealed → Released`，禁止逆向。

**强制回写规则**：
1. 每完成一个任务，必须**立即**回到本文件更新该任务状态和实际完成日期
2. 每完成一个 Phase，必须在本文件标记该 Phase 为 `Sealed` 并记录封板日期
3. 封板后的 Phase 禁止追加新任务——新需求只能写入 WISHLIST.md 或排入下一版本
4. 自动连续判定在判定"是否继续"前，必须先确认上一个任务状态已回写

```markdown
## 5. 完成状态追踪

| 任务版本号 | 任务名称 | 计划周期 | 实际完成日期 | 迭代次数 | 状态 |
|----------|--------|--------|----------|--------|------|
| v0.39.1 | {{任务1}} | {{时间}} | {{完成日期}} | {{次数}} | Completed |
| v0.39.2 | {{任务2}} | {{时间}} | — | 0 | Planned |
| v0.39.3 | {{任务3}} | {{时间}} | — | 0 | Planned |

**Phase 封板记录：**
| 功能项 | 包含任务 | 封板日期 | 封板版本号 | 回归测试结果 |
|-------|--------|--------|----------|-----------|
| v0.39.0 {{功能项名}} | v0.39.1–v0.39.N | {{日期}} | v0.39.N | {{通过/未通过}} |
```

### 6. 变更记录

```markdown
## 6. 变更记录

| 日期 | 变更内容 | 责任人 |
|-----|--------|------|
| {{日期}} | {{变更1}} | {{名字}} |
| {{日期}} | {{变更2}} | {{名字}} |
```

### 7. 决策和假设

```markdown
## 7. 决策和假设

**关键决策：**
- {{决策1 及原因}}
- {{决策2 及原因}}

- {{假设1}}
- {{假设2}}
```

```markdown
| 风险 | 概率 | 影响 | 缓解措施 |
|-----|-----|------|--------|
| {{风险1}} | {{高/中/低}} | {{高/中/低}} | {{缓解策略}} |
| {{风险2}} | {{高/中/低}} | {{高/中/低}} | {{缓解策略}} |
```

## 2.4 计划变更记录

> 开发计划的变更由产品负责人发起。AI 开发 Agent 在执行过程中如果发现计划需要调整（如发现技术不可行、依赖缺失等），应在 Phase 7 衍生建议中提出，而非直接修改计划。

当开发计划需要调整时（范围变更、时间变更、优先级变更等），必须：

1. 在计划文档中的"变更记录"章节添加新条目
2. 记录变更日期、变更内容、变更原因、责任人
3. 如果涉及 `vX.Y.Z` 任务的增删改，更新"任务列表"表格
4. git commit 并记录日志

## 2.5 版本开发任务计划写作规范

> 本节定义版本开发任务计划的写作标准和质量要求。虽然 AI 开发 Agent 不负责创建开发计划，但产品负责人编写的计划必须满足以下规范，以确保 Agent 能准确理解和执行。Agent 在 Phase 1 ③ 门禁中应对照本节检查计划质量，如不符合则向用户反馈。

### 2.5.1 写作前必须做的事

1. **读代码，不要猜** — 用 `git show` / `git ls-tree` 等方式读取目标 commit 的实际代码，确认现有模块、表结构、API、前端页面的真实状态
2. **读项目技术规范文档** — 特别是版本号规范、测试规范、文档产出规范、任务闭环规范、命名规范等章节，确保输出的计划不与已有规范冲突
3. **读 PRD** — 确认目标功能在 PRD 中的定义（`docs/prd/`），不自行发明需求
4. **做 Gap 分析** — 列出"需求需要什么" vs "现在已经有什么"，只针对 Gap 制定任务

### 2.5.2 文档必需章节

每份版本开发任务计划必须包含以下章节（与 §2.2 的推荐结构互补，本节强调内容深度要求）：

| 章节序号 | 章节名称 | 核心要求 |
|---------|---------|---------|
| 1 | 开发管理（总原则） | 不推倒重写；继承已有能力（列出具体的已有 service / middleware / module / infra，如 `services/api/`、`services/ingestion-worker/`、`services/pipeline-worker/`、`services/ai-orchestrator/`、`packages/shared-config/`、`packages/shared-models/`、`packages/shared-schemas/`、`packages/shared-errors/`、`apps/web/`）；最小改动；每次只能领取一个任务 |
| 2 | 当前阶段事实 | 项目目标（一句话）；当前基线 commit / 分支；当前已完成能力的完整清单（按层分类）；当前未完成的任务列表 |
| 3 | 本轮目标与边界 | 只做什么（任务列表）；明确不做什么（必须写，防止范围蔓延） |
| 4 | 优先级与顺序 | 严格排序，给出执行顺序的理由；标注依赖关系 |
| 5 | 各任务详细定义 | 见下方 §2.5.3 任务详细定义规范 |
| 6 | 实现约束 | 目录结构规范；migration 命名规范（Alembic，路径 `infra/sql/alembic/`）；审计 / 权限 / 加密要求；人工入口 + API 双入口要求 |
| 7 | 任务领取规则 | 每次只能领取一个任务；完成后汇报，确认再领下一个；不混做不同阶段；衍生任务仅记录不执行 |
| 8 | 测试要求 | 引用项目技术规范的对应章节（`testing-strategy.md`）；测试层次；覆盖重点；后端使用 pytest，前端使用 vitest |
| 9 | 版本号管理 | 引用项目技术规范的对应章节（`dev-governance.md` §1.1–§1.4）；版本号格式；每个批次对应的版本号 |
| 10 | 文档产出要求 | 引用项目技术规范的对应章节；每个任务完成后必须同步更新的文档列表；版本全部完成后必须产出的文档列表 |
| 11 | 汇报格式 | 引用项目技术规范的对应章节（`dev-governance.md` §0.7）；固定结构 |
| 12 | 新增数据库表汇总 | 每个任务新增了哪些表（PostgreSQL），合计多少张 |
| 13 | 开始前必须先输出 | 当前代码现状理解；第一个任务的实施计划；第一个任务的预计修改文件清单。**在这三项输出之前，不要开始写代码** |

### 2.5.3 任务详细定义规范（核心）

每个任务（§2.3 中定义的 `vX.Y.Z`）必须包含以下要素：

| 要素 | 精度要求 | 反面示例（禁止） |
|------|---------|----------------|
| 目标 | 一句话说清这个任务解决什么问题 | "完善功能" |
| 改动范围 | 新建什么模块 / 改动哪些已有文件（在 `services/`、`packages/`、`apps/web/` 下） | "改相关文件" |
| 新增数据库表 | 表名 + 每个字段（字段名、类型、约束、说明），使用 PostgreSQL 类型 | 只写表名不写字段 |
| 已有表变更 | 新增字段列表（字段名、类型、默认值、说明） | "加几个字段" |
| API 定义 | 端点路径、HTTP 方法、权限要求、入参字段、说明（FastAPI 路由） | 只写 "CRUD" |
| 业务规则 | 分步骤的逻辑：第 1 步校验什么 → 第 2 步做什么 → 第 3 步返回什么 → 错误码是什么 | "按正常流程处理" / "做异常处理" |
| 前端变更 | 新增页面 / 改动页面 / 导航变更（在 `apps/web/` 下，使用 Next.js 15 + React 19） | "更新界面" |
| 不做什么 | 本任务的边界约束 | 不写边界 |
| 验收标准 | 逐条可核对的 checklist（输入什么 → 期望什么） | "功能正常" |

### 2.5.4 写作原则

1. **以现有代码为准，不以文档为准** — 如果文档说有某个能力但代码里没有，以代码为准
2. **不写代码实现** — 定义做什么、输入输出是什么、规则是什么，但不写具体的函数体。开发自己决定怎么实现
3. **不自行扩张需求** — PRD 里没有的不加。如有建议的衍生功能，单独列在"建议但不在本版本范围内"段落
4. **不与已有代码冲突** — 新增模块独立目录（`services/{服务名}/` 或 `packages/{包名}/`），不改无关模块。如果必须改已有文件，明确写出改哪个文件的哪个方法，为什么
5. **每个任务必须是最小可实现的闭环** — 做完这一个任务后系统可运行、可测试、可验收，不依赖后面的任务才能跑通
6. **引用项目已有规范，不另起炉灶** — 版本号、命名、测试、文档产出等规则引用项目技术规范的章节号，不重新定义

### 2.5.5 常见错误（写作时必须避免）

| 错误 | 正确做法 |
|------|---------|
| 没读代码就写计划，导致计划与实际代码严重不符 | 先 `git show` / `git ls-tree` 读关键文件 |
| 给出"大致方向"而不是精确定义 | 每张表、每个 API、每条规则都写清楚 |
| 写了 "CRUD" 但没写每个端点的具体路径和权限 | 列出完整的 API 表格 |
| 写了"按常规逻辑处理"或"做异常处理" | 写出具体的错误码和处理方式 |
| 验收标准写"功能正常" | 写成可执行的测试场景（输入 → 期望） |
| 任务粒度太大（一个任务包含 3 个新模块） | 一个任务 = 一个模块或一个独立能力 |
| 任务粒度太小（每个 API 端点是一个任务） | 一个模块的完整 CRUD 可以是一个任务 |
| 写了具体的实现代码 | 只写接口定义和规则，不写函数体 |
| 给已有模块加了不需要的改动 | 只改与当前任务直接相关的文件 |
| 发明了 PRD 里没有的需求 | 严格基于 PRD（`docs/prd/`）和用户提出的需求 |

### 2.5.6 Agent Phase 1 门禁中的计划质量检查

Agent 在 Phase 1 ③ 门禁中读取开发计划时，应对照以下清单快速评估计划质量。如有不达标项，向用户反馈但**不自行修补计划**：

| 检查项 | 判定标准 | 不达标时处理 |
|--------|---------|------------|
| 任务有 API 定义但只写了 "CRUD" | 缺少端点、方法、权限、入参 | 反馈给用户，请求补全 |
| 任务有数据库表但只写了表名 | 缺少字段级定义 | 反馈给用户，请求补全 |
| 验收标准不可执行 | "功能正常"、"效果良好"等模糊表述 | 反馈给用户，请求改为可测试的场景 |
| 业务规则含模糊指令 | "按正常流程"、"做异常处理" | 反馈给用户，请求明确逻辑步骤 |
| 任务间有隐式依赖但未标注 | 后序任务使用了前序任务的产出但依赖关系栏空白 | 反馈给用户，请求补充依赖关系 |
| 缺少"不做什么"边界 | 任务范围无上界约束 | 反馈给用户，请求明确边界 |
