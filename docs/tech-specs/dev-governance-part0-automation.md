# 第零部分：Claude Code 自动化开发指令

> 本部分定义 Claude Code 作为自动化开发执行者时的行为规范。当 Claude Code 接收到开发任务时，必须先阅读本文件全文，然后严格按照以下规则执行。

## 0.1 执行身份与约束

你是 KB Platform 项目的执行开发者。你的工作模式是**严格按照版本开发计划逐任务执行**。

核心约束：
1. **严格遵守本文件的所有技术规范**：分层架构、命名规范、测试要求、文档产出要求。
2. **严格按照版本开发计划执行**：计划文件位于 `docs/dev-plans/` 目录下（如 `docs/dev-plans/dev-plan-v0.39.md`），以及 `docs/plans/` 目录下的版本开发任务计划。不能发明计划中不存在的任务，不能跳过、合并、修改任务定义。
3. **每次只做一个任务**：按计划中的优先级顺序，完成该任务的全部开发、测试、验收后，输出完整汇报，再领取下一个。
4. **不允许范围蔓延**：只修改当前任务定义中明确列出的文件和模块。
5. **保护已有业务逻辑**：不重构、不重命名、不删除、不迁移任何与当前任务无关的代码。

## 0.2 每个任务的统一执行流程（七阶段治理）

> **核心原则**：每个阶段都遵循统一的三段式结构——**① 规范输入（读什么）→ ② 执行（做什么）→ ③ 阶段门禁（检查什么）**。
> 只有当前阶段的门禁通过后，才能进入下一阶段。任何阶段门禁失败，必须先修复再继续。
>
> **重要**：本节定义的七阶段流程是每个 `vX.Y.Z` 任务的**唯一执行流程**。第三部分提供本流程引用的详细操作指南和文档模板，不是独立的流程。

### 流程总览

```
Phase 1 → Phase 2 → Phase 3 → Phase 4 → Phase 4.5 → Phase 5 → Phase 6 → Phase 7 → 自动连续判定
```

| 阶段 | 名称 | 目标 | 核心产出 | 门禁类型 |
|------|------|------|---------|---------|
| Phase 1 | 理解与计划 | 深入理解任务，制定实施方案 | 实施计划文档 | 计划质量门禁 |
| Phase 2 | 编码实现 | 按计划增量编写代码 | 源代码 + 测试代码 | 编码质量门禁 |
| Phase 3 | 测试 | 全面测试，确保质量 | 测试执行结果 | **Part A：自动化门禁** |
| Phase 4 | 审计 | 对照规范全面审查 | 审计报告 | **Part B/C/D 门禁** |
| Phase 4.5 | 子 Agent 独立验收 | 消除自审偏误 | 独立验收报告 | 子 Agent 验收门禁 |
| Phase 5 | 测试报告 | 汇总测试结果 | 测试报告文档 | 报告完整性门禁 |
| Phase 6 | 收尾 | 更新文档，输出汇报 | 任务汇报 + CHANGELOG + VERSION | 收尾完整性门禁 |
| Phase 7 | 衍生建议 | 记录改进机会 | WISHLIST 更新 | 衍生建议门禁 |
| — | 自动连续判定 | 决定是否领取下一个任务 | 继续/停止决定 | 连续判定门禁 |

### Phase 1：理解与计划（开始写代码之前）

#### ① 规范输入

开始本阶段前，必须阅读以下内容：

0. **检测可用上下文容量并选择加载策略**

   在加载任何规范文件之前，先判定自身可用上下文窗口大小，按 `dev-governance.md` 中"上下文受限时的最小必读集"章节选择加载策略：
   - ≥ 128K tokens → **完整模式**：按下方步骤 1-5 正常加载全文
   - 64K–128K tokens → **精简模式**：加载所有治理文件的 TL;DR 块 + 当前 Phase 对应文件的全文
   - 32K–64K tokens → **最小模式**：仅加载 index 导航表 + 必读 TL;DR 块 + 当前 Phase 对应的 §0.2 子节和 §3.x 模板节
   - < 32K tokens → **超受限模式**：仅加载 part0 TL;DR + Phase 1 的 §0.2 子节 + §3.1 模板

   > 如无法确定自身上下文大小，默认走精简模式。加载过程中遇到截断则立即降级。

1. **读取技术规范**
   - 阅读 `docs/tech-specs/architecture.md` 了解系统整体设计
   - 阅读 `docs/tech-specs/coding-standards.md` 了解代码规范
   - 阅读 `docs/tech-specs/dev-governance.md` 理解开发流程

2. **读取当前状态**
   - 读取 `VERSION` 文件，获知当前版本号
   - 阅读 `CHANGELOG.md`，了解最近 3-5 个版本的变更历史
   - 运行 `git log --oneline -20` 查看最近 20 条 commit，理解最近的改动趋势

3. **读取开发计划**
   - 定位当前版本对应的计划文件：`docs/dev-plans/dev-plan-v0.39.md`
   - 找出当前要处理的任务（状态 = Planned 的第一个 `vX.Y.Z`）
   - 完整阅读该任务的定义（目标、改动范围、API 定义、业务规则、验收标准等全部字段）
   - 阅读 **§2.5**（版本任务计划写作规范）作为任务定义质量参照——后续 Phase 1 ③ 门禁将据此检查任务定义质量

4. **读取约束文件**
   - **§1.7**：禁止修改的文件清单
   - **§1.9**：并行开发协议（如有多 Agent 并行场景）
   - **§2.3**：执行流程与闭环规范（理解实施计划应包含的要素）
   - **§2.4**：目录结构（确认新文件应放置的位置）
   - （如涉及前端）**UI 设计规范**：`docs/tech-specs/coding-standards-frontend.md`

5. **确认分支与工作目录（⛔ 硬性门槛——不通过则立即停止开发）**

   在做任何其他操作之前，必须先执行以下检查并**输出结果**：

   ```bash
   git branch --show-current   # 当前分支名
   pwd                         # 当前工作目录
   cat VERSION                 # 当前版本号
   git worktree list           # 列出所有 worktree（如适用）
   ```

   **逐项确认：**
   - **当前分支**是否为自己的 `test-v-{X}-{Y}-{a}` 开发测试分支？（`a` = 当前开发者/Agent 标识）
   - **当前工作目录**是否在正确的项目根目录或 worktree 路径下？
   - **Worktree 确认**（如项目使用 worktree 隔离）：`git worktree list` 输出中，当前目录是否匹配预期的 worktree 路径？是否存在其他 worktree 可能干扰？
   - **版本号**是否与当前任务所属的版本一致？

   **必须在输出中明确展示：**
   ```
   🔍 分支/目录/Worktree 确认：
   - 当前分支: test-v-{X}-{Y}-{a}  ✅/❌
   - 当前目录: /path/to/project     ✅/❌
   - Worktree: {主仓库 / worktree路径}  ✅/❌（如适用）
   - 当前版本: X.Y.Z                ✅/❌
   - 允许修改路径: 当前任务涉及的文件范围
   ```

   **判定规则：**
   - 任何一项为 ❌ → **立即停止开发**，不执行后续任何步骤，向用户报告当前状态并说明如何切换到正确的分支/目录
   - 全部 ✅ → 继续执行后续前置条件检查

6. **检查前置条件**
   - 检查上一个 `vX.Y.Z` 任务是否已完成（查看计划文件中的状态）
   - 如果当前任务有"依赖项"，逐一验证依赖项是否已完成
   - 验证 git 本地状态：`git status` 应该是 clean（无未提交改动）

#### ② 执行

在动手写任何代码之前，你必须先输出以下内容：

**A. 当前代码现状理解**
- 读取当前任务涉及的所有已有文件，列出文件路径和当前职责
- 确认这些文件的现有接口、数据结构、依赖关系
- 如果任务涉及数据库，读取相关 migration 文件确认当前表结构
- 核对禁止修改文件清单，确保本任务不会触碰

**B. 本任务实施计划**
- 任务编号和目标（从开发计划中原文引用）
- 计划新建的文件列表（含路径）
- 计划修改的已有文件列表（含路径和具体改动点）
- 实施顺序（先做什么后做什么）
- 测试策略（单元测试、集成测试、手工验证各覆盖什么）
- 预期风险点

**C. 预计修改文件清单**
- 逐文件列出：文件路径 | 新建/修改/功能性删除/重构性删除 | 变更内容一句话说明
- 如标注"重构性删除"，须补充：`→ {新位置说明}`（与 §0.5 规则 11 及 impl-plan §5.1 对应）

**D. 创建实施计划文档**
- 新建文件：`docs/dev-plans/impl-plan-v{X.Y.Z}.md`
- 文档模板见第三部分 §3.1

#### ③ 阶段门禁（计划质量检查）

输出 A/B/C/D 后，在进入编码之前，必须自检以下条目：

| 检查项 | 通过条件 |
|--------|---------|
| ⛔ 分支确认（§1.5.4） | 当前分支是否为自己的 `test-v-{X}-{Y}-{a}` 开发测试分支？不是 → ❌ **立即停止开发**，不继续后续检查 |
| ⛔ 工作目录确认 | 当前工作目录是否在正确的项目根目录或 worktree 路径下？不是 → ❌ **立即停止开发** |
| 任务定义完整性 | 是否已完整阅读了开发计划中的任务目标、改动范围、API 定义、业务规则、验收标准？ |
| ⛔ 任务定义质量（§2.5） | 当前任务是否包含**明确的改动范围**（涉及文件或模块列表）和**至少 3 条可验证的验收标准**？缺失任一 → ❌ **停止**，提示用户补充开发计划中该任务的定义后再继续。任务定义质量不足会导致后续所有门禁（尤其 Phase 4 Part C 验收核对）失去校验基础 |
| 禁止文件核对（§1.7） | 将预计修改文件清单逐一与 §1.7 三个 Tier 比对：Tier 1 文件出现 → ❌ 立即停止；Tier 2 文件已封板 → ❌ 立即停止；Tier 3 文件未在任务定义中授权 → ❌ 立即停止。无命中或命中 Tier 3 已授权 → ✅ |
| 目录结构合规 | 计划新建的文件路径是否符合目录结构规范？ |
| 范围约束 | 实施计划是否只包含当前任务定义范围内的改动？ |
| 依赖确认 | 任务所依赖的前置任务是否已完成？涉及的已有接口是否存在且可用？ |
| 验收标准结构化 | 验收标准是否已从开发计划复制并转为逐条 Checklist 格式（impl-plan §2）？ |
| 代码现状理解 | 是否已记录涉及文件的当前职责、接口、依赖关系（impl-plan §3）？ |
| 实施计划文档 | 实施计划文档是否已创建并包含完整的架构设计、文件清单、禁止文件核对、实施步骤、测试策略、风险预判、文件锁声明（如适用）？ |

每项标注：✅ 通过 / ❌ 不通过

- 全部 ✅ → **自动进入 Phase 2**（门禁通过即继续，不等待用户确认）
- 存在 ❌ → 修正对应问题后重新自检，直到全部通过

#### ② 执行

**开始前检查：**

```bash
git status              # 确保 clean
git branch              # 确认在正确分支
cat VERSION             # 确认当前版本号
```

**编码规则（根据项目实际情况裁剪此列表）：**

1. **分步实现**：每步完成一个最小语义单元（一个函数/一个端点/一个组件）。每步完成后自检是否引入了编译错误或测试失败。
2. **分层边界**：遵守项目的分层架构约束。
3. **目录结构**：新文件必须放在正确的目录下。
4. **命名规范**：数据库表名、API 路径、模块名等遵守命名规则。
5. **数据库规范**（如涉及）：Migration 序号、命名格式、幂等保护。使用 Alembic (infra/sql/alembic/) 管理迁移。
6. **接口规范**（如涉及）：统一前缀、鉴权、返回结构、幂等要求。
7. **权限规范**（如涉及）：权限检查到位。
8. **安全规范**（如涉及）：机密策略、执行安全、鉴权安全。
9. **前端技术规范**（如涉及前端）：技术栈（Next.js 15 + React 19 + TypeScript）、路由、API 访问层。
10. **UI 设计规范**（如涉及前端）：严格遵守 Design Tokens、组件模式、暗色主题适配、动画规范。禁止自行发明颜色值、间距值、组件样式——必须使用 UI 规范中定义的 CSS 变量。
11. **测试同步编写**：每个新功能必须附带对应测试。
12. **不做多余的事**：不优化无关代码，不重构已有结构，不添加计划中没有的功能。

**增量开发操作要点：**

- 每个 Step 先阅读已有代码 → 添加新代码 → 验证语法 → 运行相关测试
- 不允许积累超过 4-5 个 Step 的改动后再 commit
- 严禁想象或猜测某个库、函数、接口的存在——必须通过代码扫描确认
- 详细操作指南见第三部分 §3.2

#### ③ 阶段门禁（编码质量检查）

| 检查项 | 通过条件 |
|--------|---------|
| 语法正确 | 所有新增/修改文件是否通过语法检查？ |
| 测试同步 | 每个新功能是否附带对应测试？ |
| 增量提交 | 是否按规范进行了增量 commit？ |
| 无范围蔓延 | 实际修改的文件是否都在实施计划范围内？ |
| 无幻觉代码 | 是否所有引用的库、函数、接口都经过代码扫描确认存在？ |
| 常见错误自查 | 是否已按 `docs/experience/common-errors.md` 逐条扫描本次变更？（文件不存在时跳过，详见 §3.8） |

每项标注：✅ 通过 / ❌ 不通过

- 全部 ✅ → **自动进入 Phase 3**（门禁通过即继续，不等待用户确认）
- 存在 ❌ → 修正后重新自检

### Phase 3：测试

#### ① 规范输入

阅读以下内容：
- Phase 1 输出的**实施计划**中的测试策略（impl-plan §8）
- 当前任务在开发计划中的**验收标准**
- **`coding-standards-testing.md`**：编码级测试规则（AAA 模式、覆盖率、禁止事项）
- **`testing-strategy.md`**（**完整阅读**）：测试策略与规范（测试类型分类、频次与触发时机、各类型通用流程、用例规范、路径管理、报告命名、数据管理）。Phase 2 仅需阅读 §5（测试目录结构），本阶段是完整阅读的时机。

#### ② 执行

**全面测试**（详细操作指南见第三部分 §3.3）：

1. **单元测试**：遵循 AAA 模式（Arrange-Act-Assert），覆盖正常路径和异常路径
2. **集成测试**：覆盖多模块协作的真实流程，如有 API 则验证端点

**Part B：技术规范合规审计**（逐项对照 Phase 2 ① 中阅读的章节）

> **对抗性审计原则**：Part B 审计时，AI 必须从"我要找到至少 1 个违规点"的视角出发，而非"确认一切正常"。

>
> **自审可信度标注（硬性规则）**：如果 Phase 2（编码实现）和 Phase 4（审计）在同一个 AI session 中完成，Part B 审计结论必须标注为**"自审"**而非"对抗性审计"。原因：同一 session 的 AI 对自己刚写的代码存在确认偏误，无法实现真正的对抗性审计。此标注必须体现在 Phase 6 ② 任务汇报的第 6 项"规范审计结果"中，格式为：`审计模式: 自审（同 session）`。高风险任务（涉及安全、支付、数据迁移等）建议由不同 session 的 Agent 执行 Phase 4 审计（详见 §5.5）。
>
> **可选外部校验点**：Part B 审计完成后，如果任务属于高风险类别（在开发计划中标注为 `risk: high`），AI 应暂停并输出：`⏸️ Part B 审计已完成（自审模式）。本任务为高风险任务，建议由用户或另一个 Agent 复核审计结论后再继续。输入"继续"跳过外部复核，输入"等待复核"暂停。` 如果用户选择跳过，在任务汇报中标注 `外部复核: 已跳过`。

**git commit 失败的应急处理**：

如果 `git commit` 执行失败（如 pre-commit hook 拒绝、磁盘空间不足、index.lock 冲突等），按以下步骤处理：

```bash
# 1. 先用 git stash 保存当前所有修改（包括 staged 和 unstaged）
git stash push -m "emergency-stash: Phase6-commit-failure-$(date +%Y%m%d%H%M%S)"

# 2. 记录 stash 的 ref，确保可追溯
git stash list | head -1   # 输出 stash@{0} 的完整信息

# 3. 诊断 commit 失败原因
git status                  # 检查工作区状态
git diff --cached --stat    # 检查暂存区内容
# 如果是 hook 失败：查看 hook 输出，修复对应问题
# 如果是 lock 文件：rm -f .git/index.lock（确认无其他 git 操作在运行后）

# 4. 修复问题后，恢复 stash 中的修改
git stash pop               # 恢复修改到工作区

# 5. 重新执行 git commit
git add -A
git commit -m "feat(vX.Y.Z): ..."
```

**注意**：如果 `git stash pop` 产生冲突，必须手动解决冲突后再 commit。stash 条目在 pop 成功前不会被删除，可用 `git stash list` 确认。

> **关键原则：分支上的所有操作（commit、push）无需等待用户确认。只有合并到 main 分支时才需要用户评审。**

**如果自动继续条件全部满足**：
→ 确认 Phase 6 门禁中的 commit、文档归档、TODO 更新已全部完成
→ 立即领取下一个任务，回到 Phase 1
→ **不需要等待用户确认，不需要询问"是否继续"，直接执行**

**功能项边界处理**（当前任务是某功能项的最后一个任务时）：
→ 执行全量回归测试
→ 更新 VERSION 文件
→ 输出阶段完成报告
→ git commit + git push origin 当前分支
→ **自动进入下一功能项，不等待确认，不询问用户**

**版本边界处理——大版本（vX.Y.0）封板流程**（当前版本所有任务完成时）：
→ **先执行 §0.11 无任务空闲循环**（PRD Gap 扫描 → 全量测试 → 问题分类 → Bug 修复），直到循环终止（Bug 修复清单为空或达到上限）
→ 空闲循环完成后，执行大版本封板检查清单（详见 §1.10），包括：
  → 注释代码审核与清理（清理所有 `// DEPRECATED vX.Y.Z:` 标记的注释代码）
  → 安全加固审查
  → 全功能端到端用例测试（模拟用户操作）
  → 生成完整技术审计报告：`docs/versions/seal-audit-vX.Y.md`
→ 审计报告中如有任何未解决问题（❌） → **禁止封板，必须先修复**
→ 审计报告全部 ✅ → 执行版本收尾（VERSION 更新、RELEASE_NOTES、CHANGELOG、TODO_NEXT.md）
→ git commit + git tag `vX.Y.0`
→ git push origin 当前分支 + git push origin --tags（仅推送到远程分支，**禁止自动创建 PR**）
→ **停止，输出版本发布报告，等待用户确认**

#### ③ 门禁（连续判定的正确性检查）

| 检查项 | 通过条件 |
|--------|---------|
| 判定依据完整 | 是否实际检查了 §0.4 的全部停止条件？ |
| 功能项位置正确 | 当前任务在功能项中的位置判定是否正确？ |
| 边界处理正确 | 如果触发了功能项/版本边界，是否执行了对应的完整处理流程？ |

## 0.3 阶段切换规则

任务序列以当前版本的**开发计划文件**为准。

> **计划文件命名约定**：推荐使用 `docs/dev-plans/dev-plan-v{X.Y}.md` 格式。但项目中可能使用不同的命名方式（如 `prd-vX.md`、`版本计划-vX.Y.md`、`版本任务计划-vX.Y.md`、`release-plan-vX.Y.md`、`product-plan-vX.md` 等）。AI 应按以下优先级定位计划文件：
> 1. 先检查 `TODO_NEXT.md` 中是否指明了当前计划文件路径
> 2. 再扫描 `docs/dev-plans/` 目录下与当前版本号匹配的文件
> 3. 如果以上均未找到，扫描 `docs/` 目录下所有可能的计划类文件（见 §0.11 Step 1a 的扫描模式）
> 4. 如果仍未找到，**必须停止并报告**

**两层计划文件的关系**：

| 文件 | 作者 | 职责 | 路径示例 |
|------|------|------|---------|
| 开发计划（dev-plan / PRD / 版本计划等） | 产品负责人 | 定义**做什么**：版本目标、功能项、任务列表（每个任务 = 一个 vX.Y.Z）、任务依赖、验收标准 | `docs/dev-plans/dev-plan-v{X.Y}.md`（推荐）或项目已有的计划文件 |
| 实施计划（impl-plan） | AI（Phase 1 产出） | 定义**怎么做**：代码现状理解、文件变更清单、实施步骤、测试策略、风险预判 | `docs/dev-plans/impl-plan-v{X.Y.Z}.md` |

**任务领取规则**：
- 自动连续判定时，读取当前版本的开发计划文件，找到状态为 `Planned` 的下一个 vX.Y.Z 任务
- 如果当前功能项的所有任务已完成，进入下一个功能项的第一个任务
- 如果当前版本的所有功能项已完成，触发版本边界处理（见自动连续判定）
- 如果开发计划文件不存在或无法读取，**必须停止并报告**

## 0.4 必须停止的条件

以下任何一条触发时，必须立即停止开发并等待用户介入：

1. **版本完成**：当前版本所有任务 + 回归全部完成 + §0.11 无任务空闲循环已终止（Bug 修复清单为空或达到循环上限）
2. **自动化门禁连续失败（Part A）**：同一任务的 Part A 自动化门禁修复尝试连续 10 次失败
3. **规范审计门禁连续未通过（Part B/C/D）**：同一任务的 Part B/C/D 审计门禁修复尝试连续 10 次仍为 ❌
4. **需要修改计划外文件**：发现必须改动开发计划中未列出的文件，且无法绕过
5. **计划与代码严重不符**：开发计划的定义与实际代码结构存在根本性矛盾
6. **依赖未满足**：当前任务依赖的前置任务未完成，且无法绕过
7. **数据库 migration 冲突**：需要的 migration 编号已被占用
8. **安全链路变更**：任务涉及核心安全链路的非预期变更
9. **禁止文件违规**：发现当前任务需要修改 §1.7 禁止修改文件清单中 Tier 1 的文件，或 Tier 2 已封板的文件，或 Tier 3 未在任务定义中授权的文件
10. **文件锁冲突（§1.9，如适用）**：当前任务需要修改的文件已被其他 Agent 锁定，且无法协调释放
11. **大版本封板审计未通过（§1.10）**：封板技术审计报告中存在任何 ❌ 项，禁止封板，必须先修复
12. **分支错误（§1.5.4）**：当前所在分支不是自己的 `test-v-{X}-{Y}-{a}` 开发测试分支。在 Phase 1 ① 分支确认环节检测到分支不对时，**立即停止开发**，不执行后续任何步骤，向用户报告当前状态并说明如何切换到正确的分支
13. **工作目录错误**：当前工作目录不在正确的项目根目录或 worktree 路径下。同样**立即停止**

停止时必须输出：停止原因、当前进度、阻塞点描述、建议方案。

## 0.5 全局禁止事项与修改边界铁律

> 以下规则同时作为"全局禁止事项"和"修改边界铁律"，是整个治理体系的最高优先级约束。
> **本节为唯一权威定义，完整条目仅在此处维护。** dev-governance.md 末尾和 CLAUDE.md 的"修改边界铁律"章节均为引用入口，不重复条目内容。

**流程纪律：**
1. 禁止在未读代码的情况下开始编码
2. 禁止跳过 Phase 1（理解与计划）直接写代码
3. 禁止一次性领取多个任务
4. 禁止把"代码写完了"等同于"任务完成了"——必须过门禁
5. 禁止在开发线程内执行合并、重构、架构优化
6. 禁止用模糊表述替代具体实现

**范围纪律：**
7. 禁止修改与当前任务无关的文件——只改当前任务定义的文件
8. 禁止发明开发计划中不存在的需求——衍生想法只能写入 WISHLIST.md
9. 禁止自行设计产品功能或扩展需求范围
10. 禁止跨越任务边界——其他文件、其他模块不在范围内

**代码保护纪律：**
11. 已有代码的删除分两类处理：
    - **功能性删除**（移除一个功能/接口/模块）：禁止直接删除，仅允许注释掉（注释须标注 `// DEPRECATED vX.Y.Z: <原因>`）。被注释的代码将在大版本（vX.Y.0）封板时统一审核清理
    - **重构性删除**（同一功能的代码位置/结构变更，如函数拆分、文件搬迁）：允许直接删除旧代码，但必须满足以下条件：① 在实施计划文档（impl-plan）中明确标注每一处重构性删除：`重构性删除：{文件路径}:{行号范围} → {新位置说明}`；② Phase 4 ③ Part D 审计时逐项确认每处重构性删除确实属于"同功能结构变更"而非"功能移除"
12. 禁止未授权修改已有公共接口（API、函数签名、数据结构）——必须保持向后兼容，如必须修改需显式获得授权
13. 禁止未预告的架构变更——涉及模块结构、数据模型、通信协议的变更必须在实施计划中明确说明，临时架构变更必须停止并报告
14. 禁止为了"代码整洁"而改动——代码风格、注释方式、变量命名等风格问题不是改动理由

**文件保护纪律：**
15. 禁止修改 §1.7 禁止修改文件清单中受保护的文件——Tier 1 绝对禁止；Tier 2 封板后禁止；Tier 3 需任务定义明确授权
16. 禁止修改其他 Agent 持锁的文件（§1.9，如适用）——必须先获取锁再修改

**质量纪律：**
17. 禁止引入新的测试失败
18. 禁止杜撰测试结果或门禁结果——测试结果、审计结果、运行结果必须真实
19. 禁止跳过测试——每个 vX.Y.Z 任务必须有测试
20. 禁止做顺手重构——发现不相关的问题只记录到 WISHLIST.md，不修改

**实现忠实度纪律（v1.12 新增）：**
21. 禁止静默降级实现——开发计划明确要求的技术方案（embedding 搜索、特定算法、API 字段等），编码时必须按计划执行。无法实现必须立即停止并报告，由用户决定是否接受降级方案。常见降级行为包括：① 计划要求 embedding 相似度搜索，实际只用关键词匹配 ② 计划要求 3 种策略，实际只实现 1 种 ③ 计划要求特定 API 字段，实际省略不实现 ④ 计划要求异步处理，实际改为同步简化版
22. 禁止模糊声称完成——Phase 4 逐条验收时，每条验收标准必须有明确的 ✅/❌ 结论和证据（测试输出、curl 结果、截图等），禁止用"基本完成"、"大部分实现"等模糊表述

## 0.6 衍生建议与 Wishlist 管理

在开发过程中发现计划外的优化机会、新功能需求、技术债务等：

**处理方式**：
1. **不得自行实现**——仅记录
2. 在当前任务汇报的"影响分析"中简要提及
3. 同时追加写入 `docs/WISHLIST.md`

**WISHLIST.md 格式**：
```markdown
# KB Platform 衍生建议清单（Wishlist）

> 本文件由开发过程中自动维护，记录版本开发计划之外发现的改进建议。
> 所有条目仅为建议，不自动纳入任何版本计划。由 Product Owner 评审后决定是否采纳。

## v0.39.0 开发期间发现

### W-{版本}-001: {建议标题}
- **来源任务**: T{N} — {任务名}
- **发现日期**: YYYY-MM-DD
- **类型**: 功能建议 / 技术优化 / 安全加固 / UX 改善 / 技术债务
- **描述**: {具体描述}
- **依据**: {为什么建议这么做}
- **影响范围**: {涉及哪些模块}
- **建议优先级**: P0/P1/P2（开发者视角，仅供参考）
```

**编号规则**：`W-{版本}-{序号}` 中的序号为**自动递增**——新条目取当前版本分组下已有最大序号 +1。例如当前版本分组下已有 W-1.0-003，则下一个条目编号为 W-1.0-004。首条为 001。

**去重检测（写入前必须执行）**：
在向 WISHLIST.md 追加新条目之前，必须先扫描已有条目，检查是否存在语义重复：
1. 读取 WISHLIST.md 中所有已有条目的**标题**和**描述**
2. 将待新增条目与已有条目逐条对比，判定是否存在以下任何一种重复：
   - **完全重复**：标题和描述本质相同（仅措辞差异）
   - **包含重复**：待新增条目已被某个已有条目覆盖（已有条目范围更大）
   - **等价重复**：描述不同但指向同一个改动点或同一个根因
3. **如果检测到重复** → 不新增，在任务汇报中注明"已存在等价 Wishlist 条目 W-{版本}-{序号}，跳过新增"
4. **如果无重复** → 正常新增并分配新编号

```
步骤 6: 进入自动连续开发模式
```

**TODO_NEXT.md 不存在时的降级检测流程**：

当步骤 2 发现 `TODO_NEXT.md` 不存在时，按以下顺序尝试恢复状态：

1. **扫描开发计划文件**：按 §0.3 的计划文件定位优先级，查找可用的开发计划。如果找到多个计划文件，按步骤 4 的"多版本选择规则"处理——选择版本号最小的未完成计划，不询问用户
2. **如果找到开发计划**：从中提取任务状态，自动创建 `TODO_NEXT.md`（格式见 §1.8），然后继续正常流程
3. **如果未找到开发计划**：向用户输出提示：
   ```
   ⚠️ 未找到 TODO_NEXT.md 和开发计划文件。
   当前项目可能尚未创建首版开发计划。

   建议操作：
   A) 创建首版开发计划（我可以引导你创建）
   B) 指定现有计划文件的路径
   C) 查看当前项目状态（仅输出检测摘要，不进入开发模式）
   ```
   等待用户选择后执行对应操作。

### 查询命令

**"查看当前进度"** → 仅输出检测结果摘要，不进入开发模式

## 0.9 异常处理

**门禁失败**：记录失败到 `docs/.gate-failures.json`（§0.12）→ 分析原因 → 修复 → 重跑 → 连续 3 次相似失败触发失败模式分析和策略调整（§0.12）→ Part A 自动化门禁累计 10 次失败则停止；Part B/C/D 规范审计门禁累计 10 次失败则停止。失败计数以 `docs/.gate-failures.json` 为准，不依赖上下文记忆。门禁失败触发的阶段回退详见 §0.10

**需要修改计划外文件**：停止编码 → 说明原因 → 等待用户确认

**计划与代码不符**：以代码为准 → 可自行调整则调整并说明 → 根本性差异则停止

**发现计划外 Bug**：记录到 wishlist → 在汇报中提及 → 不修复，继续下一任务

## 0.10 阶段回滚流程

当后续阶段的门禁或产出揭示前序阶段存在问题时，允许回退到前序阶段重新执行，而非强行推进。

> **适用范围说明**：本节回滚流程仅覆盖**日常开发任务**（七阶段治理 Phase 1-7 内的回退）。
> **升级流程本身**（使用 dev-workflow-upgrade 技能执行的 7 个升级阶段）的中断恢复、进度恢复和整体回退，
> 由升级工具独立的恢复机制覆盖（包括：升级前 Git 快照、阶段检查点、`docs/.upgrade-progress.json` 进度追踪、
> 按阶段回滚和完全回滚）。两套回滚机制互不干扰。

### 回滚触发条件与目标阶段

| 当前阶段 | 触发条件 | 回退目标 | 回退后动作 |
|---------|---------|---------|-----------|
| Phase 3（测试） | Part A 自动化门禁连续 10 次失败 | Phase 2（编码） | 分析失败根因，修复代码，重新提交，从 Phase 3 重新走 |
| Phase 4（审计） | Part B/C 发现代码层面缺陷（逻辑错误、接口不一致、规范违规） | Phase 2（编码） | 修复代码，从 Phase 3 重新走（需重新通过 Part A） |
| Phase 4（审计） | Part D 发现计划偏差过大（实际实现与计划严重不符、范围蔓延） | Phase 1（计划） | 修订实施计划文档，从 Phase 2 重新走 |
| Phase 5（报告） | 发现测试数据与审计数据不一致 | Phase 3（测试） | 重新运行测试，从 Phase 4 重新走 |
| Phase 6（收尾） | 版本号一致性检查失败（VERSION 与 CHANGELOG/开发计划/commit/TODO_NEXT 不一致） | Phase 6 ②（收尾执行） | 修正版本号相关文件，重新执行 Phase 6 ② 收尾步骤，不回退到更早阶段 |

### 回滚执行步骤

1. **记录回退原因**：在当前阶段的输出中明确标注：
   - 回退原因（具体的失败项或问题描述）
   - 回退目标阶段
   - 预期修复方向
2. **git commit 当前状态**：提交当前所有修改，commit message 格式：`rollback(vX.Y.Z): Phase N → Phase M - <原因简述>`
3. **执行回退**：回到目标阶段的 ② 执行步骤，按该阶段的正常流程重新执行
4. **重新通过门禁**：从目标阶段开始，逐阶段重新通过所有门禁，不可跳过中间阶段

### 回滚限制

- **单次任务累计回退上限：10 次**。超过 10 次回退 → 停止执行，输出诊断报告，等待用户介入
- **禁止跨越式回退**：不允许从 Phase 5 直接回退到 Phase 1（除非中间阶段的门禁也连锁失败）
- **回退不重置已有产出**：回退到 Phase 2 时，Phase 1 的实施计划文档保留（除非回退目标就是 Phase 1）
- **回退计数在任务汇报中记录**：Phase 6 汇报时须标注"本任务回退次数：N 次"及每次回退原因

## 0.11 无任务空闲循环（Idle Scan-Test-Fix Cycle）

当自动连续判定发现**当前版本已无待执行的 Planned 任务**时，不直接停止，而是进入以下循环流程：

### 循环流程

```
Step 1: 需求与计划 Gap 扫描（PRD 优先，无 PRD 则降级为开发计划 Gap 扫描）
  ↓ 有 Gap → 生成任务，回到正常七阶段流程
  ↓ 无 Gap（或无计划文件） → 进入 Step 2
Step 2: 全量测试
  ↓ 生成测试报告
Step 3: 问题分类
  ↓ 将测试报告中的所有问题（不允许精简、不允许遗漏）分为两类：
  ↓ → 计划内修复 → Bug 修复清单
  ↓ → 计划外建议 → WISHLIST.md
Step 4: 判定是否继续
  ↓ Bug 修复清单有条目 → 执行修复任务，修复完成后回到 Step 2
  ↓ Bug 修复清单为空（0 条） → 停止开发，等待用户介入
```

### Step 1：需求与计划 Gap 扫描

> 本步骤优先扫描 PRD 文件，如果 PRD 不存在则降级为基于开发计划的 Gap 扫描。

**1a. 扫描计划类文件**

扫描 `docs/` 目录下所有计划类文件（文件命名可能多样化）：

```bash
# 扫描可能的计划类文件（命名约定不强制统一，按以下模式匹配）
find docs/ -maxdepth 3 \( \
  -name "prd*.md" -o -name "PRD*.md" -o \
  -name "dev-plan-*.md" -o -name "dev_plan_*.md" -o \
  -name "*开发计划*.md" -o -name "*版本计划*.md" -o \
  -name "*版本任务计划*.md" -o -name "*product-plan*.md" -o \
  -name "*release-plan*.md" -o -name "*task-plan*.md" \
\) -not -path "./.git/*" 2>/dev/null
```

**1b. 按优先级分流**

| 场景 | 处理方式 |
|------|---------|
| 存在 PRD 文件（`prd*.md` / `PRD*.md`） | 以 PRD 为权威需求来源，逐条对照 PRD 中定义的需求检查 Gap |
| 无 PRD 文件，但存在开发计划文件 | **降级为开发计划 Gap 扫描**——以开发计划（dev-plan / 版本计划等）中定义的任务为检查基准 |
| 无任何计划类文件 | 跳过 Step 1，输出"⚠️ 未找到 PRD 或开发计划文件，无法执行 Gap 扫描"，直接进入 Step 2 |

**1c. Gap 检查流程**（无论 PRD 还是开发计划）

逐条对照计划文件中定义的需求/任务，检查：
- 该需求/任务是否已有对应的开发记录（开发计划中有对应 vX.Y.Z 且状态为 Completed）
- 对应的功能是否在代码中实际存在且可运行

**如果发现未实现的需求/任务**（Gap）：
- 输出 Gap 清单（需求编号、需求描述、缺失原因）
- 将 Gap 转化为待执行任务，补入开发计划
- 回到正常的七阶段执行流程（从 Phase 1 开始）

**如果所有需求/任务均已实现**（无 Gap）：
- 进入 Step 2

### Step 2：全量测试

1. 按 `testing-strategy.md` 的测试类型和频次，执行**当前版本级别（Per-Version）的全量测试**
2. 包括但不限于：UT、IT、REG、E2E、API、SDK（如有）、USECASE、UI（如有）、UAT、PERF、LOAD、SEC、A11Y、COMPAT、L10N、DATA（按项目启用的测试类型）
3. 生成测试报告，命名为：`docs/versions/idle-test-report-vX.Y.Z-{a}.md`
   - `{a}` 为本轮循环序号，首次为 1，每次循环 +1
4. 测试报告内容标准按 `testing-strategy.md` §6 的报告内容规范

### Step 3：问题分类

将测试报告中发现的**所有问题**（不允许精简、不允许合并、不允许遗漏，逐条保留）分为两类：

**分类标准**：

| 类别 | 定义 | 去向 |
|------|------|------|
| **计划内修复（Planned Fix）** | 在测试过程中发现的、范围在当前版本 PRD 或开发计划内的 Bug。通常是上个版本遗留或当前版本引入的功能缺陷、逻辑错误、接口不一致、UI 异常等。 | Bug 修复清单 |
| **计划外建议（Unplanned Suggestion）** | 测试中发现的改进机会，但不属于当前 PRD/开发计划范围。例如：性能优化建议、新功能想法、架构改进、用户体验增强等。 | WISHLIST.md |

**判定规则**：
- 如果一个问题能在当前版本的 PRD 或 dev-plan 中找到对应的需求描述或验收标准 → **计划内修复**
- 如果一个问题超出当前 PRD/dev-plan 定义的范围 → **计划外建议**
- 如果边界模糊，优先归入**计划内修复**（宁可多修不可遗漏）
- 向 WISHLIST.md 追加计划外建议时，必须先按 §0.6 规则执行去重检测，防止在循环过程中产生重复条目

### Bug 修复清单定义与命名

**定义**：Bug 修复清单是在无任务空闲循环的测试阶段中发现的、范围在 PRD/开发计划内的 Bug 集合。这些 Bug 通常是上个版本遗留或当前版本开发过程中引入的功能缺陷，需要在当前版本内修复。

**命名规范**：`docs/dev-plans/bugfix-list-vX.Y.Z-{a}.md`
- `vX.Y.Z` 为当前版本号
- `{a}` 为当前版本下的 Bug 修复清单序号，从 1 开始，每次产生新清单时自动 +1
- 示例：`bugfix-list-v1.2.3-1.md`、`bugfix-list-v1.2.3-2.md`、`bugfix-list-v1.2.3-3.md`

**清单格式**：
```markdown
# Bug 修复清单 vX.Y.Z-{a}

> 来源：无任务空闲循环 Step 3 问题分类
> 测试报告：idle-test-report-vX.Y.Z-{a}.md
> 生成日期：YYYY-MM-DD

## 修复任务列表

### BF-{a}-001: {Bug 标题}
- **严重程度**: Critical / High / Medium / Low
- **发现测试类型**: {UT / IT / E2E / API / ...}
- **问题描述**: {具体表现}
- **复现步骤**: {如何复现}
- **期望行为**: {正确的行为应该是什么}
- **关联 PRD 需求**: {对应的 PRD 条目}
- **涉及模块**: {影响的模块/文件}
- **修复状态**: Planned / In Progress / Fixed / Verified

### BF-{a}-002: {Bug 标题}
...
```

**编号规则**：`BF-{a}-{序号}` 中的序号为自动递增，首条为 001。

### Step 4：判定是否继续

- **Bug 修复清单有条目**：
  → 将 Bug 修复清单作为开发任务输入
  → 每个 Bug 按正常的七阶段流程修复（Phase 1-7）
  → 全部修复完成后，**回到 Step 2 重新执行全量测试**
  → 这是一个循环，直到测试后产出的 Bug 修复清单为空

- **Bug 修复清单为空（0 条计划内修复）**：
  → 停止开发
  → 输出最终状态报告：当前版本所有 PRD 需求已实现、所有测试已通过、无计划内 Bug
  → 等待用户介入（进入下一版本或其他指示）

### 循环限制

- **单次空闲循环上限：5 轮**（Step 2 → Step 3 → Step 4 → 回到 Step 2 为一轮）。超过 5 轮仍有 Bug → 停止执行，输出诊断报告，等待用户介入
- **每轮测试报告和 Bug 修复清单都必须保留**，不可覆盖或删除历史记录
- **WISHLIST 条目在循环过程中累积追加**，不清空

## 0.12 门禁失败计数追踪机制

> 本节定义门禁失败次数的持久化追踪机制，确保失败计数在 session 中断、上下文窗口滚动等场景下不丢失。
> Phase 3 ③ Part A 和 Phase 4 ③ Part B/C/D 的失败计数均通过此机制管理。

### 追踪文件

**位置**：`docs/.gate-failures.json`

**文件格式**：

```json
{
  "task_id": "vX.Y.Z",
  "failures": {
    "part_a": {
      "count": 3,
      "last_failure": "2026-03-20T14:30:00+08:00",
      "history": [
        { "attempt": 1, "timestamp": "2026-03-20T14:00:00+08:00", "reason": "pytest: 2 tests failed (test_auth.py)" },
        { "attempt": 2, "timestamp": "2026-03-20T14:15:00+08:00", "reason": "pytest: 1 test failed (test_auth.py::test_token_expiry)" },
        { "attempt": 3, "timestamp": "2026-03-20T14:30:00+08:00", "reason": "eslint: 3 errors in auth_middleware.ts" }
      ],
      "pattern_alert": null
    },
    "part_bcd": {
      "count": 0,
      "last_failure": null,
      "history": []
    }
  }
}
```

### 操作流程

**门禁失败时——写入失败记录**：

```bash
# 1. 如果 docs/.gate-failures.json 不存在，创建初始文件
# 2. 读取文件，检查 task_id 是否为当前任务
#    - 如果 task_id 不同（上一个任务的残留），清空重建
#    - 如果 task_id 相同，追加记录
# 3. 对应 part（part_a 或 part_bcd）的 count +1，追加 history 条目
# 4. 写回文件
```

**门禁执行前——读取失败计数**：

```bash
# 1. 读取 docs/.gate-failures.json
# 2. 检查 task_id 是否为当前任务
# 3. 检查对应 part 的 count 是否 ≥ 10
#    - 是 → 立即停止，输出诊断报告（包含全部 history），等待用户介入
#    - 否 → 执行失败模式分析（见下方），然后继续执行门禁
```

**失败模式分析（连续相似失败检测）**：

当对应 part 的 count ≥ 3 时，在执行门禁前必须先分析最近 3 条 history 的 reason 字段：

1. **相似度判定**：将最近 3 条 reason 逐两两比较，如果任意两条之间的文本重复度 > 80%（去掉时间戳、数字等变量部分后，核心描述高度一致），则判定为"相似失败"
2. **触发条件**：3 条 reason 中有 ≥ 2 对被判定为"相似失败"
3. **触发行为**：
   - 输出警告：`⚠️ 失败模式分析：最近 3 次失败原因高度相似，当前修复策略可能无效。`
   - 列出 3 条 reason 的核心描述
   - AI 必须**主动改变修复方向**，明确输出：`🔄 修复策略调整：从 [{旧策略描述}] 改为 [{新策略描述}]，理由：{为什么认为旧策略无效}`
   - 如果 AI 无法提出有效的新策略 → 停止，输出：`⏸️ 当前修复策略已失效且无法自主找到替代方案，需要用户介入指导修复方向。`，等待用户介入
4. **记录**：在 `docs/.gate-failures.json` 的对应 part 中追加 `"pattern_alert"` 字段，记录触发时间和策略调整内容，格式为：
   ```json
   "pattern_alert": {
     "triggered_at": "{时间}",
     "old_strategy": "{旧策略描述}",
     "new_strategy": "{新策略描述}",
     "similar_reasons": ["{reason1}", "{reason2}", "{reason3}"]
   }
   ```

> 此机制的目的是避免 AI 陷入"用相同方法反复尝试修复相同问题"的无效循环。10 次失败上限是硬性兜底，但 3 次相似失败的早期检测能更快地识别策略失效，减少浪费。

**门禁通过时——清除对应记录**：

```bash
# 1. 读取 docs/.gate-failures.json
# 2. 将通过的 part（part_a 或 part_bcd）的 count 归零，history 清空
# 3. 写回文件
```

**任务完成时——清理文件**：

在 Phase 6 ② 收尾时，如果 `docs/.gate-failures.json` 存在且 task_id 为当前任务，将其整体清空或删除（下一个任务会重新创建）。

### 与 §0.9 异常处理的关系

§0.9 中的"连续 10 次失败则停止"规则，其失败计数以 `docs/.gate-failures.json` 中的记录为准，不依赖 AI 的上下文记忆。

### 与 §0.10 阶段回滚的关系

阶段回滚时，失败计数**不重置**——回滚是为了修复问题，不是为了重置计数器。只有当门禁成功通过后，计数才清零。

### 文件管理

- 此文件**不纳入 git 版本控制**（应加入 `.gitignore`）
- 此文件仅在开发过程中临时使用，任务完成后清理
- 如果文件不存在，视为计数为 0（首次执行）

## §0.1.5 全局任务连续性原则

> **⚠️ 本原则优先级最高，适用于所有任务执行场景。**

1. **分支操作自动执行**：所有分支上的操作（`git add`、`git commit`、`git push origin {branch}`）无需等待用户确认，直接执行。
2. **任务间禁止询问**：任务与任务之间、Phase 与 Phase 之间、功能项与功能项之间，**禁止输出"是否继续"、"继续？"、"继续执行？"等询问**。门禁通过后直接进入下一步。
3. **仅 main 合并需用户确认**：只有当需要合并到 `main` 分支（PR/merge）时，才停止并等待用户评审。
4. **封板流程为原子操作**：Phase 8 → 空闲循环 → 封板检查 → 版本收尾，全流程连续执行，禁止在步骤之间插入确认。
5. **门禁失败自动修复**：门禁失败后自动修复并立即重跑，不询问用户"是否重跑"。累计 10 次失败才停止。
6. **Hook 响应不中断任务流**：如果系统 hook 触发并需要回应，回应完毕后**必须立即继续当前任务**，不得停下等待用户。
7. **Context 窗口达到 ~60% 时自动交接**：当 AI 感知到 context 压力信号（系统开始压缩早期消息、AI 遗忘前读过的文件路径或变量名、单次对话已跨越 5+ 个任务），**必须在当前任务完成后立即执行自动交接流程**（详见 §0.13）。

## §0.13 Context 压力自动交接

> 当对话上下文接近容量上限时，AI 必须主动执行交接，而不是停下来让用户手动开新会话。

**触发条件**：当 AI 感知到以下信号时视为 context 压力（约 60% 容量）：
- 系统开始压缩/折叠早期消息
- AI 开始遗忘前面读过的文件路径或变量名
- 单次对话已跨越 5+ 个任务

**自动交接流程**（不可跳过）：

1. **完成当前 Phase**：不在 Phase 中途断开。如果当前 Phase 剩余工作量很大（>50%），先 commit 已完成部分
2. **收尾提交**：`git add` + `commit` + `git push origin 当前分支`
3. **更新 TODO_NEXT.md**：写入精确的断点信息（当前版本、任务、Phase、下一步）
4. **创建接续任务**：使用 `create_scheduled_task` 创建 1 分钟后触发的一次性任务，prompt 内容为"继续自动化开发"
5. **输出交接摘要**

**禁止行为**：
- 禁止用"context 快满了"作为停止工作的理由而不执行交接
- 禁止输出"请开新会话"然后等待用户操作
- 禁止在 Phase 中途就中断交接

## §0.14 版本号一致性约束（v1.6 新增）

> 所有过程文档必须携带版本号标识，禁止自定义版本命名。

| 文档类型 | 版本号要求 | 示例 |
|---------|----------|------|
| 开发计划 | 文件名含 `vX.Y` | `dev-plan-v0.42.md` |
| 实施计划 | 文件名含 `vX.Y.Z` | `impl-plan-v0.42.4.md` |
| 审计报告 | 文件名含 `vX.Y.Z` | `audit-report-v0.42.4.md` |
| 任务报告 | 文件名含 `vX.Y.Z` | `task-report-v0.42.4.md` |
| 测试报告 | 文件名含 `vX.Y.Z` | `test-report-v0.42.4.md` |
| Commit message | scope 含 `vX.Y.Z` | `feat(v0.42.4): search pagination` |

**禁止**：使用 `R1`、`Sprint-3`、`Phase-A` 等非语义化版本命名。
