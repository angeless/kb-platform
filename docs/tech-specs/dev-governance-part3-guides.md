## 3.2 增量开发操作指南（Phase 2 引用）

**用途：** Phase 2 ② 执行的增量开发操作要点的详细展开。

**核心原则：**
- **增量编写**：每次只完成一个小步骤，立即验证
- **及时验证**：不积累修改；每个文件完成后立即检查语法
- **避免幻觉**：严禁想象或猜测某个库、函数、接口的存在；必须通过代码扫描确认
- **清晰注释**：关键逻辑添加注释；函数签名明确

**详细操作步骤：**

1. **开始前检查**
   ```bash
   git status              # 确保 clean
   git branch              # 确认在正确分支
   cat VERSION             # 确认当前版本号
   ```

2. **按照实施计划逐步执行**

   对于每一个 Step（例如 Step 1）：

   a. **打开相关文件，阅读已有代码**
      - 运行 grep 找到相关代码
      - 阅读参考类 / 函数的完整实现
      - 理解基类或接口的要求

   b. **添加新代码**
      - 在适当位置插入新代码
      - 每个方法上添加 docstring
      - 使用 TODO 标记未完成部分

   c. **验证语法**
      ```bash
      ruff check services/ packages/  # Python 代码 lint 检查
      # 前端代码检查
      cd apps/web && npx tsc --noEmit
      ```

   d. **运行相关单元测试**
      ```bash
      pytest tests/ -x -q                    # 后端单元测试
      cd apps/web && npx vitest run           # 前端单元测试
      ```

   e. **生成简要的 Step 完成笔记**
      在实施计划中旁注完成时间和摘要

3. **处理集成依赖**

   当完成单个文件的修改后，验证不会破坏现有引用：
   ```bash
   ruff check --select F401,F811 services/ packages/   # 检查未使用导入和重定义
   ```

4. **定期 commit**

   不允许积累超过 4-5 个 Step 的改动后再 commit。推荐每个 Step 或每日 commit：
   ```bash
   git add {{文件}}
   git commit -m "feat({{scope}}): {{description}}

   - {{实现细节1}}
   - {{实现细节2}}"
   ```

5. **避免常见陷阱**

   - **幻觉导入：** 不要假设库存在；通过 `pip show` / `requirements.txt` / `package.json` 确认
   - **模糊假设：** 不要假设配置项存在；通过 grep 确认
   - **跨文件不一致：** 使用 `packages/shared-schemas/` 中的中央集中定义而非重复定义

**检查清单：**
- [ ] 所有新文件都通过语法检查
- [ ] 每个 commit message 满足规范
- [ ] 没有幻觉导入或假设
- [ ] 代码注释清晰
- [ ] 没有遗漏涉及文件

## 3.3 测试操作指南（Phase 3 引用）

**用途：** Phase 3 ② 执行（全面测试）的详细操作指南。

**关联文件**：`testing-strategy.md` 定义了测试类型分类、频次与触发时机、各类型通用五步流程（准备→设计→执行→验证→记录）、测试用例编写规范、测试文件夹路径管理、测试报告命名规范、测试数据管理。本操作指南侧重具体操作步骤，`testing-strategy.md` 侧重策略与规范。

**分为三个级别：单元测试、集成测试、手工验证**

### 3.3.1 单元测试

**操作步骤：**

1. **确认测试文件存在**
   - 对于新模块，创建 `tests/test_{{模块名}}.py`（后端）或 `apps/web/src/**/__tests__/{{组件名}}.test.tsx`（前端）
   - 对于既有模块的扩展，在已有测试文件中新增测试

2. **编写测试用例**

   遵循 Arrange-Act-Assert (AAA) 模式：

   ```python
   def test_{{功能}}_success():
       """Test {{功能}} with valid inputs."""
       # Arrange: set up test data
       {{设置测试数据和 mock}}

       # Act: call the method
       result = {{调用函数}}

       # Assert: verify the result
       assert {{验证结果}}

   def test_{{功能}}_failure():
       """Test {{功能}} with invalid inputs."""
       # Arrange
       {{设置失败场景}}

       # Act & Assert
       with pytest.raises({{异常类型}}):
           {{调用函数}}
   ```

3. **运行单元测试**
   ```bash
   pytest tests/ -x -q --tb=short           # 后端（pytest）
   cd apps/web && npx vitest run             # 前端（vitest）
   ```

4. **衡量覆盖率**
   ```bash
   pytest tests/ --cov=services --cov=packages --cov-report=term-missing   # 后端覆盖率
   cd apps/web && npx vitest run --coverage                                # 前端覆盖率
   ```
   目标：≥ 80% 代码行覆盖率

### 3.3.2 集成测试

**操作步骤：**

1. **定义集成测试场景**

   集成测试应覆盖多个模块协作的真实流程，不只是单个模块：

   ```python
   def test_end_to_end_{{流程}}():
       """End-to-end test: {{用户的完整流程}}."""
       # Step 1: 初始化系统状态
       {{初始化}}

       # Step 2: 执行操作序列
       result1 = {{操作1}}
       result2 = {{操作2}}
       result3 = {{操作3}}

       # Step 3: 验证最终状态
       assert {{最终验证}}
   ```

2. **如有 API，验证端点**

   对于 FastAPI REST API，测试应包括：
   ```python
   def test_api_endpoint_success():
       response = client.post('/api/v1/{{端点}}', json={{请求体}})
       assert response.status_code == 200
       assert response.json() == {{预期响应}}

   def test_api_endpoint_unauthorized():
       response = client.post('/api/v1/{{端点}}', headers={})
       assert response.status_code == 401
   ```

3. **运行集成测试**
   ```bash
   pytest tests/integration/ -x -q --tb=short
   ```

### 3.3.3 手工验证

**操作步骤：**

1. **启动应用**
   - 使用 Docker Compose 启动所有服务（`infra/docker/`）
   - 验证应用启动正常

2. **执行真实用户流程**
   - 按照用户的实际操作路径验证功能
   - 记录每一步的观察结果

3. **验证关键点**
   - 成功路径是否清晰
   - 错误提示是否清晰准确
   - 用户体验是否流畅
   - 与已有功能的一致性

4. **记录验证结果**

   | 项目 | 操作 | 观察结果 | 状态 |
   |-----|------|--------|------|
   | {{功能1}} | {{操作说明}} | {{观察结果}} | PASS/FAIL |
   | {{功能2}} | {{操作说明}} | {{观察结果}} | PASS/FAIL |

### 评分量化标准

每个维度按以下标准评定等级：

**等级 A（优秀）**：0 个 Critical 问题 + 0 个 High 问题 + ≤ 2 个 Medium 问题。代码质量高，可直接合并。

**等级 B（合格）**：0 个 Critical 问题 + ≤ 1 个 High 问题 + ≤ 5 个 Medium 问题。存在小范围需改进项，修复后可合并。

**等级 C（不合格）**：存在 ≥ 1 个 Critical 问题，或 ≥ 2 个 High 问题，或 > 5 个 Medium 问题。必须修复后重新审计。

**问题严重程度定义**：

| 严重程度 | 定义 | 示例 |
|---------|------|------|
| Critical | 导致系统不可用、数据丢失、安全漏洞或破坏性回归 | 未处理的空指针异常、SQL 注入、鉴权绕过、数据覆写、Breaking Change |
| High | 功能缺陷、逻辑错误或明显的设计问题，影响核心流程 | 边界条件未处理、错误的业务规则、接口不一致、缺少关键测试 |
| Medium | 代码质量或规范问题，不影响功能但影响可维护性 | 命名不规范、缺少注释、重复代码、测试覆盖不足、文档缺失 |
| Low | 风格建议或微小改进，不阻塞合并 | 代码格式、变量命名偏好、非关键注释缺失 |

> Low 级别问题不计入评分，但应在审计报告中记录供后续优化。

**总体评分规则**：
- **总体 A**：所有 5 个维度均为 A
- **总体 B**：无 C 评分 + 至少 3 个维度为 A
- **总体 C**：存在任何一个维度为 C
- **总体 BLOCKED**：存在 Critical 问题未修复，或 Phase 3 自动化门禁（Part A）未通过

**合并判定**：
- 总体 A 或 B → ✓ APPROVED FOR MERGE
- 总体 C → ✗ REQUIRES FIXES（修复后重新审计）
- 总体 BLOCKED → ✗ BLOCKED（必须解决阻塞问题后重新审计）

## 3.8 常见错误清单与自查机制（Phase 2 门禁引用）

**用途：** Phase 2 ③ 编码门禁中的常见错误自查步骤。记录跨项目通用的、AI 和人类开发者都容易犯的常见错误模式，在每次编码完成后自动扫描检查。

**文件位置：** `docs/experience/common-errors.md`

**文件格式：**
```markdown
# 常见错误清单（Common Errors Checklist）

> 本文件记录跨项目通用的常见开发错误。每个版本开发完成后，如果发现了可在不同项目中复现的通用错误模式，则追加到本清单中。
> Phase 2 编码完成后，门禁流程会逐条扫描本清单中的所有条目。

## 错误条目

### CE-001: 模板占位符残留
- **类型**: 代码质量
- **检测方法**: 搜索 `{{`、`}}`、`TODO`、`FIXME`、`XXX`、`PLACEHOLDER` 等占位符标记
- **严重程度**: High
- **说明**: 模板代码或生成代码中的占位符未被替换为实际值

### CE-002: SQL 特殊字符未转义
- **类型**: 安全 / 运行时崩溃
- **检测方法**: 检查所有 SQL 查询构建代码，确认特殊字符（`&`、`(`、`)`、`'`、`"`、`;`）未被直接拼接进 `to_tsquery()`、`LIKE`、`WHERE` 子句等
- **严重程度**: Critical
- **说明**: 特殊字符直接传入 SQL 函数会导致 500 错误或 SQL 注入风险

### CE-003: 硬编码密钥或敏感信息
- **类型**: 安全
- **检测方法**: 搜索 `password`、`secret`、`api_key`、`token` 等关键词，确认均来自环境变量或密钥管理服务
- **严重程度**: Critical
- **说明**: 密钥、密码、API Token 等不得硬编码在源代码中

### CE-004: 未处理的异步错误
- **类型**: 运行时崩溃
- **检测方法**: 检查所有 `async/await`、`Promise`、`.then()` 是否有对应的 `try/catch` 或 `.catch()`
- **严重程度**: High
- **说明**: 未捕获的异步异常会导致进程崩溃或静默失败

### CE-005: 导入路径错误（相对/绝对混用）
- **类型**: 构建失败
- **检测方法**: 检查 import/require 路径是否与项目模块解析规则一致
- **严重程度**: Medium
- **说明**: 在不同环境下可能出现模块找不到的问题
```

**新增条目规则：**
- 在每个版本的 Phase 6（收尾）或 Phase 7（衍生建议）中，如果发现了本版本开发过程中出现的**跨项目通用错误模式**，追加到 `docs/experience/common-errors.md`
- 编号规则：`CE-{序号}`，序号自动递增，取当前最大序号 +1
- 每个条目必须包含：类型、检测方法、严重程度（Critical / High / Medium / Low）、说明
- **判定标准**：如果一个错误不是项目特定的（例如不是某个业务逻辑的 bug），而是可能在其他项目中也出现的通用模式，则应记录
- **去重规则**：新增前检查是否已有语义等价的条目，如有则不重复添加

**Phase 2 ③ 门禁中的自查流程：**
1. 读取 `docs/experience/common-errors.md`（如文件不存在，跳过此步骤）
2. 逐条执行检测方法，扫描本次编码变更涉及的所有文件
3. 如果检测到匹配 → 标记为 ❌，必须修复后重新自检
4. 如果全部通过 → 标记为 ✅
5. 扫描结果记录在 Phase 2 ③ 门禁输出中
