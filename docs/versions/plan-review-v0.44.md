**🔴 缺陷 H-2：v0.44.3 `GET /versions` 权限语义与只读操作不符**

计划将版本列表接口 `GET /v1/docs/{doc_id}/versions` 的权限设为 `editor+`，但：

- 该接口是**只读**操作（仅返回版本元信息，不含 `content_md`）
- 现有 `GET /v1/docs/{id}/versions/{version}`（版本详情，含全文）的权限不在计划中明确列出，不清楚是 `viewer+` 还是 `editor+`
- 如果版本详情允许 `viewer` 查看，那版本列表要求 `editor+` 在语义上是矛盾的

**建议**：产品 Owner 明确以下问题后，在计划中注明决策理由：
> `viewer` 是否应该能够浏览版本历史（只读）？还是版本历史属于编辑信息、viewer 无需感知？

如果 `viewer` 可看：将 `GET /versions` 权限改为 `viewer+`
如果仅 editor 可看：在计划中加一句"理由：版本历史属于编辑信息，与只读阅读权限分离"

---

**🔴 缺陷 H-3：v0.44.1 关键前置项（`/users/me` 或 JWT role 字段）未核实**

计划 1.2 的"继承已有能力"清单中**不包含** `GET /v1/users/me`，但 v0.44.1 的 Input 要求"从 `/users/me` 或 JWT payload 获取 role"。

- 若 JWT payload 不含 `role` 字段，且 `/users/me` 不存在 → 需修改 `auth.py` 的 token 生成逻辑
- 这不是前端任务，而是后端微修复，但计划未将其作为一个独立步骤或条件任务列出
- 第十三章提到"开始前先确认"，但若确认结果是"需修改"，计划未说明该修改归属哪个任务版本号（v0.44.1 内？还是前置 fix？）

**建议**：在 v0.44.1 的业务规则或风险预判中，明确以下分支：

```markdown
**关键前置确认（Phase 1 必须先做）：**
- 读 `services/api/app/routers/auth.py` 确认 JWT token payload 是否含 `role`
- 若不含：作为 v0.44.1 Phase 2 的第 1 步修改 `auth.py`，scope 已包含，不新增任务版本号
- 若含：直接进入前端开发
```

### 中等优先级问题（可接受但建议在计划中澄清）

**🟡 M-1：v0.44.5 的 `GET /batch-import/{batch_id}` 返回结构未定义**

验收标准写了"返回批次内各文件当前 `parse_status`"，但没有 JSON 结构定义。执行时可能与 schema 产生偏差。

建议：补充返回结构（至少列出字段名和类型），与 `GET /projects/{id}/batch-import` 的 `POST` 返回结构保持风格一致。

---

**🟡 M-2：v0.44.9 合并时 `parent_id` 的跨父级假设未标注为假设**

当前规则：若两个源节点 `parent_id` 不同，新节点 `parent_id = null`（成为顶层节点）。

这是一个有影响的业务决策（将分类提升到根层级），但计划未将其标注为"假设"，也未说明"用户体验上是否合理"。

建议：在该规则后加注：`> ⚠️ 假设：parent_id 不一致时，新节点提升为顶层。若实际需要让用户指定目标父级，需调整入参结构（加 target_parent_id 字段）。`
