## 一、当前代码现状理解

### 1.1 crypto.py 现状

- `_derive_key(secret)`: 将 secret 编码为 UTF-8，不足 32 字节则用 `\0` 填充，超出则截断到 32 字节
- `encrypt(plaintext, secret)`: 用 `_derive_key` 生成密钥 → AES-256-GCM 加密 → 返回 `nonce(12B) + ciphertext`
- `decrypt(data, secret)`: 用 `_derive_key` 生成密钥 → 从 data 中拆出 nonce(12B) + ciphertext → AES-256-GCM 解密
- `mask_api_key(api_key, visible)`: 不涉及加密，不改动

### 1.2 调用方

- `model_provider_service.py`: 使用 `encrypt(api_key, settings.encryption_key)` 加密 API Key，存储为 base64
- `test_utils.py`: 3 个测试覆盖 roundtrip、不同 nonce、错误密钥

### 1.3 安全问题

当前 `_derive_key` 是简单的截断/填充，没有使用标准密钥派生函数。这意味着：
- 短密钥的实际熵低（大量 `\0` 填充）
- 没有经过拉伸（stretching），易受暴力攻击
- 不符合密码学最佳实践

### 1.4 Settings 中的 encryption_key

- 默认值: `"change-me-32-byte-key-for-aes256"`（长度 32）
- 生产环境强制要求 ≥ 32 字符
- 只有 model_provider_service.py 使用此密钥

## 二、本轮实施计划

### 2.1 新增 PBKDF2 密钥派生

新增 `_derive_key_pbkdf2(secret)` 方法：
1. 使用 `hashlib.sha256(secret.encode()).digest()[:16]` 作为固定 salt
2. 使用 `PBKDF2HMAC(SHA256, length=32, salt, iterations=100000)` 派生 32 字节密钥
3. 返回派生后的密钥

### 2.2 新格式加密

修改 `encrypt()`:
1. 使用 `_derive_key_pbkdf2()` 生成密钥
2. 加密后返回 `b"KDF1" + nonce(12B) + ciphertext`（4 字节标识头 + 12 字节 nonce + 密文）

### 2.3 向后兼容解密

修改 `decrypt()`:
1. 检查前 4 字节是否为 `b"KDF1"`
   - 是：使用 `_derive_key_pbkdf2()` 生成密钥，从 data[4:16] 读 nonce，data[16:] 读 ciphertext
   - 否：使用旧的 `_derive_key()` 生成密钥，从 data[:12] 读 nonce，data[12:] 读 ciphertext
2. AES-256-GCM 解密

### 2.4 保留旧方法

保留 `_derive_key()` 用于解密旧格式数据，但新加密不再使用。

## 四、实现约束

1. **接口不变**: `encrypt(plaintext, secret) -> bytes` 和 `decrypt(data, secret) -> str` 签名不变
2. **向后兼容**: 旧格式数据（无 KDF1 头）仍可解密
3. **新加密使用新格式**: 所有新加密数据带 `b"KDF1"` 前缀
4. **固定 salt**: 从 encryption_key 的 SHA-256 前 16 字节派生（确保同一 key 始终产生同一密钥）
5. **iterations**: 100000（OWASP 推荐最低值）
6. **不引入新依赖**: `cryptography` 库已包含 PBKDF2HMAC
