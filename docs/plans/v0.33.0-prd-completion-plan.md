# v0.33.0 PRD 补全 — 实施计划

## 1. 当前代码现状

### 速率限制
- `settings.py` 已有 `rate_limit_per_minute=100`、`upload_rate_limit_per_minute=20`
- 无中间件消费这些配置
- 只有 `RequestIdMiddleware`

### 架构版本历史
- Architecture 模型有 `version` 字段（字符串），但只能 publish，不能对比/回滚
- 无"创建新版本"API

### Worker 编排
- `ingestion-worker` 存在且完整：4 个解析器（text/pdf/ocr/asr）+ Celery task
- `pipeline-worker` 不存在，设计文档中要求的分类→架构→文档生成→质检编排缺失

---

## 2. 本轮实施计划（按顺序）

### 任务 A：速率限制中间件
- 新建 `middleware/rate_limit.py` — Redis 滑动窗口
- 在 `main.py` 注册
- 从 `settings` 读取限流配置
- 上传端点用 `upload_rate_limit_per_minute`，其余用 `rate_limit_per_minute`

### 任务 B：架构版本历史
- 新增 `POST /v1/architectures/{id}/fork` — 从当前架构创建新版本（复制节点）
- 新增 `GET /v1/architectures/{id}/compare/{other_id}` — 对比两个架构版本的节点差异
- 新增 `POST /v1/architectures/{id}/rollback` — 回滚到指定版本

### 任务 C：Pipeline Worker（9 阶段编排）
- 新建 `services/pipeline-worker/` 目录
- Celery task `run_pipeline(project_id, job_id)` 编排 9 阶段
- 调用 AI Orchestrator 完成分类/架构草稿/文档生成/质检
- 更新 docker-compose.yml 注册 pipeline-worker 服务

## 4. 实现约束

1. 速率限制不阻塞已有 API 行为，仅在超限时返回 429
2. 架构 fork 深复制所有节点，新架构 version 自动递增
3. Pipeline Worker 的 AI 调用通过 httpx 请求 AI Orchestrator，不直接调模型
4. 不修改 ingestion-worker 已有代码
