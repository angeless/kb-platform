# V0.3.0 实施计划：Ingestion Worker — 基础解析器接入

## 当前代码现状理解

### 已有能力
- **API 服务** (services/api)：完整的认证、CRUD、文件上传、URL 导入、压缩包导入
- **数据模型**：Asset（含 parse_status 字段）、AssetChunk（解析结果存储表）、Job（含 celery_task_id 字段）
- **共享配置**：shared-config 含 Redis URL、PostgreSQL URL
- **基础设施**：docker-compose 有 PostgreSQL + Redis + MinIO
- **Job API**：POST /v1/jobs 创建任务、GET 状态查询、POST retry
- 当前上传后 parse_status 始终为 "pending"，无实际解析

### 差距
- 无 `services/ingestion-worker/` 目录和代码
- 无 Celery app 配置
- API 服务的 Job 创建不下发实际 Celery 任务
- 无解析器实现（文本/PDF 等）
- 上传后不触发解析流程

## 本轮实施计划

### 目标
搭建 ingestion-worker 服务，实现纯文本文件的基础解析，打通「上传 → 创建 Job → Celery 任务 → 解析 → 写入 AssetChunk → 更新 parse_status」完整链路。

### 分步方案

**Step 1**: 创建 ingestion-worker 服务骨架（Celery app + pyproject.toml）

**Step 2**: 实现文本解析器（text_parser）— 将文本文件按段落/固定长度切分为 chunk

**Step 3**: 实现 Celery 任务 `parse_asset` — 从 DB 读取 Asset → 从 MinIO 下载文件 → 调用解析器 → 写入 AssetChunk → 更新 parse_status

**Step 4**: 修改 API 服务的 job_service — 当创建 `ingest` 类型 Job 时，下发 Celery 任务并记录 celery_task_id

**Step 5**: 补充测试

## 实现约束

1. **不破坏 API 服务已有 71 个测试**
2. **不修改 shared-models** — AssetChunk 模型已满足需求
3. **不修改 shared-config** — Redis URL 已配好作为 Celery broker
4. **Celery broker 使用 Redis**（settings.redis_url）
5. **解析器遵循统一接口** — 输入 bytes + filename → 输出 list[dict]（content_text, page_or_timestamp, tags）
6. **文本切分策略** — 按双换行分段，每段为一个 chunk，保持段落完整性
7. **parse_asset 任务必须幂等** — 重复执行时先清除旧 chunk
8. **失败处理** — 解析失败更新 parse_status="failed" + 写 error_message 到 Job
9. **API 层 Job 创建不强依赖 Celery** — 如果 Celery 不可用，Job 记录仍创建（status=pending），不阻塞 API
