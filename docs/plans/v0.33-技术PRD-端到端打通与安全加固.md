## 1. 开发管理（总原则）

### 1.1 任务类型定义
本版本是**开发任务**，严格遵循开发任务工作流：
- 先理解再执行（understand first, then execution）
- 最小化改动，不进行无关重构（default to minimal changes）
- 保护现有业务逻辑（protect existing business logic）
- 每个任务形成最小闭环，可独立评审（smallest viable closed loop）

- **验收闭环**: 每任务必须满足"能启动、能运行、能验证、无明显回归"

- **当前分支**: main（master分支）

- 计划（目标、范围、改动文件）

### T-33-03: Ingestion → Pipeline 任务串联

#### 5.3.1 目标
修复ingestion.parse_asset任务在成功完成后，自动触发pipeline.run_pipeline的调用，形成端到端的数据流。

#### 5.3.2 改动范围
- **文件**:
  - ingestion-worker/tasks.py (parse_asset任务)
  - pipeline-worker/tasks.py (如需改动)
  - job_service.py (如需调整send_task逻辑)

#### 5.3.3 新增数据库表
无

#### 5.3.4 已有表变更
可选：Job表新增字段 `next_task_name` (VARCHAR, 下一个要执行的任务名) 和 `next_task_args` (JSON, 下一个任务的参数)，用于记录任务链。但如果不修改Job表，也可通过业务逻辑实现。

#### 5.3.5 API定义
不涉及新API

#### 5.3.6 业务规则
**任务串联流程**:

步骤1: 当 parse_asset 任务在 ingestion-worker 中成功执行时
```
a) 验证asset已解析完毕
b) 更新Job.status = "PARSE_COMPLETED"
c) 查询Project下的所有Asset，获取asset_ids列表
d) 从Job记录中获取project_id、user_id
```

步骤2: 触发下一个任务
```
a) 调用 send_task("pipeline.run_pipeline", args={
     project_id: str,
     job_id: str,
     asset_ids: list[str],
     user_id: str
   })
b) 更新Job.status = "PIPELINE_QUEUED"
c) 记录Job.updated_at = now()
```

步骤3: 错误处理
```
a) 如parse_asset失败，Job.status = "PARSE_FAILED", error_reason记录
b) 不触发run_pipeline
c) 返回错误给API（通过Job.status查询）
```

步骤4: 冥等性保证
```
a) parse_asset被重新执行时，检查Job.status
b) 如已是PARSE_COMPLETED或PIPELINE_QUEUED，则不重复触发run_pipeline
c) 如是PARSE_FAILED，则重新尝试触发
```

**实现方式** (推荐):
- 在 parse_asset 的 success callback 或 task.delay().then() 链中触发
- 或在 parse_asset 主逻辑末尾，成功提交后，同步发送 send_task("pipeline.run_pipeline", ...)

无

#### 5.3.8 不做什么
- 不改变parse_asset或run_pipeline的执行逻辑
- 不修改Asset、Project的数据模型
- 不新增API端点
- 不改变错误处理方式（仍然记录到Job）

#### 5.3.9 验收标准

| 场景 | 输入 | 预期输出 | 验证点 |

    user = db.query(User).filter(User.username == username).first()

    # 步骤2: 选择要验证的哈希值
    hash_to_verify = user.hashed_password if user else DEFAULT_DUMMY_HASH

    # 步骤3: 验证密码（耗时恒定）
    is_valid = verify_password(password, hash_to_verify)

from functools import wraps
def rate_limit(limit: int, window: int = 60):
    def decorator(func):
        @wraps(func)
        async def wrapper(request: Request, *args, **kwargs):
            ip = get_client_ip(request)
            key = f"rate_limit:{request.url.path}:{ip}"
            count = redis.incr(key)
            if count == 1:
                redis.expire(key, window)

            if count > limit:
                raise HTTPException(status_code=429, detail="Rate limit exceeded")
            return await func(request, *args, **kwargs)
        return wrapper
    return decorator

# 使用

@rate_limit(limit=10, window=60)
async def login(...):
    ...

class RateLimitMiddleware(BaseHTTPMiddleware):
    RATE_LIMIT_CONFIG = {
        "/v1/auth/login": (10, 60),
        "/v1/auth/register": (5, 60),
        "/v1/auth/refresh": (30, 60),
    }

    async def dispatch(self, request: Request, call_next):
        # 检查豁免路由
        if any(request.url.path.startswith(p) for p in ["/healthz", "/docs"]):
            return await call_next(request)

        # 检查限流规则
        if request.url.path in self.RATE_LIMIT_CONFIG:
            limit, window = self.RATE_LIMIT_CONFIG[request.url.path]
            ip = get_client_ip(request)
            key = f"rate_limit:{request.url.path}:{ip}"

            count = redis.incr(key)
            if count == 1:
                redis.expire(key, window)

            if count > limit:
                return JSONResponse(status_code=429, content={
                    "error": "rate_limit_exceeded",
                    "message": "Too many requests",
                    "retry_after": window
                })

        response = await call_next(request)
        return response
```

步骤1: 理解问题
```
❌ 错误做法 (ingestion-worker/tasks.py 第112-124行):
try:
    asset = db.query(Asset).filter(...).first()
    asset.status = "parsing"
    db.commit()
    # ... 处理逻辑
except Exception as e:
    session.rollback()  # 回滚事务
    asset = session.query(Asset).filter(...).first()  # ❌ 同一session重查
    # session已回滚，此时查询状态不确定，可能返回旧数据或抛异常

原因:
- session.rollback() 清空了待提交的更改，但不关闭session
- 在同一session上继续查询，可能返回被清除的缓存数据
- 若原始查询对象已被分离，重查可能失败
```

步骤2: 正确的session管理模式
```
a) 使用context manager自动管理lifecycle:
   with Session() as session:
       try:
           asset = session.query(Asset).filter(...).first()
           asset.status = "parsing"
           session.commit()
       except Exception as e:
           session.rollback()
           # 不在此处重查，而是记录错误
           logger.error(f"Failed to update asset: {e}")
           # 如需重查，应新建session
           raise

b) 或显式关闭session:
   session = SessionLocal()
   try:
       ...
       session.commit()
   except Exception as e:
       session.rollback()
       raise
   finally:
       session.close()  # 关键

c) 若需要在错误处理中查询，应新建session:
   except Exception as e:
       session.rollback()
       session.close()  # 关闭旧session
       new_session = SessionLocal()  # 新session
       asset = new_session.query(Asset).filter(...).first()
       new_session.close()
```

@celery_app.task(bind=True)
def parse_asset(self, asset_id: str, job_id: str):
    session = SessionLocal()
    try:
        # 查询asset
        asset = session.query(Asset).filter(Asset.id == asset_id).first()
        if not asset:
            raise ValueError(f"Asset not found: {asset_id}")

        # 更新状态
        asset.status = "parsing"
        session.commit()

        # ... 解析逻辑 ...

        asset.status = "completed"
        session.commit()

        return {"asset_id": asset_id, "status": "success"}

    except Exception as e:
        session.rollback()  # 回滚当前事务
        logger.error(f"Error parsing asset {asset_id}: {e}")

        # 不在此处重查，而是抛出异常
        # Celery会自动重试或标记为FAILED
        raise
    finally:
        session.close()  # 关键：一定要关闭session
```

步骤4: 具体修复（pipeline-worker/tasks.py）
```python
@celery_app.task(bind=True)
def run_pipeline(self, project_id: str, job_id: str, asset_ids: list, user_id: str):
    session = SessionLocal()
    try:
        job = session.query(Job).filter(Job.id == job_id).first()
        job.status = "running"
        session.commit()

        # 执行各个stage
        for stage_name in ["PARSE", "NORMALIZE", "PROPOSE_ARCH", ...]:
            try:
                execute_stage(stage_name, session)
            except Exception as stage_error:
                session.rollback()
                job.status = f"failed_at_{stage_name}"
                session.commit()  # 新的事务记录失败状态
                raise

        job.status = "completed"
        session.commit()
        return {"job_id": job_id, "status": "success"}

    except Exception as e:
        session.rollback()
        logger.error(f"Pipeline failed: {e}")
        raise
    finally:
        session.close()
```
