
```

```

### 关键模式参考
- Celery 任务签名：`@celery_app.task(bind=True, name="orchestrator.xxx")`
- 调度方式：`celery.send_task("orchestrator.xxx", args=[str(uuid), str(uuid)])`
- DB 操作：同步 session，提交后更新 Job 状态
- 幂等性：重跑时先删除旧的 draft 结果
- LLM 调用：`call_llm()` + `parse_json_response()`

## 2. 本轮实施计划

### 目标
在 AI Orchestrator 服务中新增 `generate_docs` Celery 任务，遍历 Architecture 的每个叶子节点，调用 LLM 为其生成知识文档（Markdown），写入 KnowledgeDoc + KnowledgeDocVersion + SourceRef。

### 执行流程
```
1. API: POST /v1/jobs {job_type: "kb_generate", project_id: xxx}
2. job_service: 创建 Job → send_task("orchestrator.generate_docs", [project_id, job_id])
3. AI Orchestrator (generate_docs task):
   a. 加载项目的 published/draft Architecture 及其 ArchitectureNode
   b. 加载项目所有已解析的 AssetChunk
   c. 对每个叶子节点：
      - 根据 node_type 选择对应 Prompt 模板
      - 收集相关 chunk（基于 tags/关键词匹配）
      - 调用 LLM 生成 Markdown 文档
      - 解析响应，写入 KnowledgeDoc + KnowledgeDocVersion
      - 记录 SourceRef（哪些 chunk 被引用）
   d. 更新 Job → completed
4. 用户通过 GET /v1/docs?project_id=xxx 查看生成的文档
```

### 分步任务
1. **新增 Prompt 模板** — `orchestrator/prompts.py` 添加 `build_generate_doc_prompt()`
2. **新增 Celery 任务** — `orchestrator/tasks.py` 添加 `generate_docs()`
3. **API 调度集成** — `job_service.py` 添加 `kb_generate` 类型的 Celery 调度
4. **Celery app 配置** — 确认 `celery_app.py` 的 `include` 已覆盖新任务（现有 tasks.py 内新增即可）
5. **补充测试** — prompt 构建测试 + 任务逻辑测试
6. **跑全量回归** — 确保 87 个已有测试仍通过

## 4. 实现约束

1. **严格复用现有模式** — 参照 `propose_architecture` 的 Celery 任务结构、DB 操作、错误处理
2. **不修改已有代码逻辑** — 只在 `job_service.py` 的调度分支中新增 `elif`，不改动已有 `ingest` 和 `architecture_draft` 分支
3. **幂等性** — `generate_docs` 重跑时先删除该项目下所有 `status=draft` 的 KnowledgeDoc 及其 Version/SourceRef
4. **Prompt 安全** — 遵循 doc 12 约束：不指示模型忽略来源，不诱导编造事实，输出包含推理摘要
5. **文档类型** — 本阶段仅生成 `topic` 和 `document` 类型，其他类型（glossary、conflict、index）留待后续
6. **LLM 调用** — 复用 `llm_client.call_llm()` 和 `parse_json_response()`，不引入新依赖
7. **不新建服务** — 在现有 ai-orchestrator 服务内新增任务，不创建新的微服务
