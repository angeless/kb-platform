# v0.8.0 增量接入 API — 实施计划

## 1. 当前代码现状理解

### 已有能力
- 资料上传 → 解析 → 生成架构 → 生成文档 闭环已通
- `job_service.py` 支持 `ingest`、`architecture_draft`、`kb_generate` 三种 Job 类型
- `JobSchema` 已定义 `review_publish` job_type，但 `incremental` 未定义
- AI Orchestrator 有 `generate_docs` 任务可参考
- ConflictRecord 模型和 API 已存在（list/get/resolve）
- KnowledgeDocVersion 支持多版本（追加不覆盖）

### 缺失环节
- 没有 `POST /v1/ingestion/incremental` 端点
- 没有增量判断逻辑（新增/补充/修正/冲突）
- `job.py` schema 中 job_type 正则不包含 `incremental`
- AI Orchestrator 没有 `classify_incremental` 任务

### PRD 要求（doc 02, section 4）
新材料进入后判断与旧知识的关系：
- **新增**：知识库中没有对应主题 → 新建节点+文档
- **补充**：已有主题但缺少细节 → 在原节点下生成新版本
- **修正**：新资料证明旧知识过期 → 生成修正版
- **冲突**：新旧材料互相矛盾 → 进入冲突池

## 2. 本轮实施计划

### 目标
实现 `POST /v1/ingestion/incremental` 端点 + AI Orchestrator 的 `classify_incremental` 任务，完成增量资料分类和处理。

### 执行流程
```
1. API: POST /v1/ingestion/incremental { project_id, asset_ids }
2. job_service: 创建 Job(type=incremental) → send_task("orchestrator.classify_incremental")
3. AI Orchestrator (classify_incremental task):
   a. 加载新资料的 AssetChunk（指定 asset_ids）
   b. 加载项目已有的 KnowledgeDoc + 最新版本摘要
   c. 对每个新 chunk 组，调用 LLM 判断关系类型
   d. 按类型处理：
      - 新增 → 创建新 KnowledgeDoc + Version
      - 补充 → 给已有 Doc 追加新 Version
      - 修正 → 给已有 Doc 追加修正 Version（标记 change_reason）
      - 冲突 → 创建 ConflictRecord
   e. 更新 Job → completed
4. 用户通过 GET /v1/docs 和 GET /v1/conflicts 查看结果
```

### 分步任务
1. 更新 job schema — 添加 `incremental` 到 job_type 枚举
2. 新增增量接入 schema — IncrementalRequest
3. 新增 API 端点 — `POST /v1/ingestion/incremental`
4. 新增 Prompt 模板 — `build_classify_prompt()`
5. 新增 Celery 任务 — `classify_incremental()`
6. API 调度集成 — job_service 新增 `incremental` 分支
7. 补测试

## 4. 实现约束

1. **复用现有 Celery 任务模式** — 参照 generate_docs 结构
2. **不修改已有逻辑** — 只新增代码
3. **幂等性** — 同一批 asset 重跑不产生重复文档
4. **Prompt 安全** — 遵循 doc 12 约束
5. **版本追加不覆盖** — 补充/修正创建新 Version，不改旧 Version
6. **冲突不强行合并** — 矛盾时创建 ConflictRecord，不自动解决
