## 一、当前代码现状理解

### 迁移链（4 个文件）
1. `df611e31f58f_initial_schema.py` — 创建 15 张表（audit_log, tenant, model_provider, project, user, architecture, asset, job, model_route, architecture_node, asset_chunk, conflict_record, knowledge_doc, knowledge_doc_version, source_ref）
2. `a1b2c3d4e5f6_add_pgvector_extension.py` — `CREATE EXTENSION IF NOT EXISTS vector`
3. `b2c3d4e5f6a7_add_embedding_vec_column.py` — `ALTER TABLE doc_embedding ADD COLUMN IF NOT EXISTS embedding_vec vector(1536)` + 数据回填
4. `c3d4e5f6a7b8_add_search_vector_gin_index.py` — knowledge_doc/knowledge_doc_version 添加 tsvector 列和 GIN 索引

### 问题
- `doc_embedding` 表在 ORM 模型中定义（`packages/shared-models/shared_models/embedding.py`），但**从未在任何迁移脚本中创建**
- 第 3 步 `b2c3d4e5f6a7` 直接对 `doc_embedding` 表执行 ALTER TABLE，假设表已存在
- 结果：在全新数据库上执行 `alembic upgrade head` 会在第 3 步失败（表不存在）
- 在开发环境中可能不触发（如果表是通过 `Base.metadata.create_all()` 或其他方式手动创建的）

### ORM 模型定义（DocEmbedding）
- **表名**: `doc_embedding`
- **继承 Base**: 自动获得 `id`(UUID PK), `created_at`(TIMESTAMPTZ), `updated_at`(TIMESTAMPTZ)
- **自有字段**:
  - `doc_id`: UUID, FK → knowledge_doc.id (ON DELETE CASCADE), UNIQUE, NOT NULL
  - `project_id`: UUID, FK → project.id, NOT NULL
  - `version`: INTEGER, NOT NULL
  - `embedding`: JSONB, NOT NULL
  - `embedding_vec`: VECTOR(1536), NULLABLE（pgvector 可选）
  - `model_name`: VARCHAR(100), NOT NULL
  - `dimensions`: INTEGER, NOT NULL
- **索引**: `ix_doc_embedding_project` on (project_id)

## 二、本轮实施计划

### 修改策略
在迁移 `b2c3d4e5f6a7` 的 `upgrade()` 函数**开头**，添加 `CREATE TABLE IF NOT EXISTS doc_embedding(...)` 语句。这样：
1. 全新数据库：先创建表，再添加 embedding_vec 列 → 成功
2. 已有数据库（表已存在）：`IF NOT EXISTS` 跳过 → 不影响现有数据

### 不修改的部分
- 不修改其他 3 个迁移文件
- 不修改 ORM 模型
- 不新增迁移文件（在现有迁移中修复，保持链完整）
- 不修改任何业务代码

## 四、实现约束

1. 表结构必须与 `DocEmbedding` ORM 定义完全一致
2. 使用 `IF NOT EXISTS` 保证幂等性
3. 必须包含外键约束（doc_id → knowledge_doc.id ON DELETE CASCADE, project_id → project.id）
4. 必须创建索引 `ix_doc_embedding_project`
5. downgrade() 中 DROP TABLE 在 DROP COLUMN 之后执行（或者先 DROP TABLE 就包含了列删除）
6. 不破坏已有数据库的迁移状态
