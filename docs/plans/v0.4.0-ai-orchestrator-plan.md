# V0.4.0 实施计划：AI Orchestrator — 初版架构生成

## 当前代码现状理解

### 已有能力
- **Architecture 模型**：含 project_id, name, version, status, levels_json, nodes 关系
- **ArchitectureNode 模型**：含 architecture_id, parent_id, node_name, node_type, level, accept_types 等
- **Architecture API**：list/get/publish/create_node/update_node 已完成
- **AssetChunk 模型 + 写入**：ingestion-worker 的 parse_asset 已可将文本解析为 chunk
- **Job API**：支持创建 architecture_draft 类型 Job
- **Celery 基础设施**：ingestion-worker 已建立 Celery 模式
- **settings**：含 OPENAI_API_KEY 等模型配置（.env.example）

### 差距
- 无 `services/ai-orchestrator/` 目录
- 无大模型调用封装
- 无 `propose_architecture` 任务
- Job 创建 architecture_draft 时不下发 Celery 任务
- 设计文档中 ai-orchestrator 被定义为独立服务

## 本轮实施计划

### 目标
搭建 ai-orchestrator 服务，实现 propose_architecture Celery 任务。读取项目下所有已解析的 AssetChunk → 构造 Prompt → 调用大模型 → 解析返回的 JSON → 写入 Architecture + ArchitectureNode → 更新 Job 状态。

### 分步方案

**Step 1**: 创建 ai-orchestrator 服务骨架（Celery app + pyproject.toml）

**Step 2**: 实现大模型调用封装 `orchestrator/llm_client.py` — 封装 OpenAI-compatible API 调用，从 model_provider / model_route 读配置，或 fallback 到环境变量

**Step 3**: 实现 `propose_architecture` 任务 — 收集 chunk → 构造 prompt → 调用 LLM → 解析 JSON 输出 → 写入 Architecture + ArchitectureNode

**Step 4**: 修改 API job_service — architecture_draft Job 下发 Celery 任务

**Step 5**: 补测试 + 回归

## 实现约束

1. **不破坏已有 77 个测试**
2. **不修改 shared-models** — Architecture/ArchitectureNode 模型已满足需求
3. **LLM 调用通过 httpx 直接请求 OpenAI-compatible API**（不引入 openai SDK，减少依赖）
4. **Prompt 输出必须为结构化 JSON**，含 architecture_name, industry, levels, nodes
5. **propose_architecture 任务必须幂等** — 重复执行清除旧 draft 架构
6. **LLM 不可用时任务失败** — 不做 fallback，直接标记 Job failed
7. **Prompt 不诱导模型填补缺失事实**（文档 12 约束 4）
8. **API job_service 改动最小化** — 仅在 create 方法中增加 architecture_draft 分支
