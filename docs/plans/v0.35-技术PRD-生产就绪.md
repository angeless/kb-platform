## 第1章 概述

### 1.1 版本定位

v0.35 是生产就绪阶段的核心版本。在 v0.34 完成功能验证和质量改进的基础上，v0.35 聚焦于：

1. **API 版本化完善** - 确保一致的路由前缀 `/api/v1/`
2. **CORS 跨域策略** - 支持多源部署和前端集成
3. **深度健康检查** - 完整的依赖项连通性诊断
4. **结构化日志** - JSON 格式日志便于日志聚合和分析
5. **Prometheus 指标暴露** - 完整的应用性能和业务指标
6. **Grafana 监控仪表盘** - 开箱即用的可视化监控
7. **CI/CD 流水线** - GitHub Actions 自动化测试和构建
8. **优雅停机处理** - 确保副作用一致性和数据完整性
9. **OpenAPI 规范完善** - 详细的 API 文档和错误定义
10. **运维文档** - 部署、升级、故障排查完整指南

### 1.2 成功指标

| 指标 | 目标值 | 检验方式 |
|------|--------|---------|
| API 文档覆盖率 | 100% | OpenAPI spec 所有端点均有描述、示例、错误响应 |
| 健康检查覆盖度 | ≥3 项 | PostgreSQL、Redis、MinIO 连通性检查 |
| Prometheus 指标数 | ≥10 | http_requests_total、duration_seconds 等核心指标 |
| CI/CD 流水线覆盖 | PR + Build | GitHub Actions 自动运行单元测试和集成测试 |
| 日志结构化率 | 100% | 所有应用日志为 JSON 格式 |
| 优雅停机超时 | ≤30s | Uvicorn 和 Celery 都在规定时间内完成清理 |

### 1.3 约束与假设

- 现有 API 前缀为 `/v1/`，已在 v0.32+ 部署
- FastAPI 框架原生支持 CORS Middleware、OpenAPI 生成
- PostgreSQL 13+、Redis 6+、MinIO latest 作为标准依赖
- Docker Compose 用于本地开发，支持扩展配置（`docker-compose.monitoring.yml`）
- GitHub 作为主要代码托管和 CI/CD 平台
- 日志输出到 stdout（便于 Docker 日志收集）

## 第2章 现状分析与差距

### 2.1 现状清单

| 项目 | 现状 | 影响 |
|------|------|------|
| API 路由前缀 | `/v1/` 已存在 | 部分旧端点可能还在根路径，需清理 |
| CORS 中间件 | 未配置 | 前端跨域请求被拒绝 |
| 健康检查 | 仅有 `/healthz` 和 `/readyz`（基础 DB 检查） | 无法诊断 Redis、MinIO、网络问题 |
| 日志输出 | Python stdlib logging，纯文本 | 难以聚合、搜索、分析 |
| 性能指标 | 无 Prometheus 端点 | 无法监控应用性能和业务 KPI |
| 监控仪表盘 | 无 Grafana 配置 | 运维人员无法可视化监控 |
| CI/CD | 无自动化流水线 | 每次发布需手工测试、构建 |
| 优雅停机 | Uvicorn 默认 60s 超时 | 在高并发下可能导致请求丢失 |
| OpenAPI 文档 | 自动生成，但缺少详细描述和错误响应 | API 消费者难以理解端点行为 |
| 运维文档 | 缺失 | 新入职运维人员无法快速上手 |

3. 没有可观测性基础设施 → 需部署 Prometheus + Grafana
4. 部署流程全手工 → 需自动化

## 第3章 需求分析

### 3.1 功能需求

#### 3.1.1 API 路由版本化 (T-35-01)

**FR-35-01-A**: `/api/v1/` 前缀一致性
- 所有业务端点必须使用 `/api/v1/` 前缀
- 旧的根路径端点（如 `/knowledge/list`）需重定向到 `/api/v1/knowledge/list`
- 旧前缀的请求返回 301 Moved Permanently，`Location: /api/v1/<path>`

**FR-35-01-B**: 版本协议端点
- `GET /api/versions` → 返回支持的 API 版本列表
  ```json
  {
    "versions": [
      {"version": "v1", "status": "active", "deprecation_date": null}
    ]
  }
  ```

#### 3.1.2 CORS 策略 (T-35-02)

**FR-35-02-A**: FastAPI CORS Middleware
- 集成 `fastapi.middleware.cors.CORSMiddleware`
- 通过环境变量 `CORS_ORIGINS` 配置允许的源，格式：逗号分隔
  - 示例: `CORS_ORIGINS=http://localhost:3000,https://app.example.com`
  - 默认值：`http://localhost:3000,http://localhost:3001` (开发环境)
  - 生产环境需显式配置

**FR-35-02-B**: CORS 参数
- `allow_origins`: 从 `CORS_ORIGINS` 环境变量解析
- `allow_credentials`: `True`
- `allow_methods`: `["GET", "POST", "PUT", "DELETE", "PATCH", "OPTIONS"]`
- `allow_headers`: `["*"]`

#### 3.1.3 深度健康检查 (T-35-03)

**FR-35-03-A**: GET /api/health/ready 端点
- 路径：`GET /api/health/ready`
- 认证：不需要（用于负载均衡器探测）
- 响应格式：
  ```json
  {
    "status": "ok" | "degraded" | "unhealthy",
    "version": "0.35.0",
    "checks": {
      "postgres": {
        "status": "ok" | "error",
        "latency_ms": 5,
        "message": "Connected"
      },
      "redis": {
        "status": "ok" | "error",
        "latency_ms": 2,
        "message": "PING successful"
      },
      "minio": {
        "status": "ok" | "error",
        "latency_ms": 8,
        "message": "Health check passed"
      }
    }
  }
  ```

**FR-35-03-B**: 健康状态规则
- `status = "ok"`: 所有检查都通过
- `status = "degraded"`: 至少一项检查超时或返回警告（但不影响核心功能）
- `status = "unhealthy"`: PostgreSQL 检查失败（无法工作）
- HTTP 响应：
  - `status = "ok"` → 200
  - `status = "degraded"` → 200（但在 readiness probe 中可视为可接受）
  - `status = "unhealthy"` → 503

**FR-35-03-C**: 检查超时和重试
- 每项检查超时时间：1000ms
- 如果超时，该项标记为 "error"，消息为 "Timeout"
- 不重试（单次探测）

#### 3.1.4 结构化日志 (T-35-04)

**FR-35-04-A**: 日志格式转换
- 所有应用日志输出为 JSON 格式
- 使用 `python-json-logger` 或 `structlog` 库
- JSON 字段：
  - `timestamp`: ISO 8601 格式
  - `level`: DEBUG, INFO, WARNING, ERROR, CRITICAL
  - `logger`: 模块名
  - `message`: 日志消息
  - `request_id`: 关联请求（若在 HTTP 上下文）
  - `user_id`: 用户 ID（若已认证）
  - `duration_ms`: 操作耗时（若适用）
  - `error`: 错误堆栈（仅 ERROR 及以上）

**FR-35-04-B**: 日志级别规范
- `INFO`: 应用启动、重要业务事件（新建文档、发送消息）
- `WARNING`: 非致命错误、重试、降级（缓存未命中）
- `ERROR`: 异常捕获、操作失败（数据库连接失败）
- `DEBUG`: 开发调试信息（环境变量加载）

#### 3.1.5 Prometheus 指标暴露 (T-35-05)

**FR-35-05-A**: GET /metrics 端点
- 路径：`GET /metrics`
- 认证：不需要（用于 Prometheus scrape）
- 格式：Prometheus text format (application/openmetrics-text; version=1.0.0)
- 无分页，返回所有指标

**FR-35-05-B**: 核心指标集合
- `http_requests_total{method,path,status}`: 请求总数（Counter）
- `http_request_duration_seconds{method,path}`: 请求耗时分布（Histogram，buckets: 0.01, 0.05, 0.1, 0.5, 1.0）
- `http_request_size_bytes{method,path}`: 请求体大小（Histogram）
- `http_response_size_bytes{method,path}`: 响应体大小（Histogram）
- `database_query_duration_seconds{operation,table}`: 数据库查询耗时（Histogram）
- `database_connections_active`: 活跃连接数（Gauge）
- `redis_commands_total{command,status}`: Redis 命令总数（Counter）
- `redis_command_duration_seconds{command}`: Redis 命令耗时（Histogram）
- `cache_hits_total{cache_name}`: 缓存命中总数（Counter）
- `cache_misses_total{cache_name}`: 缓存未命中总数（Counter）

**FR-35-05-C**: 指标采集机制
- 集成 `prometheus-client` 库
- 使用 middleware 拦截 HTTP 请求/响应，自动记录指标
- 在数据库操作前后记录耗时
- 在 Redis 操作前后记录耗时

#### 3.1.6 Grafana 仪表盘 (T-35-06)

**FR-35-06-A**: 监控基础设施
- 部署 Prometheus + Grafana，配置文件：`docker-compose.monitoring.yml`
- Prometheus 配置：`monitoring/prometheus.yml`
  - Scrape interval: 15s
  - Evaluation interval: 15s
  - Scrape targets: `http://api:8000/metrics`
- Grafana 配置：`monitoring/grafana/provisioning/dashboards/`
  - 自动加载仪表盘 JSON 文件

**FR-35-06-B**: 预配置仪表盘（至少 3 个）
1. **应用性能仪表盘** (Application Performance)
   - 请求速率 (req/s)
   - 平均响应时间 (ms)
   - 错误率 (%)
   - P95/P99 响应时间

2. **资源使用仪表盘** (Resource Utilization)
   - 数据库连接使用率
   - Redis 内存使用
   - HTTP 请求大小分布
   - 响应大小分布

3. **业务指标仪表盘** (Business Metrics)
   - 文档创建/修改/删除速率
   - 用户活跃度
   - 缓存命中率
   - Redis 命令分布

#### 3.1.7 CI/CD 流水线 (T-35-07)

**FR-35-07-A**: GitHub Actions 工作流文件
- `.github/workflows/ci.yml`: PR 验证流水线
  - 触发：PR 创建/更新、push to main
  - 步骤：
    1. Checkout 代码
    2. 设置 Python 环境
    3. 安装依赖
    4. 运行 linting (pylint, black)
    5. 运行单元测试 (pytest)
    6. 运行集成测试（可选，若有）

- `.github/workflows/build.yml`: 构建并发布镜像流水线
  - 触发：tag push (v0.35.0 格式)
  - 步骤：
    1. Checkout 代码
    2. 运行 ci.yml 测试
    3. 构建 Docker 镜像 (api, worker)
    4. 登录 Docker 仓库（GitHub Container Registry 或 Docker Hub）
    5. 推送镜像，tag: latest 和 version tag

**FR-35-07-B**: 测试覆盖率要求
- 单元测试覆盖率 ≥70%
- 关键业务路径必须有集成测试
- 所有端点必须有功能测试

#### 3.1.8 优雅停机处理 (T-35-08)

**FR-35-08-A**: Uvicorn 优雅关闭
- 配置 Uvicorn 的 `--timeout-graceful-shutdown` 参数，值：30 秒
- 收到 SIGTERM 后，拒绝新请求，等待现有请求完成，30s 超时后强制关闭
- 在关闭前，确保数据库连接池闭合、缓存刷新

**FR-35-08-B**: Celery Worker 优雅关闭
- 配置 `time_limit` 和 `soft_time_limit` 参数
  - `soft_time_limit`: 25s（task 收到 SigTerm 信号，有机会清理）
  - `time_limit`: 30s（强制杀死）
- 在 Docker Compose 中，为 worker 服务配置 `stop_grace_period: 35s`
- Task 执行前保存检查点，异常关闭时能从检查点恢复

**FR-35-08-C**: 应用关闭 Hook
- FastAPI 应用注册 `shutdown` 事件处理
  - 关闭数据库连接池
  - 关闭 Redis 连接
  - 刷新待处理的日志缓冲

#### 3.1.9 OpenAPI 规范完善 (T-35-09)

**FR-35-09-A**: 端点文档标准化
- 每个端点必须包含：
  - `summary`: 一句话总结
  - `description`: 详细描述
  - `tags`: 分类标签（e.g., "documents", "users", "health")
  - `parameters`: 明确所有查询参数、路径参数、请求头
  - `requestBody`: 请求体 schema，包含示例
  - `responses`: 所有可能的响应（2xx, 4xx, 5xx）
    - 200: 成功响应，包含 schema 和示例
    - 400: Bad Request（参数错误）
    - 401: Unauthorized
    - 403: Forbidden
    - 404: Not Found
    - 409: Conflict（业务冲突）
    - 500: Internal Server Error

**FR-35-09-B**: Error Response Schema
- 统一的错误响应格式：
  ```json
  {
    "error_code": "DOCUMENT_NOT_FOUND",
    "message": "文档不存在",
    "detail": "Document ID: 12345",
    "timestamp": "2026-03-19T10:30:00Z"
  }
  ```

**FR-35-09-C**: 安全schemes定义
- 所有 API 在 OpenAPI 中声明所需的安全方案（Basic, Bearer Token, API Key）
- 在不需要认证的端点上明确标注 `security: []`

## 第4章 架构与设计

### 4.1 整体架构

v0.35 在 v0.34 的基础上添加以下组件：

```
┌─────────────────────────────────────────────────────┐
│                  FastAPI 应用 (v0.35)               │
├─────────────────────────────────────────────────────┤
│  路由层                                              │
│  ├─ /api/v1/* (业务端点)                            │
│  ├─ /api/health/* (健康检查)                        │
│  └─ /metrics (Prometheus)                          │
├─────────────────────────────────────────────────────┤
│  中间件栈                                            │
│  ├─ CORSMiddleware                                 │
│  ├─ 日志中间件 (JSON 输出)                          │
│  ├─ 指标中间件 (Prometheus 采集)                     │
│  └─ RequestID 中间件                               │
├─────────────────────────────────────────────────────┤
│  业务逻辑层 (不变，v0.34 继承)                      │
│  ├─ 认证/授权 (JWT)                                │
│  ├─ 知识库 CRUD                                    │
│  ├─ 全文搜索                                       │
│  └─ 协作功能                                       │
├─────────────────────────────────────────────────────┤
│  数据访问层 (不变)                                 │
│  ├─ PostgreSQL (ORM)                               │
│  ├─ Redis (缓存)                                   │
│  └─ MinIO (文件存储)                               │
└─────────────────────────────────────────────────────┘
     ↓ SIGTERM
┌─────────────────────────────────────────────────────┐
│            优雅停机流程 (Graceful Shutdown)         │
│  1. 停止接受新请求                                 │
│  2. 等待现有请求完成 (timeout: 30s)               │
│  3. 关闭数据库连接池                               │
│  4. 关闭 Redis 连接                                │
│  5. 刷新日志缓冲                                   │
│  6. 进程退出                                       │
└─────────────────────────────────────────────────────┘
```

### 4.2 模块设计

#### 4.2.1 日志模块 (logging_module)

- **职责**: 初始化 JSON 日志配置，提供结构化日志 API
- **输入**: 应用配置（日志级别、环境）
- **输出**: JSON 格式日志到 stdout
- **关键类**:
  - `JSONLogFormatter`: 将 Python logging Record 转换为 JSON
  - `LogContextManager`: 管理请求级别的上下文（request_id, user_id）
- **依赖**: `python-json-logger` 或 `structlog`

#### 4.2.2 健康检查模块 (health_check_module)

- **职责**: 实现各项连通性检查，聚合健康状态
- **输入**: 依赖项配置（PG, Redis, MinIO）
- **输出**: 健康检查响应对象
- **关键函数**:
  - `check_postgres()`: 执行 SELECT 1 查询，返回 {status, latency_ms, message}
  - `check_redis()`: 执行 PING 命令，返回 {status, latency_ms, message}
  - `check_minio()`: 执行 bucket listing，返回 {status, latency_ms, message}
  - `aggregate_health()`: 合并所有检查结果，返回整体状态
- **依赖**: psycopg2, redis, minio 客户端

#### 4.2.3 指标采集模块 (metrics_module)

- **职责**: 初始化 Prometheus 指标对象，提供采集接口
- **输入**: 应用启动信号
- **输出**: Prometheus 格式的指标文本
- **关键指标类**:
  - `http_requests_total`: Counter
  - `http_request_duration_seconds`: Histogram
  - `database_query_duration_seconds`: Histogram
  - `redis_commands_total`: Counter

### 5.2 CORS 业务逻辑

**T-35-02 逻辑流程**

```
启动时:
  1. 从环境变量 CORS_ORIGINS 读取允许源列表（逗号分隔）
  2. 解析为 list，如：["http://localhost:3000", "https://app.example.com"]
  3. 将 FastAPI CORSMiddleware 添加到应用，传入解析后的源列表
  4. 配置 allow_methods, allow_headers 等参数

请求时:
  1. 浏览器发送 Origin 头
  2. 中间件检查 Origin 是否在允许列表中
  3. 如果允许，响应头添加 Access-Control-Allow-Origin
  4. 如果不允许，浏览器阻止响应（不返回错误，仅拦截 JS 访问）

错误处理:
  - 如果 CORS_ORIGINS 未设置 → 使用默认值（开发环境源）
  - 如果 CORS_ORIGINS 格式错误 → 启动时报错，不启动服务
```

### 5.3 深度健康检查业务逻辑

**T-35-03 逻辑流程**

```
输入: GET /api/health/ready 请求
输出: 健康检查响应

步骤:
  1. 初始化结果对象: checks = {}, overall_status = "ok"
  2. 并发执行三项检查（或顺序执行，若并发有问题）:
     a. check_postgres():
        - 记录开始时间
        - 执行 SELECT 1 查询，超时 1s
        - 记录耗时
        - 返回 {status: "ok"/"error", latency_ms: int, message: str}
     b. check_redis():
        - 记录开始时间
        - 执行 PING 命令，超时 1s
        - 记录耗时
        - 返回 {status: "ok"/"error", latency_ms: int, message: str}
     c. check_minio():
        - 记录开始时间
        - 执行 bucket listing 或 health check，超时 1s
        - 记录耗时
        - 返回 {status: "ok"/"error", latency_ms: int, message: str}
  3. 聚合检查结果:
     a. 如果 postgres.status = "error" → overall_status = "unhealthy"
     b. 如果 (redis.status = "error" ∨ minio.status = "error") ∧ postgres.status = "ok" → overall_status = "degraded"
     c. 否则 → overall_status = "ok"
  4. 构造响应:
     {
       "status": overall_status,
       "version": app.version,
       "checks": {
         "postgres": checks.postgres,
         "redis": checks.redis,
         "minio": checks.minio
       }
     }
  5. 根据状态返回 HTTP 码:
     - overall_status ∈ {"ok", "degraded"} → 200
     - overall_status = "unhealthy" → 503

错误处理:
  - 如果任何检查超时（>1000ms） → 该项 status = "error", message = "Timeout"
  - 如果连接异常（ ConnectionError 等） → status = "error", message = 异常信息
  - 不重试，快速失败
```

### 5.4 结构化日志业务逻辑

**T-35-04 逻辑流程**

```
初始化 (应用启动):
  1. 配置 Python logging，使用 JSONFormatter
  2. 所有处理器（StreamHandler）使用 JSONFormatter
  3. 设置日志级别（环境变量 LOG_LEVEL，默认 INFO）

每次日志记录:
  输入: logger.info("message", extra={key: value})
  处理:
    1. JSONFormatter 拦截 LogRecord
    2. 提取标准字段: timestamp, level, logger_name, message
    3. 提取 extra 字段: request_id, user_id, duration_ms 等
    4. 格式化为 JSON: {"timestamp": "...", "level": "...", ...}
    5. 写入 stdout

日志上下文管理:
  - 在 HTTP 中间件中，为每个请求分配唯一 request_id
  - 使用 contextvars 或 threading.local 存储 request_id, user_id
  - 所有在该请求上下文中的日志自动注入这些字段

示例日志输出:
  {"timestamp": "2026-03-19T10:30:45.123Z", "level": "INFO", "logger": "app.services.document", "message": "Document created", "request_id": "req-12345", "user_id": "user-99", "duration_ms": 123}
  {"timestamp": "2026-03-19T10:30:46.456Z", "level": "ERROR", "logger": "app.services.database", "message": "Query failed", "error": "Traceback...", "request_id": "req-12346"}
```

### 5.5 Prometheus 指标采集业务逻辑

**T-35-05 逻辑流程**

```
初始化 (应用启动):
  1. 创建 Prometheus 指标对象
     - http_requests_total = Counter(...)
     - http_request_duration_seconds = Histogram(..., buckets=[0.01, 0.05, 0.1, 0.5, 1.0])
     - 等等（共 10+ 个指标）
  2. 注册到默认的 Prometheus Registry
  3. 挂载中间件以拦截 HTTP 请求/响应

每个 HTTP 请求:
  1. 在中间件 process_request 中:
     - 记录请求开始时间
     - 记录请求大小（body 字节数）
  2. 在业务逻辑执行中:
     - 数据库操作前后记录耗时
     - Redis 操作前后记录耗时
  3. 在中间件 process_response 中:
     - 计算响应耗时
     - 调用 http_requests_total.labels(method=..., path=..., status=...).inc()
     - 调用 http_request_duration_seconds.labels(method=..., path=...).observe(耗时)
     - 调用 http_response_size_bytes.labels(...).observe(响应大小)

GET /metrics 请求:
  1. 触发 Prometheus 暴露端点（由 prometheus-client 库提供）
  2. 遍历默认 Registry 中所有已注册的指标
  3. 按 Prometheus text format 输出
  4. 格式示例:
     # HELP http_requests_total Total HTTP requests
     # TYPE http_requests_total counter
     http_requests_total{method="GET",path="/api/v1/documents",status="200"} 1523
     ...

缓存指标计算:
  - 在缓存 get/set 操作中，调用对应指标：
    - cache_hits_total.labels(cache_name=...).inc()  (hit)
    - cache_misses_total.labels(cache_name=...).inc() (miss)
```

### 5.6 优雅停机业务逻辑

**T-35-08 逻辑流程**

```
正常运行中:
  Uvicorn 监听 SIGTERM 和 SIGINT 信号

收到 SIGTERM:
  1. Uvicorn 主进程收到信号
  2. 立即停止接受新连接（关闭服务端套接字）
  3. 已接收但未处理的请求继续处理（等待完成）
  4. 设置 30 秒倒计时
  5. 定期检查是否还有待处理请求
  6. 如果所有请求完成或 30 秒超时：
     a. 调用应用 shutdown 事件处理
     b. 关闭数据库连接池（调用 pool.close()）
     c. 关闭 Redis 连接（调用 redis.close()）
     d. 刷新日志缓冲（调用 logging.shutdown()）
     e. 进程退出（exit(0))
  7. 如果 30 秒后仍有请求未完成：
     a. 强制关闭，进程异常退出（exit(1))
     b. 未完成的请求被中断

Celery Worker 优雅停机:
  1. Worker 收到 SIGTERM
  2. 不再接受新 Task
  3. 已启动的 Task 继续执行，soft_time_limit = 25s
  4. Task 在 25s 时收到 SigTerm，有 5s 清理时间
  5. 如果 Task 未在 30s 内完成，被强制杀死
  6. Docker stop_grace_period = 35s，留余量

验证优雅停机:
  - 在高负载下发送 SIGTERM，检查 access.log 中未出现中断的请求
  - 检查日志中无 "Forced shutdown" 错误
```

## 第9章 风险评估与缓解

### 9.1 技术风险

| 风险 | 可能性 | 影响 | 缓解措施 |
|------|--------|------|---------|
| JSON 日志格式化性能开销 | 中 | 应用 CPU 增加 5-10% | 使用异步日志处理，缓冲输出 |
| Prometheus 指标采集导致 GC 压力 | 低 | 内存占用增加 | 定期清理旧指标，设置合理的保留期 |
| CORS 配置错误导致跨域失败 | 中 | 前端无法调用 API | 提供详细的环境变量配置文档和示例 |
| 优雅停机超时不足导致请求丢失 | 低 | 用户请求失败 | 设置充足的超时时间（30s），并在 Docker 中配置 stop_grace_period |
| CI/CD 流水线测试覆盖不足 | 中 | 发布后出现回归 | 要求覆盖率 ≥70%，强制门禁 |
| 监控数据延迟导致无法及时告警 | 低 | 无法快速响应 | 设置合理的采集间隔（15s）和告警阈值 |

### 9.2 运维风险

| 风险 | 可能性 | 影响 | 缓解措施 |
|------|--------|------|---------|
| 新运维人员不了解系统 | 中 | 部署/故障排查效率低 | 提供完整的 runbook 和视频教程 |
| 监控系统故障 | 低 | 无法监控应用 | 独立部署 Prometheus + Grafana，定期备份配置 |
| 镜像推送失败导致 CI/CD 卡住 | 低 | 发布流程中断 | 设置 GitHub Actions 的重试机制，提供手工推送指南 |

### 9.3 业务风险

| 风险 | 可能性 | 影响 | 缓解措施 |
|------|--------|------|---------|
| API 版本化不清晰导致客户端混乱 | 低 | 集成问题增加 | 提供迁移指南，标记旧路径为 deprecated |
| 优雅停机耗时过长导致部署延缓 | 低 | 上线周期延长 | 监控关闭流程，设置合理的 timeout |

## 第13章 后续路线图与建议

### 13.1 v0.35 完成后的优化方向

**P1 (紧急，下个版本)**:
1. 告警系统集成 - Grafana 告警规则和通知（Slack、Email）
2. 日志聚合系统 - ELK Stack 或 Loki，便于大规模日志查询

4. SLA 监控 - 针对关键业务指标的 SLO 定义和监控

**P2 (重要，1-2 个月)**:
1. 自动扩缩容 - 基于 Prometheus 指标的 HPA (Kubernetes)
2. 蓝绿部署 - 无停机部署流程（需 Kubernetes）
3. 数据库查询性能分析 - 慢查询日志、查询计划分析
4. 成本优化 - 资源使用分析和优化建议

**P3 (可选，3+ 个月)**:
1. 多区域部署 - 高可用和灾难恢复
2. API 限流和速率限制 - 保护系统稳定性
3. 灰度发布 - 基于用户分组的金丝雀部署
4. 自动化性能测试 - CI/CD 中的性能基准检查

### 13.2 架构演进建议

**短期 (3 个月内)**:
- 当前架构已支持容器化部署，建议尽快迁移到 Kubernetes
- 分离 API 和 Worker，独立扩展
- 引入消息队列（如 RabbitMQ）支持异步任务

**中期 (6-12 个月)**:
- 微服务架构演进：按功能域拆分（知识库服务、用户服务、协作服务等）
- 事件驱动架构：采用 CQRS 模式支持复杂的业务流程
- 多租户支持：租户隔离、计费、资源配额管理

**长期 (12+ 个月)**:
- 服务网格（Istio）：统一的流量管理、安全、可观测性
- 成本优化：基于动态定价的资源调度
- 全球部署：跨地域的数据同步和一致性保证

## 附录 B: 故障排查快速参考

### 健康检查失败

```bash
# 查看详细健康状态
curl -s http://localhost:8000/api/health/ready | jq .

# 检查各依赖连接
# PostgreSQL
psql -h postgres -U user -d knowledge_db -c "SELECT 1"

# Redis
redis-cli -h redis PING

# MinIO
curl -s http://minio:9000/minio/health/live

# 查看日志
docker logs <api-container-id>
```

### Prometheus 无数据

```bash
# 检查 Prometheus 采集配置
curl -s http://localhost:9090/api/v1/targets | jq .

# 检查 API 的 /metrics 端点
curl -s http://localhost:8000/metrics | head -20

# 检查 Prometheus 数据库大小
du -sh /prometheus/data

# 重启 Prometheus
docker restart <prometheus-container-id>
```

### 应用无法优雅关闭

```bash
# 查看关闭日志
docker logs --tail 50 <api-container-id>

# 检查待处理请求
ss -ntp | grep 8000

# 强制关闭
docker kill <api-container-id>

# 检查是否有未清理的资源
ps aux | grep uvicorn
```
