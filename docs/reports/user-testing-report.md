# KB Platform 用户视角评测报告

**评测日期**: 2026-03-18
**评测版本**: v0.12.0 (Sprint 1-4 完毕)
**评测方法**: 模拟三类目标用户，逐环节走通核心流程，从产品、技术、体验三个维度审视

---

## 一、用户画像与场景模拟

### 用户 A：个人知识工作者（小李）
- 场景：把散落的 PDF 学习笔记 + 网页文章 + 音频转录整理成系统化知识库
- 期望：上传 → 看到架构图 → 确认 → 拿到整理好的文档

### 用户 B：企业知识管理员（张经理）
- 场景：为公司 30 人团队搭建 SOP 知识库，有持续更新需求
- 期望：多人协作 → 权限分工 → 审核发布 → 增量更新

### 用户 C：开发者（王工）
- 场景：通过 API 接入，让自己的 AI 客服系统调用结构化知识
- 期望：RESTful API → 上传 → 检索 → 拿到格式化知识

## 二、核心流程走通评测

### 2.1 注册 → 登录 → 创建项目
| 环节 | 是否可用 | 评价 |
|------|---------|------|
| 注册 | ✅ 可用 | 自动创建租户+管理员，流程清晰 |
| 登录 | ✅ 可用 | 返回 Access Token + Refresh Token |
| Token 刷新 | ✅ 可用 | 30分钟过期 + 7天 refresh，合理 |
| 创建项目 | ✅ 可用 | 支持 industry_hint，为后续 AI 识别提供上下文 |

**用户体验问题**：
- ⚠️ 注册时无邮箱验证，任何人可注册任意邮箱
- ⚠️ 无密码强度要求，可设置弱密码
- 💡 注册后无引导流程，用户不知道下一步该做什么

### 2.2 上传资料 → 解析 → 生成架构
| 环节 | 是否可用 | 评价 |
|------|---------|------|
| 文件上传 | ✅ 可用 | SHA-256 去重、类型白名单、大小限制（100MB），安全可靠 |
| URL 导入 | ✅ 可用 | SSRF 防护已实现（私有 IP 拦截、协议限制） |
| 压缩包导入 | ✅ 可用 | 自动展开、逐文件去重、100 文件上限 |
| 文本解析 | ✅ 可用 | TextParser 按段落切分并标记标签 |
| 创建任务 | ✅ 可用 | 返回 job_id，可轮询状态 |
| 架构生成 | ✅ 可用 | LLM 调用 → JSON 解析 → 写入 Architecture + ArchitectureNode |
| 文档生成 | ✅ 可用 | 逐节点生成 → 带来源引用 → 带冲突检测 |

**🔴 关键阻塞**：
1. **只有 TextParser** — PDF、图片、音频、视频等多模态资料上传后永远停留在 `parse_status=pending`，用户上传了 PDF 但系统不会告诉他"我解析不了"，只会默默搁置
2. **解析和生成任务需要 Celery Worker 和 AI Orchestrator 同时运行** — 但 `docker-compose.yml` 中没有定义 worker 和 orchestrator 服务，用户 `docker-compose up` 后只有 API + DB + Redis + MinIO 启动，任务永远处于 `pending` 状态
3. **任务创建后没有自动触发 Celery 任务** — `job_service.create()` 只创建 Job 记录，不调用 `celery_app.send_task()`，需要手动触发

### 2.3 架构审核 → 文档审核 → 发布
| 环节 | 是否可用 | 评价 |
|------|---------|------|
| 查看架构 | ✅ 可用 | 树状结构可查 |
| 发布架构 | ✅ 可用 | draft → published 状态流转 |
| 文档审核 | ✅ 可用 | draft → reviewing → published |
| 版本对比 | ✅ 可用 | diff 算法可用，支持逐行对比 |
| 来源追溯 | ✅ 可用 | SourceRef 链接到原始片段 |

**用户体验问题**：
- ⚠️ 架构发布后没有"撤回"功能，只能手动新建 draft
- ⚠️ 文档审核没有"驳回"操作（reviewing 只能 → published），reviewer 无法打回给 editor 修改
- ⚠️ 没有"编辑文档内容"的 API — 文档内容只能由 AI 生成，人工无法修改

### 2.4 增量更新 → 冲突处理
| 环节 | 是否可用 | 评价 |
|------|---------|------|
| 增量接入 | ✅ 可用 | LLM 分类：new / supplement / correction / conflict |
| 冲突列表 | ✅ 可用 | 分页查询，支持 pending 筛选 |
| 冲突解决 | ✅ 可用 | 记录解决人和备注 |

**用户体验问题**：
- ⚠️ 增量分类结果（new/supplement 等）不在 API 响应中展示给用户，用户看不到 LLM 做了什么判断
- ⚠️ "冲突解决"只改状态，不实际合并或修改文档内容

### 2.5 模型配置 → 权限 → 审计
| 环节 | 是否可用 | 评价 |
|------|---------|------|
| 添加模型供应商 | ✅ 可用 | API Key AES-256 加密，响应掩码 |
| 模型路由 | ✅ 可用 | 按任务类型路由到不同模型 |
| 连通性测试 | ✅ 可用 | 调用模型验证 |
| 角色权限 | ✅ 可用 | 6 级层级，写操作全部受控 |
| 审计日志 | ✅ 可用 | 8 种操作可查，支持筛选 |

## 三、用户故事验证

### 故事 1：初次建库（PRD 9.1）
> "上传资料后，系统先给我一个'知识系统架构图'，让我确认，然后再正式整理内容"

**验证结果：🟡 部分达成**
- API 层面完全支持
- 但实际使用需要：(1) 启动 Celery Worker (2) 启动 AI Orchestrator (3) 配置 LLM API Key
- 这三步在部署文档中未明确说明
- 用户实际体验：上传后看到 `parse_status: pending`，然后…就没有然后了

### 故事 2：多模态资料整理（PRD 9.2）
> "把 PDF、视频、聊天记录、网页链接一起导入"

**验证结果：🔴 未达成**
- 只有 TextParser，不支持 PDF / 图片 OCR / 音频转写 / 视频拆解
- PRD 7.2 明确要求多模态解析
- 上传非文本文件后，系统沉默，不告知用户无法处理

### 故事 3：持续更新（PRD 9.3）
> "新材料可以持续进入，不需要整库重做"

**验证结果：🟡 部分达成**
- `classify_incremental` 任务逻辑完整（new/supplement/correction/conflict 四分类）
- 但同样依赖 Celery Worker 运行
- 且分类结果不在 API 响应中可见

### 故事 4：外部 AI 调用（PRD 9.4）
> "通过 API 推入资料，让我的 AI 系统直接检索到最新知识"

**验证结果：🔴 未达成**
- 全文检索（`/v1/search`）仅做数据库 LIKE 查询，不是语义检索
- 没有向量化存储和 embedding 能力
- 没有 API Key 认证机制（只有 JWT），外部系统集成不方便

## 四、技术架构评价

### 4.1 优势
| 项 | 评价 |
|---|------|
| **多租户隔离** | 全链路 tenant_id 注入，从 JWT → Depends → Service → Query，隔离彻底 |
| **数据完整性** | SHA-256 去重、版本追溯（doc_version + source_ref）、软删除、审计日志 |
| **安全性** | AES-256 密钥加密、SSRF 防护、JWT + Refresh Token、RBAC 6 级权限 |
| **幂等设计** | upload 去重、架构生成删除旧 draft 重建、增量分类有状态跟踪 |
| **测试基线** | 157 tests，覆盖正常路径 + 异常路径 + 权限边界 |

### 4.2 架构问题
| 严重度 | 问题 | 影响 |
|--------|------|------|
| 🔴 严重 | **docker-compose 缺少 worker/orchestrator 服务定义** | 用户 docker-compose up 后系统无法执行任何 AI 任务 |
| 🔴 严重 | **Job 创建不触发 Celery 任务** | job_service.create() 只写 DB，不调 send_task()，任务永远 pending |
| 🔴 严重 | **只有 TextParser** | 产品号称"多模态"但只能处理纯文本 |
| 🟡 中等 | **AI Orchestrator 用同步 SQLAlchemy** | 用 create_engine 而非 async_engine，在 Celery 任务中可以接受但与 API 层风格不统一 |
| 🟡 中等 | **全文检索是 SQL LIKE** | 性能差、不支持语义匹配，大数据量会很慢 |
| 🟡 中等 | **没有 Alembic 迁移脚本** | infra/sql/ 目录为空，模型定义存在但无实际迁移，新部署需手动建表 |
| 🟢 轻微 | **错误信息中英混杂** | 有些中文"文件类型不允许"、有些英文"Project not found" |

### 4.3 安全问题
| 严重度 | 问题 | 影响 |
|--------|------|------|
| 🟡 中等 | **JWT Secret 硬编码** | docker-compose.yml 中 `change-me-in-production`，开发环境可以但需部署文档强调 |
| 🟡 中等 | **MinIO 默认凭据** | minioadmin/minioadmin 在 docker-compose 中硬编码 |
| 🟡 中等 | **无邮箱验证** | 注册时不验证邮箱归属 |
| 🟡 中等 | **无密码强度校验** | 可设置 "1" 这样的弱密码 |
| 🟢 轻微 | **token_revocation 未实现** | 设计文档提到 Redis 存 refresh token 支持主动吊销，但代码中 refresh token 存在 DB 不在 Redis |

## 五、交互易用性评价

### 5.1 API 设计
| 项 | 评分 | 说明 |
|---|------|------|
| RESTful 规范性 | ⭐⭐⭐⭐ | 路径清晰，HTTP 方法得当 |
| 响应格式一致性 | ⭐⭐⭐⭐⭐ | 统一 `{data, meta}` 格式，分页标准化 |
| 错误码体系 | ⭐⭐⭐⭐ | 分域错误码（AUTH_*, ASSET_*, DOC_*），结构清晰 |
| 状态码使用 | ⭐⭐⭐⭐ | 201 创建、404 不存在、409 冲突、403 权限、429 限流 |
| 分页支持 | ⭐⭐⭐⭐ | page + page_size + total，标准模式 |
| OpenAPI 文档 | ⭐⭐⭐ | FastAPI 自动生成，但描述缺乏中文说明 |

### 5.2 缺失的用户交互
| 缺失项 | 影响 |
|--------|------|
| **无文档编辑 API** | 用户无法手动修改 AI 生成的文档内容 |
| **无架构编辑 API**（节点拖拽/排序） | 只能新增和修改属性，不能移动节点位置 |
| **无批量操作** | 不能批量审核、批量发布、批量删除 |
| **无任务进度通知** | 只能轮询 GET /jobs/{id}，没有 WebSocket/SSE 推送 |
| **无导出功能** | 不能导出知识文档为 PDF / ZIP |
| **无回滚功能** | 文档发布后不能回滚到上一版本 |
| **审核驳回** | reviewing 状态不能回退到 draft |

## 六、真实用户是否能解决问题？

### 用户 A（个人知识工作者）
**能解决吗：🔴 不能**
- 上传 PDF / 音频后系统不做任何事
- 即使是纯文本，需要自己启动 3 个服务、配置 LLM Key 才能看到结果
- 没有前端界面，纯 API 对个人用户不友好
- 结论：当前版本对个人用户没有可用价值

### 用户 B（企业知识管理员）
**能解决吗：🟡 理论上可以，实际不行**
- 权限体系完善（6 级 RBAC）、审计可追踪、多租户隔离
- 但部署链路不通（docker-compose 缺服务）、审核流缺驳回、没有前端
- 结论：后端能力具备，但距离"可用"还差最后一公里

### 用户 C（开发者）
**能解决吗：🟡 基础可用**
- REST API 规范、响应格式清晰、OpenAPI 自动生成
- 能上传文本、创建任务、查询文档和来源
- 但全文检索太弱（LIKE），没有语义检索，不能作为 AI 知识源
- 结论：作为 CRUD 后端可用，作为 AI 知识系统后端还不够

## 七、建议优先级排序

### P0 — 不修复则系统无法真正运行
1. **docker-compose 补充 worker + orchestrator 服务定义**
2. **job_service.create() 中调用 celery send_task() 触发实际任务**
3. **Alembic 迁移脚本初始化**（让新部署能自动建表）

### P1 — 核心体验缺失
4. **PDF 解析器**（至少用 PyMuPDF 或 pdfplumber）
5. **文档内容编辑 API**（PUT /v1/docs/{id}/content）
6. **审核驳回功能**（reviewing → draft）
7. **上传非文本文件时返回明确提示**（而非静默 pending）

### P2 — 体验完善
8. 错误信息统一为中文
9. 注册增加密码强度校验
10. 任务状态 WebSocket 推送
11. 批量操作 API
12. 文档导出功能

### P3 — 长期能力
13. 向量化存储 + 语义检索
14. 图片 OCR 解析器
15. 音频 ASR 解析器
16. 前端 Web 界面

## 八、总结

**一句话评价**：后端骨架扎实、安全和治理能力完善，但从"用户能不能真正用起来"的角度看，核心流水线没有打通——上传后的资料无法自动流向解析、生成、输出环节。

**类比**：这就像造了一台发动机精密的汽车，但变速箱没连上——引擎（AI Orchestrator）有了、轮子（API）有了、仪表盘（审计/权限/RBAC）有了，但踩油门（创建 Job）后车不动（Celery 任务不触发）。

**量化评估**：
| 维度 | 评分（1-10） | 说明 |
|------|-------------|------|
| 代码质量 | 8 | 分层清晰、测试覆盖好、安全措施到位 |
| 架构设计 | 7 | 微服务划分合理，但服务间连接未打通 |
| 功能完成度 | 5 | Sprint 1-4 代码写完但端到端流程跑不通 |
| 用户可用性 | 3 | 没有前端、核心流水线断裂、多模态缺失 |
| 安全性 | 8 | RBAC + 加密 + SSRF + 审计 + 租户隔离 |
| 部署就绪度 | 4 | docker-compose 不完整、无迁移脚本、无部署文档 |
