## 第一部分：产品全景解读

### 1.1 产品定位与目标用户

**产品一句话**：将多模态原始资料（文档、图片、音频、视频、网页）自动整理为可追溯、可维护、可被 AI 使用的结构化知识系统。

**目标用户**：
- 个人学习者：整理学习笔记、研究资料
- 团队用户：沉淀 SOP、培训资料、FAQ
- 企业用户：构建行业知识库、客户支持知识库

**核心价值主张**：
- 不是"总结"而是"系统化"——保留细节、可追溯
- 支持增量更新——新资料自动归入已有架构
- AI 原生——输出格式直接可被 AI 消费

### 1.2 产品是否真正解决了用户问题？

| 用户痛点 | 产品方案 | 当前状态 | 评价 |
|----------|---------|---------|------|
| 资料格式杂乱，AI 无法直接用 | 多模态解析 → 结构化 Markdown | 解析器存在但端到端未充分验证 | ⚠️ 概念正确，落地待验证 |
| 总结后丢失细节（知识坍缩） | 多份 Markdown 文档 + 来源追溯 | SourceRef 表设计完整 | ✅ 架构合理 |
| 新资料无法稳定补入 | 增量摄入 + 冲突检测 | 增量 API 存在，AI 分类逻辑存在 | ⚠️ 依赖 LLM 质量，未真实验证 |
| 缺乏整体结构 | 知识架构图管理 | 前端树编辑器可用 | ✅ 基本可用 |
| 没有治理流程 | 审核 → 发布 → 版本化 | 完整的状态流转 | ✅ 流程完整 |

**结论**：产品设计思路正确且有差异化价值，但从"能用"到"好用"仍有距离。核心卡点在端到端流程的真实 LLM 调用质量和用户体验打磨。

### 2.2 关键安全场景详细分析

#### SEC-01: IDOR — 跨租户文档-节点分配（CRITICAL）

**位置**: `services/api/app/services/doc_service.py`
**问题**: `batch_assign_node` 方法接收 `node_id` 参数后，未验证该 node 是否属于当前租户的项目。攻击者可将自己的文档分配到其他租户的架构节点上，实现跨租户数据关联。

**攻击步骤**:
1. 租户 A 创建架构节点，获取 node_id
2. 租户 B 调用 `POST /v1/docs/batch-assign-node` 传入租户 A 的 node_id
3. 租户 B 的文档被分配到租户 A 的架构树下

**修复建议**: 在 `batch_assign_node` 中增加 `_verify_node_belongs_to_tenant()` 校验。

#### SEC-02: Rate Limiter JWT verify_exp=False（HIGH）

**位置**: `services/api/app/middleware/rate_limit.py`
**问题**: 中间件在提取 tenant_id 进行限流时，使用 `options={"verify_exp": False}` 解码 JWT。这意味着已过期的 token 仍然能通过 tenant_id 识别，避开更严格的 IP 级限流（IP 限流阈值更低）。

**修复建议**: 改为 `verify_exp=True`，解码失败时回退到 IP 级限流。

#### SEC-07: 前端 localStorage 存储 JWT（HIGH）

**位置**: `apps/web/src/stores/auth-store.ts`
**问题**: JWT access_token 直接存储在 `localStorage`。任何通过 XSS 注入的脚本都可以 `localStorage.getItem("access_token")` 窃取 token，获得完全的 API 访问权限。

**修复建议**:
- 短期：改用 `sessionStorage`（关闭标签页即清除）
- 长期：改为 HttpOnly + Secure + SameSite cookie 方案

#### SEC-08: Markdown XSS（HIGH）

**位置**: `apps/web/src/components/markdown-view.tsx`
**问题**: 使用 `react-markdown` 渲染用户提交的 Markdown 内容，但未设置 `skipHtml={true}`。攻击者可在知识文档中嵌入 `<script>` 标签或 `<img onerror>` 事件，在其他用户浏览时执行任意 JavaScript。

**修复建议**: 添加 `skipHtml={true}` 属性，或使用 `rehype-sanitize` 插件。

### 3.2 P1 级关键 Bug 详情

#### BUG-P1-01: 注册事务不完整（租户孤儿记录）

**路径**: 注册 → 创建租户 → 创建用户
**问题**: `auth_service.register()` 先创建 Tenant 再创建 User。如果 User 创建失败（如 email 唯一约束冲突），Tenant 已经 flush 到数据库但未回滚，产生孤儿 Tenant 记录。
**影响**: 数据库污染，可能影响后续同名租户创建。

#### BUG-P1-02: Asset 记录先于文件上传创建

**路径**: 上传文件 → 创建 DB 记录 → 上传到 MinIO
**问题**: `asset_service.upload()` 在调用 MinIO 上传之前就 flush 了 Asset 记录。如果 MinIO 宕机或网络中断，数据库中存在 Asset 记录但 MinIO 中没有对应文件。
**影响**: 后续解析任务尝试从 MinIO 下载文件时必然失败。

#### BUG-P1-03: 缺少显式 commit()

**路径**: 多个服务方法
**问题**: 服务层大量使用 `session.flush()` 而非 `session.commit()`。事务边界不清晰，依赖 FastAPI 中间件的隐式 commit。如果中间件配置有误或异常路径，数据可能丢失。
**影响**: 所有写操作都存在数据丢失风险。

#### BUG-P1-04: 文档可跳过审核直接发布

**路径**: 创建文档 → 直接 publish
**问题**: `doc_service.publish()` 未检查文档当前状态是否为 "reviewed"。状态为 "draft" 的文档可以直接被 publish，绕过审核流程。
**影响**: 审核流程形同虚设。

#### BUG-P1-05: 架构树可创建循环引用

**路径**: 创建节点 A → 创建节点 B(parent=A) → 修改 A 的 parent=B
**问题**: `architecture_service.update_node()` 未检测循环引用。将父节点设置为自己的子孙节点会创建无限循环，导致前端树渲染崩溃或后端递归查询 OOM。
**影响**: 架构树功能完全不可用。

#### BUG-P1-06: 搜索特殊字符导致 SQL 错误

**路径**: 搜索 → 输入 `hello&world` 或 `hello(world`
**问题**: `search_service.text_search()` 将用户输入直接拼入 PostgreSQL `to_tsquery()` 函数。`&`、`(`、`|`、`!` 等字符是 tsquery 语法符号，会导致 SQL 语法错误。
**影响**: 搜索功能在包含特殊字符时完全崩溃，返回 500 错误。

#### BUG-P1-07: 批量操作部分失败不回滚

**路径**: 批量审核 5 个文档 → 第 3 个因状态不对失败
**问题**: `doc_service.batch_review()` 使用 for 循环逐条处理。如果中间某条失败，前面已处理的不会回滚，导致批量操作部分成功部分失败，数据不一致。
**影响**: 用户无法确定哪些操作成功了，需手动排查。

#### BUG-P1-08: 用户可邀请更高角色的用户（权限提升）

**路径**: editor 用户 → 邀请 → 设置角色为 tenant_admin
**问题**: `user_service.invite()` 未检查邀请人的角色是否高于被邀请人的目标角色。editor 可以邀请 tenant_admin 级别的用户，实现权限提升。
**影响**: 整个 RBAC 体系可被绕过。

#### BUG-P1-09: 用户可删除自己的账号

**路径**: tenant_admin → 用户管理 → 删除自己
**问题**: `user_service.delete()` 未检查被删除用户是否为当前操作者。租户唯一管理员删除自己后，该租户再无管理员，所有管理功能不可用。
**影响**: 租户被永久锁定。

#### BUG-P1-10: 搜索空查询返回全量数据

**路径**: 搜索 → 提交空字符串
**问题**: `search_service.text_search()` 未验证查询字符串是否为空。空查询可能返回项目下全部文档，在大数据量下导致性能问题。
**影响**: 性能风险 + 信息过度暴露。

#### BUG-P1-11: 模型 API Key 未加密存储

**路径**: 配置 → 添加模型提供商 → 输入 API Key
**问题**: 当 `ENCRYPTION_KEY` 环境变量缺失或为默认值时，`model_provider_service.create()` 中的加密逻辑可能失败或使用弱密钥加密。
**影响**: API Key 明文或弱加密存储，数据库泄露即暴露所有 LLM API Key。

#### BUG-P1-12: 冲突解决无权限检查

**路径**: viewer 角色 → 调用冲突解决 API
**问题**: `conflict_service.resolve()` 未检查当前用户是否有足够权限解决冲突（至少应为 reviewer）。
**影响**: 低权限用户可以解决冲突，绕过审核流程。

### 4.2 关键 UX 问题详情

#### UX-01: 无"忘记密码"功能（HIGH）

**位置**: `/src/app/login/page.tsx`
**问题**: 登录页面没有"忘记密码"链接和对应的密码重置流程。用户忘记密码后完全无法自助恢复账户。
**影响**: 用户阻断，必须联系管理员手动重置。

#### UX-02: Token 过期无刷新机制（HIGH）

**位置**: `/src/stores/auth-store.ts`, `/src/lib/api.ts`
**问题**: 前端没有实现 Token 自动刷新逻辑。当 access_token 过期（30 分钟）后，用户的下一个 API 请求将直接失败，但前端不会自动调用 refresh 端点获取新 token，也不会优雅地重定向到登录页。
**影响**: 用户使用 30 分钟后突然看到错误，体验极差。

#### UX-03: 文件上传无进度指示（MEDIUM）

**位置**: `/src/components/file-upload.tsx`
**问题**: 文件上传使用标准 fetch API，没有实现上传进度条。上传大文件时用户不知道进度，无法取消，无法重试失败的上传。
**影响**: 上传体验差，尤其对于大文件（系统支持最大 100MB）。

#### UX-04: 密码输入无可见切换（MEDIUM）

**位置**: 登录页 + 注册页
**问题**: 密码输入框没有"显示/隐藏密码"的眼睛图标。用户无法确认自己输入的密码是否正确。
**影响**: 增加登录失败率，尤其在移动设备上。

#### UX-05: 侧边栏不支持移动端（MEDIUM）

**位置**: `/src/components/sidebar.tsx`
**问题**: 侧边栏固定宽度 224px（w-56），在移动设备上不会收起或转为汉堡菜单。在小屏设备上内容区域被严重压缩。
**影响**: 移动端基本不可用。

#### UX-06: 无错误边界（MEDIUM）

**位置**: 全局
**问题**: 整个应用没有 React Error Boundary。任何组件级别的 JS 错误（如渲染异常）会导致整个页面白屏崩溃，用户只能刷新。
**影响**: 单点组件错误导致全面不可用。

#### UX-07: 编辑文档无防丢失保护（MEDIUM）

**位置**: `/src/app/(dashboard)/docs/[id]/edit/page.tsx`
**问题**: 文档编辑页面没有"未保存更改"的离开提示。用户意外关闭标签页或导航到其他页面时，编辑内容直接丢失。
**影响**: 用户工作成果丢失。

#### UX-08: 搜索结果无高亮（LOW）

**位置**: `/src/app/(dashboard)/projects/[id]/search/page.tsx`
**问题**: 搜索结果中不会高亮匹配的关键词，用户难以快速定位相关内容。
**影响**: 搜索效率降低。

|------|----------|------|--------|-----|

### 5.2 关键基础设施问题

#### INFRA-01: Docker 容器以 root 运行（HIGH）

**位置**: 所有 Dockerfile
**问题**: 无 `USER` 指令，所有容器以 root 身份运行。容器逃逸即获得宿主机 root 权限。
**修复**: 添加非 root 用户。

#### INFRA-02: 无 .dockerignore（HIGH）

**位置**: 项目根目录
**问题**: 缺少 `.dockerignore` 文件。Docker 构建上下文包含 `.git`、`.env`、`node_modules`、`__pycache__` 等无关文件，增加镜像体积，泄露敏感信息。

#### INFRA-03: build.yml Dockerfile 路径错误（HIGH）

**位置**: `.github/workflows/build.yml`
**问题**: CI 构建引用 `services/api/Dockerfile` 等路径，实际 Dockerfile 在 `infra/docker/api.Dockerfile`。Release 构建必定失败。
**影响**: 无法自动构建和发布 Docker 镜像。

#### INFRA-04: 迁移脚本缺少 doc_embedding 表（CRITICAL）

**位置**: `infra/sql/versions/`
**问题**: 初始迁移未包含 `doc_embedding` 表的创建。后续迁移尝试修改该表的列类型，但在全新数据库上会因表不存在而失败。
**影响**: 全新环境部署必然失败。

#### INFRA-05: Celery 无死信队列（HIGH）

**位置**: 所有 Worker
**问题**: 任务达到最大重试次数后直接丢弃。没有死信队列捕获失败任务，无法人工干预或重试。
**影响**: 用户上传的资料可能在解析失败后完全丢失，且无通知。

#### INFRA-06: OpenAPI 规范严重不完整（CRITICAL）

**位置**: `openapi/openapi.yaml`
**问题**: 手写的 OpenAPI 规范仅覆盖 6 个端点，而实际 API 有 50+ 端点。缺少认证 scheme、错误响应定义、分页参数。
**影响**: 外部集成方无法基于规范开发；API 契约不可信。

#### INFRA-07: 依赖版本未锁定（HIGH）

**位置**: 所有 `pyproject.toml`
**问题**: Python 依赖使用 `>=` 宽松约束（如 `fastapi>=0.110`），无 lock 文件。不同时间构建可能得到不同版本的依赖，导致不可重现的构建问题。
**修复**: 使用 `pip-compile` 或 `uv lock` 生成锁文件并提交到 git。
