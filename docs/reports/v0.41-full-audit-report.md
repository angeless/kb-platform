# KB Platform v0.41.8 — 全面深度审计报告

> 审计日期：2026-03-22
> 审计版本：v0.41.8（已封板）
> 审计范围：后端 API（26 文件）、前端 SPA（60+ 文件）、数据库模型（13 个）、基础设施（Docker/CI/配置）、Worker 服务（3 个）
> 审计角色：专业软件测试工程师 + 安全审计员 + 真实用户模拟

---

## 一、总体评估

**综合评级：B-（有条件的准生产级）**

KB Platform 作为一个 AI 知识系统构建平台，在架构设计上体现了较高的工程素养——微服务分离清晰、多租户隔离意识强、安全基础设施（bcrypt/JWT/httpOnly/AES-256-GCM）选型正确。但经过全面深度审计，发现 **4 个严重问题**、**9 个高危问题**、**15 个中等问题**，其中严重问题会直接阻塞生产部署。

**核心结论**：架构基础扎实，但安全细节和用户体验存在明显短板。建议在修复严重问题后（预计 2-3 周），可进入受限的 beta 测试阶段。

---

## 二、面向人群与产品定位解读

### 2.1 目标用户画像

KB Platform 定位为"将多模态原始资料自动整理为可追溯、可维护、可被 AI 使用的结构化知识系统"。从功能设计推断，目标用户群体为：

- **主要用户**：中小型企业的知识管理团队（5-50人规模）
- **关键角色**：知识管理员（上传/整理）、内容审核员（审核/发布）、普通员工（搜索/查阅）
- **使用场景**：企业内部文档知识化、技术文档管理、合规文档追踪

### 2.2 产品价值评估

**已解决的问题**：
- 多模态文档（PDF/文本/OCR/ASR）统一入库流程
- 文档版本管理 + 审核发布工作流
- 全文搜索 + 语义搜索 + AI 问答三合一检索
- 架构树管理（知识分类体系）
- 多租户隔离（SaaS 潜力）

**尚未解决的关键用户痛点**：
- 邮件通知系统缺失（密码重置、审核通知、任务完成通知）
- 协作功能缺失（评论、@提醒、协同编辑）
- 权限粒度不足（只有角色层级，缺少项目级权限分配 UI）
- 搜索结果无分页（大量文档时体验恶化）
- 数据导入导出能力单薄（仅 Markdown/ZIP，缺少 PDF/Word/Notion 等主流格式）

## 三、严重问题（CRITICAL）— 必须在上线前修复

### C-01：forgot-password 页面存在语法错误导致渲染崩溃

**文件**：`apps/web/src/app/forgot-password/page.tsx`
**行号**：第 134 行

```tsx
// 文件末尾存在多余的残留代码
}
div>         // ← 这里有一个游离的 HTML 片段
  );
}
```

**影响**：忘记密码页面完全无法渲染，导致密码恢复流程 100% 阻断。

**严重度**：CRITICAL — 核心用户流程完全不可用。

**验证方式**：直接打开 `/forgot-password` 路由，页面白屏。

---

### C-02：注册后跳转到 /projects 但未登录，导致用户困惑

**文件**：`apps/web/src/app/register/page.tsx` 第 43-44 行 + `stores/auth-store.ts` 第 48-58 行

注册成功后执行 `router.push("/projects")`，但 `register()` 方法不会设置 cookies 或 auth 状态。Dashboard layout 的 `checkAuth()` 会返回 null，然后检查 `localStorage.getItem("access_token")`（该值从未被写入），最终重定向到 `/login`。

```typescript
// auth-store.ts 第 52 行
// Register does not return tokens / set cookies — user must login after registration
set({ isLoading: false });

// register/page.tsx 第 44 行
router.push("/projects"); // ← 跳转到需要登录的页面，但没有登录
```

**影响**：新用户注册后被踢回登录页，没有任何成功提示，用户误以为注册失败。

**严重度**：CRITICAL — 首次用户体验完全断裂。

**修复建议**：注册成功后跳转到 `/login` 并显示"注册成功，请登录"的提示。

---

### C-03：Dashboard 认证守卫使用了从未写入的 localStorage 值

**文件**：`apps/web/src/app/(dashboard)/layout.tsx` 第 26-31 行

```typescript
useEffect(() => {
  if (user === null && typeof window !== "undefined") {
    const token = localStorage.getItem("access_token");
    if (!token) {
      router.replace("/login");
    }
  }
}, [user, router]);
```

系统使用 httpOnly cookie 管理 token（正确的安全做法），但这里却检查 `localStorage` 中的 `access_token`——该值在整个代码库中从未被写入。

**影响**：存在竞态条件。`checkAuth()` 异步请求尚未返回时，`user` 为 null，`localStorage` 也为空，用户被错误地重定向到登录页。页面刷新时有概率闪烁到登录页再回来。

**严重度**：CRITICAL — 已登录用户刷新页面有概率被踢出。

**修复建议**：移除 localStorage 检查，改为等待 `checkAuth()` 完成后再判断。添加 `isCheckingAuth` 状态。

---

### C-04：密码重置 Token 在 API 响应中直接返回（即使在生产环境）

**文件**：`services/api/app/services/auth_service.py` 第 156 行

```python
# Dev mode: return raw token in response for testing
return {"message": response_message, "reset_token": raw_token}
```

这里的注释说是"Dev mode"，但代码中没有任何环境判断——生产环境同样会返回明文 reset token。攻击者可以通过调用 forgot-password API 获取任意用户的密码重置令牌，直接接管账户。

**影响**：任意账户接管漏洞（Account Takeover）。

**严重度**：CRITICAL — 0-click 账户劫持。

**修复建议**：

```python
if self.settings.environment == "development":
    return {"message": response_message, "reset_token": raw_token}
return {"message": response_message}
```

## 四、高危问题（HIGH）— 上线前应修复

### H-01：SSRF — URL 导入无任何域名/IP 限制

**文件**：`services/api/app/routers/assets.py` 第 100-118 行

`import_url` 端点接受任意 URL，无域名白名单、无内网 IP 过滤。攻击者可以请求：
- `http://169.254.169.254/latest/meta-data/` — 获取云服务商实例凭证
- `http://localhost:8080/healthz` — 探测内部服务
- `http://redis:6379/` — 访问内部 Redis

**严重度**：HIGH — 内网侦察 + 潜在凭证泄露。

---

### H-02：CORS 配置允许凭证但无 CSRF 保护

**文件**：`services/api/app/main.py` 第 76-82 行

```python
app.add_middleware(
    CORSMiddleware,
    allow_credentials=True,  # ← 允许发送 cookie
    ...
)
```

使用 httpOnly cookie 传递 token 且 `allow_credentials=True`，但所有 POST/PUT/DELETE 请求没有 CSRF token 验证。攻击者可以在恶意网站构造表单，利用用户已有的 cookie 发起跨站请求。

**缓解因素**：`SameSite=lax` 对大多数现代浏览器有效，但不应作为唯一防线。

**严重度**：HIGH。

---

### H-03：WebSocket 认证通过 URL query 参数传递 JWT

**文件**：`services/api/app/routers/ws.py` 第 30 行

```python
token = websocket.query_params.get("token")
```

JWT token 通过 URL 传递，会出现在：浏览器历史记录、服务器访问日志、代理服务器日志、Referer 头部。

**严重度**：HIGH — token 泄露面扩大。

---

### H-04：Embedding 服务 JSONB 回退路径存在 N+1 查询 + 内存问题

**文件**：`services/api/app/services/embedding_service.py` 第 141-182 行

`_semantic_search_jsonb_fallback` 方法先加载所有 embedding 到内存（每条 1536 维 float），然后对每个命中结果逐一查询文档详情。如果项目有 10,000 个文档，将：
1. 加载约 60MB 向量数据到 Python 内存
2. 在 Python 中做余弦相似度计算
3. 对每个 top-k 结果单独发一次 SQL 查询

**严重度**：HIGH — 大项目下内存溢出 + 搜索超时。

---

### H-05：Embedding 删除-插入非原子操作

**文件**：`services/api/app/services/embedding_service.py` 第 73-91 行

```python
# Upsert: delete existing then insert
await self.db.execute(delete(DocEmbedding).where(DocEmbedding.doc_id == doc_id))
record = DocEmbedding(...)
self.db.add(record)
await self.db.flush()
```

delete 和 insert 之间如果发生异常，embedding 数据会丢失。并发请求可能导致重复记录。

**严重度**：HIGH — 数据一致性风险。

---

### H-06：QA 服务 API Key 解密调用不存在的函数

**文件**：`services/api/app/services/qa_service.py` 第 135-140 行

```python
try:
    from app.utils.crypto import decrypt_value  # ← 该函数不存在！
    api_key = decrypt_value(api_key)
except Exception:
    pass  # Already decrypted or plain text in dev mode
```

`crypto.py` 中只有 `encrypt()` 和 `decrypt()` 函数，不存在 `decrypt_value()`。每次调用都会 ImportError 然后静默忽略。

**严重度**：HIGH — AI 问答功能可能完全不工作（如果 API key 确实是加密存储的）。

---

### H-07：MinIO 使用默认凭证且硬编码在 docker-compose 中

**文件**：`docker-compose.yml` 第 33-34 行

```yaml
MINIO_ROOT_USER: minioadmin
MINIO_ROOT_PASSWORD: minioadmin
```

PostgreSQL 密码已做 `${VAR:?msg}` 强制注入，但 MinIO 和 Redis 的凭证仍然硬编码。

**严重度**：HIGH — 存储服务开放访问。

---

### H-08：Rate Limiting 无账户锁定机制

登录接口限流为每分钟 10 次/IP，但没有账户级锁定。分布式暴破不受限。

**严重度**：HIGH — 弱密码账户易被暴破。

---

### H-09：Redis 无密码保护

**严重度**：HIGH — 任何人可访问缓存/队列数据。

## 七、架构评估

### 7.1 优点

- 微服务边界清晰（API / Ingestion / Pipeline / AI Orchestrator）
- 共享包设计合理（models, schemas, config, errors）
- 多租户基因贯穿（TenantService 基类）
- 异步优先（SQLAlchemy async + Celery）
- 安全基础选型正确（bcrypt, httpOnly, AES-256-GCM）

### 7.2 技术债务

| 领域 | 债务 | 影响 |
