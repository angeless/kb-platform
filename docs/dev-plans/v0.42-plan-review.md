## 二、需要调整的偏差（建议修正，不调整也不会出大问题）

### 偏差 1：T-42-02-D CSRF middleware — CORS allow_headers 需同步更新

**计划描述**：
> 所有 POST/PUT/PATCH/DELETE 要求 `X-Requested-With: XMLHttpRequest` 头

**当前代码**：`main.py` 的 CORS middleware 配置 `allow_headers=["Content-Type", "Authorization", "X-Request-ID"]`（v0.41.7 收紧后的值）。

**偏差**：如果前端发送 `X-Requested-With` 头但 CORS 不允许，**浏览器会在 preflight 阶段拒绝请求**（跨域时 preflight OPTIONS 请求会检查 Access-Control-Allow-Headers）。

**调整建议**：
- T-42-02-D 或 T-42-02-E 必须同时修改 `main.py` CORS 的 `allow_headers`，添加 `"X-Requested-With"`
- 这不算修改 v0.41.7 的业务逻辑，而是为新增安全机制配套

---

### 偏差 2：T-42-01-C 认证守卫 — `isCheckingAuth` 与现有 `isLoading` 语义重叠

**计划描述**：
> 新增 `isCheckingAuth` 布尔状态

**当前代码**：auth-store 已有 `isLoading: boolean`，用于 login/register/checkAuth 等操作。

**偏差**：新增 `isCheckingAuth` 可能与 `isLoading` 产生语义混淆。两个布尔值控制同一类行为，增加维护负担。

**调整建议**：考虑两种方案（二选一）：
- **方案 A**：不新增字段，改为 `isLoading` 初始值设为 `true`（代表"尚未完成首次 checkAuth"），checkAuth 完成后设为 `false`。layout 中用 `isLoading` 代替 localStorage 检查。
- **方案 B**：新增 `isCheckingAuth` 但明确区分语义（isLoading 用于用户操作，isCheckingAuth 用于静默背景检查）。

---

### 偏差 3：T-42-02-F MinIO 参数化 — docker-compose 中 S3_ACCESS_KEY/S3_SECRET_KEY 也需同步

**计划描述**：
> MinIO 环境变量改为 `${MINIO_ROOT_USER:?}` 和 `${MINIO_ROOT_PASSWORD:?}`

**当前代码**：MinIO 本身的 `MINIO_ROOT_USER/PASSWORD` 是硬编码的，但 api/ingestion-worker/pipeline-worker 服务中的 `S3_ACCESS_KEY` 和 `S3_SECRET_KEY` 也硬编码为 `minioadmin`。`minio-init` 容器中 `mc alias` 命令也用硬编码值。

**偏差**：仅改 MinIO 自身的环境变量而不同步改其他服务的 S3 凭证引用 → MinIO 启动后其他服务连不上。

**调整建议**：
- T-42-02-F 需要同时修改：
  1. MinIO 服务的 `MINIO_ROOT_USER/PASSWORD`
  2. api/ingestion-worker/pipeline-worker 的 `S3_ACCESS_KEY/S3_SECRET_KEY`
  3. minio-init 的 `mc alias` 命令
  4. `.env.example` 添加全部对应条目

## 三、需要注意的风险（不需要改计划，但执行时注意）

### 风险 1：T-42-03-E Docker 端口收紧 — 影响本地开发调试

**计划描述**：
> PostgreSQL/Redis/MinIO 的 `ports:` 改为 `expose:`

**风险**：本地开发时，开发者可能需要直接连接 PostgreSQL（用 pgAdmin/DBeaver）或 Redis（用 redis-cli），端口收紧后无法从宿主机访问。

**建议**：
- 仅在 `docker-compose.production.yml`（T-42-08-C 的 override 文件）中收紧端口
- 基础 `docker-compose.yml` 保留端口暴露，供开发调试使用
- 或者使用 `docker-compose.override.yml` 在开发时暴露端口

---

### 风险 2：T-42-12-E 邮箱唯一性改租户级 — 现有数据兼容性

**计划描述**：
> 移除 email 全局 UNIQUE → 添加 UNIQUE(email, tenant_id)

**风险**：如果现有数据中同一邮箱在不同租户已经存在（虽然当前约束不允许，但如果通过其他方式写入了），迁移可能失败。更重要的是，`auth_service.py` 中的 `login()` 方法是通过 `SELECT ... WHERE email = ?` 查找用户的——如果同一邮箱存在于多个租户，登录逻辑需要额外区分租户。

**建议**：
- 迁移前检查现有数据是否有 email 重复
- `login()` 方法可能需要同时根据 email + tenant context 查询（但当前登录接口没有传 tenant_id）
- 需要设计多租户登录时如何确定用户属于哪个租户（选择器？根据域名？）
- 如果短期内没有"同一邮箱跨租户"的真实需求，**建议推迟到 v0.43**

### 详细分析

**T-42-11-A 修改 WebSocket auth（触碰 T-41-01）**：
- T-41-01 实现了 WebSocket 通过 URL query 传 JWT + 租户隔离
- T-42-11-A 要把 JWT 传递方式从 URL query 改为 cookie
- 这**修改了已封板功能的实现方式**，但不改变业务语义（仍然是 JWT 认证 + 租户隔离）
- **评审意见**：可以接受。安全改进属于审计修复范畴，且不改变外部行为。但必须在 T-42-11-A 中完整保留 T-41-01 的租户隔离逻辑，不能丢失。

**T-42-04-C/D 给 QA 加 SSE（触碰 T-41-03）**：
- T-41-03 实现了 `POST /v1/qa/ask` 返回完整 JSON
- T-42-04-C 要给这个端点加 `stream=true` 参数
- `stream=false`（默认）时行为完全不变 → **向后兼容**
- **评审意见**：可以接受。是纯增量扩展，不修改已有响应格式。

**T-42-01-C 改 Dashboard layout（触碰 T-41-05）**：
- T-41-05 实现了 SessionGuard、骨架屏、checkAuth 逻辑
- T-42-01-C 要移除 localStorage 检查，改进 auth 判断逻辑
- 这**修改了已封板的 layout 组件**
- **评审意见**：可以接受。这是修复 C-03 CRITICAL 级 bug，属于必要修正。但必须保留 T-41-05 的 SessionGuard 和骨架屏逻辑。

**T-42-02-F/G 改 docker-compose（触碰 T-41-08）**：
- T-41-08 将 PostgreSQL/JWT/ENCRYPTION_KEY 参数化了
- T-42-02-F/G 要继续参数化 MinIO 和 Redis
- docker-compose.yml 在 Tier 3 保护（条件保护），当前任务定义已明确列出修改
- **评审意见**：可以接受。是 T-41-08 未完成的安全加固的延续。
